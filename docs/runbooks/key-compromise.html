Key compromise or lost key

Use this runbook when another human can use a signing key, or when nobody can use it any more. The rules and reasons are in Signing and trust: emergency.

  • Compromised: repoctl sign revoke, then config management installs the new key file on all hosts at once. The clients refuse the files of the key until the re-sign.
  • Lost: repoctl sign retire, then the normal rotation. The signatures of a lost key stay valid.
  • The last deployed signer is lost: a new key with a key file record (sign deployed --keyfile).
  • Each step is for a human. repoctl prints the commands for config management.

Rules

  • A human does each step. An agent can read repoctl sign ls, repoctl status and the snapshots, and it can show the commands. It does not sign, push, revoke or change config management (deny list).
  • When you are not sure if a key is lost or compromised, treat it as compromised.
  • When a check fails, stop and tell the team.

Example, a variant of the story: on 2026-11-10, A. Admin loses the YubiKey with the key a.admin on a trip. d.klein has an active, deployed key for el9 and el10.

Trigger

  • A card with a signing key is lost or stolen, or a human may know its PIN.
  • A file key may have a copy, or an attacker may control a host with a key.
  • repoctl repo snapshots --all lists a publish that nobody in the team made.
  • A card is broken, or its PIN, reset code and Admin PIN are blocked. A file key is deleted.

Decide the path

Run repoctl sign ls. It shows which keys are active and deployed for each target.

Compromise

  1. Stop the access. When the human leaves, an organization owner removes the human from the GitHub team (slurm-repo-admins in the examples). Delete the registry tokens of each host that held the key.
  2. Run repoctl sign revoke a.admin and type the key id. Push the set commit: git push origin builder/slurm-26.05.
  3. Run repoctl sign offboard a.admin. Give its output to the owner of config management. Config management installs the new key file with the pinned sum. It erases the key and deletes the dnf repository keyring. It does this first on the HTTP server, then on each client. Do not wait for a release package.
  4. Check each snapshot that sign offboard lists. Compare the publish id, the user and the host with the team channel. When a publish is not known, run repoctl repo restore REF with the newest known snapshot of that target. Do this before the next step.
  5. With another active, deployed key, run repoctl repo resign --signer a.admin --target el9. Do the same for each other target that sign offboard lists.
  6. Run repoctl status until it shows served: same for each target. Then dnf on the clients reads the metadata again.
  7. Build and publish the release package with the new key file at the next publish of each target.

Accepted outage from step 3 to step 6

dnf on the clients refuses the metadata and the RPMs that the key signed. The mirror job keeps the served tree. The team agrees to this outage, because the trust in the key must end first.

Lost key

  1. Run repoctl sign retire ID. It needs no secret key. Push the set commit.
  2. The human of the lost key makes a new key (help key) and onboards it (onboarding).
  3. With another active, deployed key, run repoctl repo resign --signer ID for each target. Then run repoctl sign remove ID and publish the new release package (offboarding and rotation).

Last deployed signer

sign retire refuses the last deployed signer (sign.last-signer). A key file record deploys a new key without a release package.

  1. The human makes a new key (help key) and runs repoctl sign add NEW --fingerprint FPR. Push the set commit.
  2. For a compromised key, run repoctl sign revoke ID now and push. For a lost key, skip this step.
  3. Run repoctl sign keyfile --checksum. Config management installs the key file with this pinned sum. It installs it on the HTTP server and on all clients of each target. For a compromised key, it also does the client commands of repoctl sign offboard ID.
  4. For each target, run repoctl sign deployed NEW --keyfile SHA256 --target ID and type the key id. Push the set commit.
  5. For a lost key, run repoctl sign retire ID now. Then continue with step 3 of Lost key, with NEW as the signer. For a compromised key, continue with step 4 of Compromise.
  6. Onboard a second key for each target (two deployed signers).

Stop conditions

StepStop when
Compromise item 3Config management cannot reach all clients or the HTTP server. Do not continue to the re-sign: tell the team which hosts still trust the key.
Compromise item 4A listed publish is not known, and no older snapshot is known. Stop all publishes and examine the registry.
Compromise item 5repo resign fails with verify.failed or verify.el-failed for a file of another key.
Last deployed signer item 4sign deployed refuses the sum (exit 12). The installed key file is not the committed key file.

Done when

  • repoctl sign ls shows the key as revoked, or as retiring or removed for a lost key.
  • For a compromised key, repoctl sign offboard ID lists no snapshot that is latest.
  • repoctl status shows served: same for each target, and repoctl repo verify --served exits with 0.
  • Each target has two active keys with a deployment record.
  • Doctor sign.release passes: the release package in latest has the new key file.
