Failed mirror job

This runbook is for a mirror job that does not serve latest. The job keeps the old tree when a step fails, so the clients keep working, but they do not get the new snapshot. The rules of the job are in Publish: mirror job.

  • The job never serves a tree that its keyring does not verify.
  • The journal of the job on the HTTP server names the failed step.
  • Each failure has a cause on the HTTP server, in the registry or in the snapshot.

Rules

  • A human with access to the HTTP server does the steps there. repoctl does not run on the HTTP server.
  • Do not change KEYRING by hand to make a snapshot pass. Config management installs it from the release package.
  • Do not write into the served tree. Only the job writes it.

The examples use the story: the publish p-20261103-1412-5e1 of el9 at 14:13, and the served path /srv/repos/slurm-repo/slurm-26.05/el9.

Trigger

  • repoctl status shows served: behind more than 15 minutes (three runs of the timer) after a publish.
  • repoctl status shows served: unknown: the file repoctl-snapshot.json is not at the URL.
  • The service unit of the job is in state failed on the HTTP server.

Find the failed step

  1. On the HTTP server, run systemctl status repoctl-mirror.service and journalctl -u repoctl-mirror.service --since -1h. The last error names the set, the target and the step.
  2. From an admin host, run repoctl repo verify --snapshot latest --el --target el9. Exit 0 means that the snapshot is good, and the cause is on the HTTP server.
  3. Find the cause in Causes. Fix it.
  4. Run the job once: systemctl start repoctl-mirror.service. Read the journal again.

Causes

Step of the jobErrorCause and fix
1 token and manifestcurl fails, or HTTP 401, 403, 404GHCR does not answer (runbook Registry outage or loss), the OCI package is private (an organization owner sets it to public), or the OCI package line in /etc/repoctl-mirror.conf is wrong.
2 blobsa sha256 does not matchA download broke. The job tries again at its next start. When it fails twice for the same blob, stop.
3 treeno space, or a link failsThe disk is full. Free space, or set a lower KEEP_TREES. The hard links need one file system for .objects/ and .trees/.
4 verifygpgv or rpmkeys fails for a keyThe key file on the HTTP server does not hold the signer. Config management did not install the release package with that key, or it removed a revoked key on purpose (key compromise). Compare sha256sum /etc/pki/rpm-gpg/RPM-GPG-KEY-slurm with repoctl sign keyfile --checksum. Install the release package of the deployment record. Do not change the keyring by hand.
4 verifya record does not have its sha256The snapshot has a bad supply chain record (records.mismatch). Stop.
5, 6 write and swappermission deniedThe system user of the job does not own the served path. Fix the owner of the directory.

A signer that is not in the key file of the HTTP server is the second guard behind gate 2 (gates). When the clients also miss the key, a signature of that key would break them. Thus the fix is a deployment of the key, never a change of the keyring.
