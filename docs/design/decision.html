Why a Go tool

This chapter gives the reasons for the design of repoctl. It starts from the bash scripts today, the real build graph and six problems, and scores six options against seven criteria. It then specifies the choice: its layers, Go packages, branches, name and license.

  • repoctl is one Go binary on GSI-HPC/go-clikit. It is the only part that builds, signs and publishes.
  • mock with the rpmautospec plugin stays the build isolation. repoctl calls git, mock, rpmsign, createrepo_c and modifyrepo_c as child processes.
  • The build graph is real but small: 11 packages, 14 edges, 4 levels. Dagger and BuildKit add a privileged second isolation layer for little gain.
  • Agent skills alone are not deterministic. A signed release must be repeatable. The agent does judgment work only.
  • A CLI, a local web UI and an MCP server share one core, one plan and one journal.
  • The tool lives on the branch main. Each set branch holds only the data of one set.

The bash scripts today

Each set/slurm-* branch (set/slurm-26.05, set/slurm-25.11, set/slurm-25.11-testing) has its own copy of the build scripts. They build one EL9 repository for one Slurm release.

  • scripts/checkout and scripts/pin manage one git worktree per package. packages.lock holds the pinned commits.
  • scripts/build calls build <dir> 11 times in a fixed order. Each call makes an SRPM, builds the RPMs in mock, signs them and runs createrepo --update on result/el9/.
  • Each build adds result/el9/slurm as an extra repository (mock --addrepo). Thus a package can use the packages of earlier builds.
  • scripts/common.sh and scripts/macros hold the set data (set data). scripts/list, scripts/rpmlist, scripts/setup, scripts/clean and scripts/update are helpers.
  • Two agent skills exist: package-info (with a bash script) and list-package-updates.

The CLI reference maps each script to its repoctl command (cli.html#migration).

Problems

#ProblemEffect
P1The build order is written by hand, and a hand order can be wrong. On the 25.11 branches, scripts/build builds munge after the pmix packages. They need munge-devel.With an empty result/, pmix builds against the munge-devel of the distribution. A second run builds it against the munge of the set. The result depends on old state.

P3All builds run one after the other.Long wall time. The graph allows 4 parallel builds.

P6Each set/slurm-* branch has a copy of the scripts.A fix to the tooling must go to 3 branches.

mock in Dagger

  • mock needs root capabilities for its own chroot and mounts. In Dagger, this needs insecureRootCapabilities. The Dagger docs compare this to docker run --privileged.
  • The mock caches (root cache, dnf cache) must be Dagger cache volumes. Else each build downloads the buildroot again.
  • A git worktree has a .git file that points outside the directory. In a mounted worktree, git does not work and rpmautospec fails. A clone is necessary first.
  • The GPG key must go into the engine as a secret. Signing in a container is possible, but it adds a trust question.

The choice: a hybrid

repoctl is option E. The Go tool does all deterministic work: graph, plan, build, sign and publish. mock and rpmautospec stay as they are. Agent skills call repoctl. They never call mock, rpmsign or createrepo_c.

The agent does judgment work: version updates, release notes, the triage of a failed build and the question "is a rebuild necessary?". A human does every step that changes shared state (model.html#safety). The skills are in agents.html#skill-list.

ProblemAnswer of repoctl
P1 hand orderEach build sees the set packages through the staging repo of the run and the local copy of latest. Thus pmix always builds against the munge of the set: the new one in staging or the published one.
P2 full rebuildsOnly nodes with a new package commit build (model.html#identity).
P3 one build at a timeUp to --jobs N parallel mock builds, each with its own root.
P4 mixed repositoryA build writes only the staging of its run. A publish makes a new snapshot, and only the tag move changes what clients see (publish.html#order).
P5 free-text outputA live tree on a terminal, plain lines for CI, --json results and one journal per run (contract.html#journal).
P6 copies of the scriptsA fix to the tool is one commit on main and one release for all sets (where the tool lives).

Rule: imports go down

  • A surface imports the core, and the core imports the adapters. The core never imports a surface.
  • A core Go package starts no child process and connects to no remote service. It calls an adapter.
  • The core reaches each adapter through a Go interface. Thus a test can put a stub in its place.

Where the tool lives

The GitHub repository dennisklein/repoctl has three kinds of branches. They do not share history.

BranchHolds
main (default)The Go module of repoctl, the skills, the mirror job (contrib/mirror/), the source of this docs site (docs/) and the CI workflows.
set/<set>The data of one set: repoctl.yaml, repoctl.lock, macros, the in-tree release package, keys/, .repoctl/advisories.yaml and CLAUDE.md. No scripts (model.html#set).
<project>/<set>[-<variant>]One package: its spec and its full git history, which rpmautospec reads. Example: pmix/slurm-26.05-v4.

In the bash era, the set branches had the name builder/<set>. The name changed for two reasons: the branch builds nothing, and the builder of a build is the repoctl process (supply-chain.html#builder).

The name

The name is repoctl, in the pattern of clusterctl. The binary, the RPM and the Go module use this name. Fedora has no package with this name.

License

The license of repoctl is the Apache License 2.0 (SPDX Apache-2.0). It covers only the branch main: the Go code, the skills, the mirror job, the CI workflows, the site generator and this design record. The full text is in the file LICENSE at the top of the repository.

  • The fonts in docs/assets/fonts/ and the script in docs/assets/vendor/ keep their own licenses. Their license files are next to them.
  • The tool RPM and the release RPM repoctl-release have the tag License: Apache-2.0.
  • The license does not cover the set branches and the package branches. A spec file keeps the license that its author gives it. The RPMs that repoctl builds have the License tag of their spec.

Why Apache-2.0

The Go libraries of repoctl, for example oras-go, use permissive licenses. Apache-2.0 is permissive too and adds a patent grant. The code and the design record have one license. Thus a human can copy a rule, a schema or an example into the code without a second license.
