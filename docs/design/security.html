Security model

The assets, actors and trust boundaries of repoctl, and the rules that protect the set inputs, the GitHub branches and the agent sessions. Then the threats, the public fields and the residual risks. The key rules are in Signing and trust.

  • The clients trust only OpenPGP signatures. GHCR, the HTTP server and the network hold signed files, but they are not trusted.
  • The builder branch is the root of trust. It holds sign.keys, the public keys and the deployment records.
  • The admin host is the builder. One human builds, signs and publishes there, with a personal key on a YubiKey.
  • Each change of a set input needs a signature of an allowed key.
  • Each field that repoctl writes to GHCR, the served tree or the set repository is public.

Trust boundaries

A trust boundary is a line where data goes from one zone to another zone with a different trust. Each crossing has a check.

#CrossingCheck at the crossing
B1Admin host and GitHub: set commits and package commits, push and fetch.Signed set inputs. The lock pins each package commit. The rulesets block force pushes and deletions.
B2Upstream to the admin host: source archives and buildroot RPMs.mock checks the signatures of the Rocky and EPEL RPMs. The lock pins each package commit, and a human reviews each version bump. The provenance records the digest of each source and buildroot RPM (supply-chain.html#provenance).
B3Admin host to GHCR: the push of a snapshot and the tag.The GHCR token. GHCR is storage only: nothing in it is trusted without its OpenPGP signature.
B4GHCR to the HTTP server: the pull of the mirror job.The mirror job verifies each repomd.xml.asc and each RPM with the key file that config management installed (publish.html#mirror).
B5HTTP server to the clients: dnf over HTTPS.repo_gpgcheck=1 and gpgcheck=1: dnf checks repomd.xml.asc, and rpm checks each RPM with the client keyrings (signing.html#chain).
B6Config management to the clients and the HTTP server: the release package and the key removal.Outside repoctl. A human confirms the result with a deployment record (signing.html#deployment-record).
B7Agent session to the admin host: tool calls.The tool list of the skill, the MCP server without shared-state tools, the deny list and the guard hook (agents.html#deny).

Signed set inputs

A set input is a file of the builder branch that decides what a publish builds or which keys the clients trust. The set inputs are repoctl.yaml, repoctl.lock, each targets[].macros file, each in-tree package path and keys/. Each human with push access to the set repository can change them, and git does not authenticate the author of a commit.

Rule: signed set inputs

Each commit that changes a set input must have a valid signature of an allowed key. Publish checks this in step 1, before the first signature. A commit that fails stops the publish with sign.trust-unverified (exit 12).

  • The commits. For each selected target, publish reads the set commit of the base, the annotation io.repoctl.set-commit (publish.html#format). It checks each commit that git log BASE..SET -- INPUTS lists. SET is the set commit of the publish, and INPUTS are the set inputs of SET. When a target has no base, or the set commit of the base is not an ancestor of SET, the range is all of SET.
  • The check. repoctl runs git verify-commit --raw with a temporary GnuPG home. The home holds the keys/ID.asc files of the first parent, plus the added keys of the commit. repoctl compares the full fingerprint of the line VALIDSIG with sign.keys.
  • The deployment records. In each checked commit, each new entry of keys/deployed.yaml has confirmedBy equal to the key id of the signer of that commit. confirmedBy is not the key of the entry, unless no other key was active in the first parent. Else the result is also sign.trust-unverified.
CommitAllowed keys
Each commitA key that is active in sign.keys of the first parent of the commit.
A commit that only adds keys: new entries in state active, their keys/ID.asc and the files of release writeAlso one of the keys that the commit adds. Thus a new admin signs the commit "Trust key ID FPR" with the new key.

In the story, A. Admin signs the commit 7e21d0a "Trust key a.admin C2F9…52A7" with the new key a.admin. d.klein signs the deployment record of a.admin. In September, d.klein confirmed his own records: hpc-repo was retiring, so no other key was active.

Signatures on set commits

  • repoctl signs each set commit that it makes with the key of sign.key (git commit -S<FPR>).
  • sign add, sign retire, sign remove and sign deployed do not commit without the secret key of sign.key (sign.no-key, exit 9).
  • A human who commits a set input with git must sign the commit too.
  • The doctor check git.signing warns when git in the set directory does not sign commits with the key of sign.key (commit.gpgsign and user.signingkey).

Review commit

A commit that fails the rule stays in the history of the builder branch. Each publish stops at it until an admin reviews it:

  1. Read the change with git show.
  2. If the change is wrong, revert it with a signed commit.
  3. In both cases, make a review commit: an empty commit with a valid signature of an allowed key.
  4. Give the review commit one trailer Trust-Reviewed: SHA for each commit that it covers.

Publish does not stop at a failed commit when a review commit in the range covers its full sha. The hint of sign.trust-unverified gives the command. A variant, not the story: a lock commit from a host without a key.

$ repoctl publish --target el9 --dry-run
repoctl: error: set commit 3c5d9e1 changes repoctl.lock and has no valid signature of an allowed key
hint: review the change. run: git show 3c5d9e1
hint: then sign a review commit. run: git commit --allow-empty -S4E7A0C93B85D21F69A0E3C47D1B266F041D80B6E -m "Review set inputs of 3c5d9e1" --trailer "Trust-Reviewed: 3c5d9e1f…"

Trust records on the remote branch

Two admins can push to the builder branch at the same time. lock.unpushed checks only that the set commit is on the remote branch. Thus a publish from an older set commit could use old key states, for example after another admin pushed a retire.

Rule: newest trust records

After the fetch of step 1, publish compares repoctl.yaml and keys/ of the set commit with the tip of the remote branch. The command is git diff --quiet SET origin/builder/SET -- repoctl.yaml keys/. A difference stops the publish with sign.trust-behind (exit 13). The hint is git pull --ff-only, then publish again.

Thus gates 1 and 2 and the trust block read the newest key states and deployment records, and all admins see the same record. A change of repoctl.yaml outside sign, for example a new package, also stops the publish. This is on purpose: the rule stays one file comparison.

GitHub rulesets

An organization owner sets three rulesets on the set repository (decision.html#home). A ruleset also stops a human with a stolen login and push access.

RulesetTarget branchesRulesWhy
mainmainRequire a pull request with one approval of another team member. Dismiss stale approvals on a new push. Require the status checks of the CI workflows. Restrict deletions. Block force pushes.main holds the tool, the skills and the mirror job script (A9). A change there runs on each admin host and on the HTTP server after the next release.
setsbuilder/*Restrict deletions. Block force pushes.The snapshots name their set commits (io.repoctl.set-commit). A rewrite removes these commits, the history of the trust records and the commits that a review commit covers.
packagesall branches except main and builder/*Restrict deletions. Block force pushes.The lock pins each package commit. A rewrite removes a pinned commit, and an old lock cannot build again.

The bypass list of each ruleset is empty. An organization owner can change a ruleset, and the audit log of the organization records the change.

Why no pull request and no GitHub signature rule on builder branches

The admins push set commits directly: lock commits, deployment records and key changes. A required pull request would put each lock commit through a review, because GitHub cannot require a review only for some paths. Two other checks cover the trust changes: the signed set inputs, and the trust block, which the human who publishes a new key file answers.

The GitHub rule "Require signed commits" is not used either. It verifies with the keys of the GitHub accounts, not with keys/. It also refuses the unsigned lock commits of a host that only builds.

The doctor check git.protection reads the rules of the set branch, of main and of the package branches of the lock. It uses the GitHub REST API (GET /repos/OWNER/REPO/rules/branches/BRANCH), with OWNER and REPO from the URL of the remote. It warns in these cases:

  • a branch without the rules "restrict deletions" and "block force pushes";
  • main without a required pull request;
  • a remote outside GitHub, or a failed request. The warning gives the reason.

Rule: no secret in a public field

repoctl writes only the fields of this table to GHCR, to the served tree and to the set repository. A free text (--reason, --note) is public. The help of each such flag says so. The journals, the logs, the staging, the user config and the credential store stay on the admin host.
