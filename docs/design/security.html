Security model

This chapter specifies the security model of repoctl. It names the assets, the actors and the trust boundaries. It gives the rules that protect the set inputs, the GitHub branches and the agent sessions. It ends with the threats, the public fields and the residual risks. The chapter on signing gives the key rules (Signing and trust).

  • The clients trust only OpenPGP signatures. GHCR, the HTTP server and the network hold signed files, but they are not trusted.
  • The builder branch is the root of trust. It holds sign.keys, the public keys and the deployment records.
  • The admin host is the builder. One human builds, signs and publishes there, with a personal key on a YubiKey.

Signed set inputs

A set input is a file of the builder branch that decides what a publish builds or which keys the clients trust: repoctl.yaml, repoctl.lock, each targets[].macros file, each in-tree package path and keys/. Each human with push access to the set repository can change them. git does not authenticate the author of a commit. Thus publish checks the OpenPGP signature of each change.

Rule: signed set inputs

Each commit that changes a set input must have a valid signature of an allowed key. Publish checks this in step 1, before the first signature. A commit that fails stops the publish with sign.trust-unverified (exit 12).

  • The commits. For each selected target, publish reads the set commit of the base, the annotation io.repoctl.set-commit (publish.html#format). It checks each commit that git log BASE..SET -- INPUTS lists. SET is the set commit of the publish. INPUTS are the set inputs of SET. When a target has no base, or the set commit of the base is not an ancestor of SET, the range is all of SET.
  • The allowed keys. A key that is active in sign.keys of the first parent of the commit. Two more cases allow one of the keys that the commit adds: a commit that only adds keys (new entries in state active, their keys/ID.asc and the files of release write), and a commit whose first parent has no sign.keys. Thus a new admin signs the commit "Trust key ID FPR" with the new key.
  • The check. repoctl runs git verify-commit --raw with a temporary GnuPG home. The home holds the keys/ID.asc files of the first parent, plus the added keys of the commit. The line VALIDSIG gives the full fingerprint, and repoctl compares it with sign.keys.
  • The deployment records. In each checked commit, each new entry of keys/deployed.yaml has confirmedBy equal to the key id of the signer of that commit. confirmedBy is not the key of the entry, unless no other key was active in the first parent. Else the result is also sign.trust-unverified.

repoctl signs each set commit that it makes with the key of sign.key (git commit -S<FPR>). The sign commands sign add, sign retire, sign remove and sign deployed do not commit without the secret key of sign.key (sign.no-key, exit 9). A human who commits a set input with git must sign the commit too. The doctor check git.signing warns when git in the set directory does not sign commits with the key of sign.key (commit.gpgsign and user.signingkey).

In the story, A. Admin signs the commit 7e21d0a "Trust key a.admin C2F9…52A7" with the new key a.admin. d.klein signs the deployment record of a.admin. d.klein also confirmed his own records in September: hpc-repo was retiring, so no other key was active.

Review commit

A commit that fails the rule stays in the history of the builder branch. Each publish stops at it until an admin reviews it. The admin reads the change with git show. If the change is wrong, the admin reverts it with a signed commit. In both cases, the admin then makes a review commit: an empty commit with a valid signature of an allowed key and one trailer Trust-Reviewed: SHA for each commit that it covers. Publish does not stop at a failed commit when a review commit in the range covers its full sha. The hint of sign.trust-unverified gives the command. A variant, not the story: a lock commit from a host without a key.

$ repoctl publish --target el9 --dry-run
repoctl: error: set commit 3c5d9e1 changes repoctl.lock and has no valid signature of an allowed key
hint: review the change. run: git show 3c5d9e1
hint: then sign a review commit. run: git commit --allow-empty -S4E7A0C93B85D21F69A0E3C47D1B266F041D80B6E -m "Review set inputs of 3c5d9e1" --trailer "Trust-Reviewed: 3c5d9e1f…"

Trust records on the remote branch

Two admins can push to the builder branch at the same time. lock.unpushed checks only that the set commit is on the remote branch. Thus a publish from an older set commit could use old key states, for example after another admin pushed a retire.

Rule: newest trust records

After the fetch of step 1, publish compares repoctl.yaml and keys/ of the set commit with the tip of the remote branch: git diff --quiet SET origin/builder/SET -- repoctl.yaml keys/. A difference stops the publish with sign.trust-behind (exit 13). The hint is git pull --ff-only, then publish again.

Thus gates 1 and 2 and the trust block read the newest key states and deployment records. All admins see the same record. A change of repoctl.yaml outside sign, for example a new package, also stops the publish. This is on purpose: the rule stays one file comparison.

GitHub rulesets

The set repository holds the tool on main, each set on builder/<set> and each package on its package branch (decision.html#home). An organization owner sets three rulesets on it. A ruleset also stops a human with a stolen login and push access.

RulesetTarget branchesRulesWhy
mainmainRequire a pull request with one approval of another team member. Dismiss stale approvals on a new push. Require the status checks of the CI workflows. Restrict deletions. Block force pushes.main holds the tool, the skills and the mirror job script (A9). A change there runs on each admin host and on the HTTP server after the next release.
setsbuilder/*Restrict deletions. Block force pushes.The snapshots name their set commits (io.repoctl.set-commit). A rewrite removes these commits, the history of the trust records and the commits that a review commit covers.
packagesall branches except main and builder/*Restrict deletions. Block force pushes.The lock pins each package commit. A rewrite removes a pinned commit, and an old lock cannot build again.

The bypass list of each ruleset is empty. An organization owner can change a ruleset, and the audit log of the organization records the change.

Why no pull request on builder branches

The admins push set commits directly: lock commits, deployment records and key changes. A required pull request would put each lock commit through a review. GitHub cannot require a review only for some paths of a branch. The design checks trust changes in two other ways: each change of a set input has a signature (signed set inputs), and the human who publishes a new key file answers the trust block. The rule "Require signed commits" of GitHub is not used either. It verifies with the keys of the GitHub accounts, not with keys/, and it also refuses the unsigned lock commits of a host that only builds.

repoctl doctor reads the rules of the set branch, of main and of the package branches of the lock with the GitHub REST API (GET /repos/OWNER/REPO/rules/branches/BRANCH). OWNER and REPO come from the URL of the remote. The check git.protection warns for each branch without the rules "restrict deletions" and "block force pushes", and for main without a required pull request. A remote outside GitHub, or a failed request, gives a warning with the reason.
