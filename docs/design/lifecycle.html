Sets and packages

This chapter specifies the life of a package in a set and the start of a new set. It gives the package states, the ordered steps for each package change and the text of the help topics new-set and packages.

  • A package has a lock state (repoctl.yaml, repoctl.lock and the worktree) and a publish state (staging and latest of each target).
  • Two lock states mark a gap between the files: unpinned (no lock entry) and orphaned (no repoctl.yaml entry).
  • A new set forks each branch from the previous set at its lock commit. The rpmautospec history and the changelogs continue.
  • checkout --create needs one start point and checks the remote first. repoctl never pushes.
  • Each package change is a list of ordered steps. Each step names the repository of its commit and the plan reason to expect.
  • Old package versions stay in the repo. Removal is explicit: repoctl repo prune --package NAME --all.

Package states

A package has two kinds of state. The lock state compares repoctl.yaml, repoctl.lock and the worktree in packages/DIR. The publish state compares the set with the staging of the runs and with latest of each target. repoctl computes both states each time. It stores neither of them.

The plan actions and plan reasons are in Build. The RepoManifest in latest says which commit gives a published NVR (Core model). A source package name is retired on a target when no dir in repoctl.yaml builds it for that target. Latest of the target still holds its RPMs.

Lock states

For each package, repoctl compares the commit in repoctl.lock with the worktree. The contract enum LockState has nine values. repoctl status lists each package that is not in-sync or in-tree and prints the hint of the first problem (terminal frame).

StateMeaningstatus hint (run:)
in-syncThe worktree HEAD is the lock commit. No tracked file has a change.none
in-treeAn in-tree package (path:) with no change under its path. It has no lock line and no worktree. Its commit is the last set commit that changes its path.none
aheadThe worktree HEAD is a descendant of the lock commit. A commit is not pinned yet.repoctl pin DIR
behindThe worktree HEAD is an ancestor of the lock commit, for example after a colleague pinned a newer commit.repoctl checkout DIR
divergedThe worktree and the lock commit both have commits that the other does not have.rebase packages/DIR on the lock commit, then repoctl pin DIR
dirtyA tracked file has an uncommitted change. For an in-tree package (path:), a file under its path has a change.commit in packages/DIR, then repoctl pin DIR
missingThe package has no worktree.repoctl checkout DIR
unpinnedThe package is in repoctl.yaml. It has no entry in repoctl.lock.repoctl pin DIR
orphanedThe package is in repoctl.lock. It is not in repoctl.yaml.repoctl pin --orphans (removes it)

"The lock is dirty": a selected package is not in-sync or in-tree, or repoctl.lock has uncommitted changes. The file format is in Configuration.

Rule

  • LockEntry.commit is required, except for state unpinned.
  • plan shows an unpinned node with the note "not pinned" and the action skip. With --from worktree, the action is build.
  • build --from lock with a selected unpinned node stops with exit 5, lock.missing-package, hint repoctl pin DIR. publish stops with the same code when a selected target has an unpinned package (checks before the first signature).
  • checkout without --create makes the worktree of an unpinned package on its local branch at the tip of the remote branch (local branch) and prints "not pinned: run repoctl pin DIR". This is how a human checks out the new package of a colleague.
  • pin without arguments removes orphaned entries and lists them (command block). pin DIR for a dir that is not in repoctl.yaml is a usage error.
  • pin writes a line only for a worktree that is ahead, or for an unpinned package. It keeps the line of a behind or missing worktree and stops at a diverged or dirty one. Thus a pin after a git pull never takes back the newer pin of a colleague.
  • publish refuses a set with an orphaned entry: exit 5, lock.orphaned. The lock and repoctl.yaml must agree, so that the set commit fixes the output (checks before the first signature).

New set

A new set forks each package branch from the previous set. Thus the rpmautospec history and the changelogs continue. The builder branch also forks from the previous builder branch. The example starts set slurm-26.11 from slurm-26.05.

repoctl init --from

repoctl init --from SET --name NAME forks the set config (command block). SET is a set directory or a builder branch, for example builder/slurm-26.05. init reads its repoctl.yaml and writes a new one in the start directory:

  • name becomes NAME.
  • In each branch, repoctl replaces the old set name with the new one: pmix/slurm-26.05-v4 becomes pmix/slurm-26.11-v4. This is also true for an external package (slurm-26.05 becomes slurm-26.11).
  • A branch that does not contain the old set name stays the same. init lists it as "shared branch". Example: slurm-25.11 uses pmix/slurm-26.05-v4.
  • The other keys stay the same: targets, repo, store, upstream, notes, roles. The human sets repo.url for the clients of the new set (help step 3).
  • When the start directory is a fork of SET (its repoctl.yaml has the old set name), init changes the file in place without --force. Otherwise init also copies the files that repoctl.yaml names: the macro files and the release package path.
  • init does not copy repoctl.lock or .repoctl/advisories.yaml. The new set has new branches and new advisories.
  • init does not create branches. checkout --create does that.

init ends with a Next list. With --from, the list is repoctl help new-set from step 3. Without --from, the list is the steps of repoctl help packages for the first package (help topics).

repoctl checkout --create

repoctl checkout [DIR...] --create makes the branch and the worktree of each package whose branch does not exist (command block). It needs exactly one start point:

FlagStart point of the new branch
--from-set SETFor each DIR: the commit of the same dir in the repoctl.lock of SET. This is the published state, not the branch tip. A dir that is not in SET fails with branch.start-missing.
--from REFAny git revision, for example pmix/slurm-26.05 or a commit. For one DIR, or for a second stream such as pmix_v4.
--from fedora[:BRANCH]The dist-git history of upstream.fedora on src.fedoraproject.org, branch rawhide by default. repoctl fetches it into a temporary ref. The new branch keeps the Fedora layout: spec, patches and sources file (sources).
--orphanA new branch without history. Only on request.
  • Without a start point: exit 2, "say --from-set, --from, --from fedora or --orphan".
  • Before it creates a branch, repoctl runs git ls-remote on the remote of the package. When the branch exists there, repoctl does not create it: exit 1, branch.exists-remote, hint repoctl checkout DIR.
  • For an external package, the server repository must exist. When ls-remote fails: exit 1, git.unreachable, hint "create the project on the git server first".
  • The output gives the start point of each branch: "forked from pmix/slurm-26.05 at 6644bdf" or "orphan".
  • repoctl makes the new branch as a local branch at the start point and attaches the worktree to it (local branch). A commit in packages/DIR goes to that branch.
  • repoctl does not push. The output ends with one push command for all new branches, then repoctl pin.

Change a spec or bump a version

This is the most frequent change. Example: ucx 1.22.0 to 1.22.1 in the story (story run).

  1. Run repoctl status. The worktree of DIR must be in-sync on its local branch. If not, run repoctl checkout DIR first.
  2. Change the spec in packages/DIR, for example Version. Do not change Release: %autorelease computes it.
  3. Run git -C packages/DIR commit -am "Bump to VERSION". Repository: the package branch. Optional: try the commit with repoctl build DIR --from worktree. That run is unpinned and never publishable.
  4. Run git -C packages/DIR push origin BRANCH.
  5. Run repoctl pin DIR.
  6. Run git add repoctl.lock && git commit && git push. Repository: the builder branch.
  7. Run repoctl plan. Expect: DIR has the reason commit-changed on each of its targets.
  8. Run repoctl build. Read the soname result of each node of DIR (soname check). "sonames unchanged" means that no dependent needs a rebuild. An advisory soname.removed names the dependents: follow the recovery path.
  9. Run repoctl publish.
  10. Run repoctl status. Expect: "served same" after the next run of the mirror job (mirror job).

Add a package in this repository

  1. Add the entry to repoctl.yaml: dir, branch, upstream. The package is now unpinned.
  2. Run repoctl checkout --create DIR --from fedora (or --orphan).
  3. Write or change the spec in packages/DIR. Commit there. Repository: the package branch.
  4. Run git -C packages/DIR push origin BRANCH.
  5. Run repoctl pin DIR.
  6. Run git add repoctl.yaml repoctl.lock && git commit && git push. Repository: the builder branch.
  7. Run repoctl plan. Expect: DIR has the reason new-package on each of its targets. When DIR provides a BuildRequires of a current node, the advisory provider.changed names the dependents (codes).
  8. Follow the advisory: repoctl rebuild DEPENDENTS --reason "build against DIR", then pin, commit and push. Or dismiss it with a note (dismissals).
  9. Run repoctl build, then repoctl publish.

Add an external package

An external package has git: {url: …} in its entry, for example rocm-smi on https://git.gsi.de/SDE/packages/rocm-smi.git. The steps are the steps of Add a package, with these changes:

  1. Create the project on the git server first. repoctl cannot do this.
  2. Add the entry with git: {url: URL}, branch and upstream.
  3. Run repoctl checkout --create DIR --from fedora (or --orphan). The worktree comes from the bare clone of the URL (external package clones).
  4. Commit the spec in packages/DIR. Repository: the package branch on the external server.
  5. Run git -C packages/DIR push origin BRANCH. The push goes to the external server.
  6. Continue with step 5 of Add a package. Expect: new-package.

Add a second stream

Example: pmix_v4 next to pmix. The second stream forks from the history of the first stream.

  1. Add the entry, for example dir: pmix_v4, branch: pmix/slurm-26.05-v4, upstream: {github: openpmix/openpmix, tags: '^v4'}.
  2. Run repoctl checkout --create pmix_v4 --from pmix/slurm-26.05.
  3. Change the spec: rename the package. Its Provides must not conflict with the Provides of the first stream. Commit in packages/pmix_v4. Repository: the package branch.
  4. Continue with step 4 of Add a package. Expect: new-package.

Build a package for some targets only

  1. Add targets: [el9] to the entry. Commit and push. Repository: the builder branch.
  2. Run repoctl plan. Expect: the nodes on the other targets show "removed from the set". A dependent on another target gets dep.not-for-target (warn, graph per target).
  3. The published RPMs of the package on the other targets stay. The package is retired on those targets. To remove them, follow Retire a package from step 5.

Example: rocm-smi is built for el9 only. slurm@el10 requires rocm-smi-devel, so the plan warns before the build.

Retire a package

  1. Delete the entry from repoctl.yaml.
  2. Run repoctl pin --orphans. It removes the orphaned lock entry and changes no other line.
  3. Run git commit -am "feat!: remove DIR from the set" && git push. Repository: the builder branch.
  4. Run repoctl plan. Expect: no node for DIR. The advisory retired.published/NAME (info) gives the RPMs that stay published.
  5. The RPMs stay in the repo by default. Clients that installed them keep them.
  6. Optional, explicit: run repoctl repo prune --target T --package NAME --all. This is a dry run. Read it. Then run it again with --apply. The prune makes a new snapshot and records the removed NVRs in removed[] (prune, command block).
  7. Optional, on the clients: remove the package through config management, or add Obsoletes to the release package.
  8. Run git worktree remove packages/DIR. Keep the package branch. It holds the history of the published NVRs.

Rule: repo prune --package NAME --all

  • NAME is a source package name. It must be retired on the target. Otherwise: exit 1, prune.not-retired. The rule "never delete the newest NVR of a package" stays for the kept packages.
  • The prune must add no broken requirement compared with the base (prune). When a kept package requires NAME, the prune stops with prune.unsafe and names that package.
  • A retired package is not in any closure of the publish gate. It never blocks a publish, and repoctl never suggests a rebuild for it.

publish never removes a file. Thus the publish summary has no "removed" count. It shows "retired: N packages still published". repo diff between two snapshots still marks a removed file with -.

Rename

Rename a dir, for example rocm-smi to rocm-smi-lib. Nothing builds.

  1. Change dir in repoctl.yaml. Run git worktree move packages/rocm-smi packages/rocm-smi-lib.
  2. Run repoctl pin. Commit and push. Repository: the builder branch.
  3. Run repoctl plan. Expect: current with the note "dir renamed from rocm-smi". plan matches manifest entries by commit, target and source package name, not by dir, branch or URL (match key).

Rename the RPM (Name in the spec). The new name builds.

  1. Change Name and add Obsoletes and Provides for the old name. Commit. Repository: the package branch.
  2. Push, pin, commit and push. Repository: the builder branch.
  3. Run repoctl plan. Expect: commit-changed. The old source package name is retired (Retire a package).

Rename the branch. The commit stays the same, so nothing builds.

  1. Rename the local branch: git -C packages/DIR branch -m OLD NEW. Push it: git -C packages/DIR push origin NEW. Change branch in repoctl.yaml.
  2. Run repoctl pin. The worktree is in-sync, so pin writes only the new branch into the line. Commit and push. Repository: the builder branch.
  3. Run repoctl plan. Expect: current.

Move a package to another source

A package has one of three sources: a path in the set tree (in-tree), a branch in the set repository, or a branch on an external server. rpmautospec computes the release from the history, so a move keeps the history. The plan result depends on the commits (match key):

Rule

  • A move that keeps the commits keeps each node current.
  • A move that makes new commits with the same history gives the same NVR from a new commit. publish refuses it with nvr.reused. Thus such a move ends with repoctl rebuild, which raises the release.

Move an in-tree package to a branch. The release package stays in-tree (release package).

  1. In the set directory, run git subtree split --prefix packages/DIR -b BRANCH. The new branch holds each commit that changes the path, with new commit ids. Run git push origin BRANCH.
  2. Run git rm -r packages/DIR. In the entry, replace path: with branch: BRANCH. The package is now unpinned.
  3. Run repoctl checkout DIR. The worktree starts on the local branch at the tip of origin/BRANCH.
  4. Run repoctl pin DIR. Then run repoctl rebuild DIR --reason "move to branch BRANCH".
  5. Run git -C packages/DIR push origin BRANCH. Then run git commit -am "refactor: move DIR to branch BRANCH" && git push. Repository: the builder branch.
  6. Run repoctl plan. Expect: build with the reason rebuild on each target of DIR.

Move a package from the set repository to an external server:

  1. Create the project on the git server. repoctl cannot do this.
  2. Push the history: git -C packages/DIR push URL BRANCH. The commits stay the same.
  3. Run git worktree remove packages/DIR. Add git: {url: URL} to the entry.
  4. Run repoctl checkout DIR. The worktree now comes from the bare clone of URL (external package clones).
  5. Run repoctl pin DIR. The worktree is in-sync, so pin writes only the URL into the line. Commit and push. Repository: the builder branch.
  6. Run repoctl plan. Expect: current.
  7. Keep the old branch in the set repository, or delete it. The external server holds the same commits.

A move from an external server to the set repository uses the same steps in the other direction: push the branch to origin, remove git.url, then checkout and pin. Expect: current. This release has no steps for a move from a branch into the set tree.

Add or drop a target

Add a target, for example el10:

  1. Add the entry to targets. Commit and push. Repository: the builder branch.
  2. Run repoctl plan. Expect: each node of the target has the reason new-target.
  3. Run repoctl build and repoctl publish. The first publish makes the first snapshot of the target. No client uses the target yet, so gate 2 does not apply (gates). Example: el10 has no import; its first snapshot is p-20260912-1403-c21.
  4. Add the target to the mirror job (mirror job).

Drop a target:

  1. Delete the entry. Commit and push. Repository: the builder branch.
  2. Run repoctl status. Expect: "target ID: not in repoctl.yaml, still published". The published repo, its GHCR package and the served tree stay.
  3. To stop serving the target, remove it from the mirror job.

Rebuild the set

Rebuild the whole set when its build roots change for all packages, for example at a minor release of the distribution (Rocky 9.8) or after a change of the macro files. The advisory mock.drift says when the mock config or the macros of this host differ from the manifest. Each host computes it from its own mock config, so do the steps on the host that builds the set.

  1. Run repoctl mock update. The roots of each target get the new packages of the distribution.
  2. Run repoctl rebuild '*' --reason "Rocky 9.8" --dry-run. Expect: one new NVR per package. The glob leaves out each in-tree package with the warning rebuild.in-tree.
  3. Run the same command without --dry-run. repoctl makes one empty commit per package branch and pins it. Repository: each package branch.
  4. Push each package branch with the Next lines of the command.
  5. Run git add repoctl.lock && git commit && git push. Repository: the builder branch.
  6. To build an in-tree package again too, change a file below its path, for example its changelog, and commit it to the builder branch.
  7. Run repoctl plan. Expect: each node has the reason rebuild on each of its targets.
  8. Run repoctl build, then repoctl publish.

The commit is per package, so a rebuild applies to all targets of the package. A rebuild for a minor release of el9 also builds the el10 nodes again, each with a new NVR. To build one target only, use repoctl build --force @el9 for a test. A forced build of a current node is never staged, so it is never published (forced builds).

External package clones

A package with git.url (in its entry or in defaults.git) lives on another git server. rpmautospec needs the full history, so repoctl keeps one bare clone per URL (external package repos).

  • The clone is $XDG_DATA_HOME/repoctl/git/HASH.git (HASH: the first 10 hex digits of the sha256 of the normalized URL). checkout fetches it and makes the worktree from it. The lock stores the URL, the branch and the commit. The clone can hold commits that are not pushed, so it is data and not cache (XDG directories). Thus the whole cache is safe to delete.
  • Before the hash, repoctl normalizes the URL: lower-case scheme and host, no trailing /, no trailing .git. An scp-like URL USER@HOST:PATH becomes ssh://USER@HOST/PATH. Thus two spellings of one URL give one clone. The lock and the clone keep the URL as repoctl.yaml gives it.
  • All sets of the user on the host share the clone. A set lock protects one set only. Thus each command that fetches into the clone, adds or removes one of its worktrees, or deletes it also takes the clone lock $XDG_RUNTIME_DIR/repoctl/git-HASH.lock, for that git step only. A second command waits for it up to --lock-wait, and at least 60 s. Then it stops with exit 7 and git.busy.
  • repoctl makes it with git clone --bare URL and the fetch refspec +refs/heads/*:refs/remotes/origin/*. It does not set remote.origin.mirror. Thus git -C packages/DIR push origin BRANCH works as in a normal clone.
  • The local branches of the clone are its refs/heads/*. git clone --bare copies each remote branch there one time, and the refspec does not update them. checkout uses them as in the set repository: it creates BRANCH at the lock commit, or fast-forwards a stale copy to it (local branch).
  • repoctl clean does not touch $XDG_DATA_HOME/repoctl/git. repoctl clean --git first runs git worktree prune in the clone, so that the record of a deleted worktree does not keep it. Then it deletes a clone only when it has no worktree and no commit that is not on the remote. Otherwise it lists the clone and keeps it (git.mirror-unpushed).
  • repoctl doctor warns about an external clone with commits that are not pushed. It also checks that each external URL is reachable.
  • The pin warning "not on origin" and the rebuild banner print the push command for the package.
  • Credentials come from the git and ssh setup of the user. The config never holds them.

Adopted manifest entries

The import runbook writes RepoManifest entries for the RPMs that the bash-era scripts built. These entries use the RepoManifest format (Core model) with these values:

FieldValue
reasonadopted when a commit of the branch gives the NVR. adopted-unmapped when no commit gives it.
commitThe commit, or null for adopted-unmapped.
dirThe dir that builds the name, or null when no dir in repoctl.yaml builds it (a retired name).
mockConfig, macros, buildroot, buildrootFile, runnull. The bash-era scripts did not record them.
provides, requiresFrom the RPM headers.
recordsprovenance is null: the build facts are lost. repo push --from writes the SBOM of each adopted build from the RPM headers and the SRPM (supply-chain.html#layout).
builtBUILDTIME of the SRPM, in UTC.
publishThe import publish id p-import-YYYYMMDD, for example p-import-20260828.
signerThe full fingerprint of the key of the RPM signature, for example the fingerprint of hpc-repo.

plan reads an adopted entry as any other entry. When the pinned commit is in it, the node is current. An adopted-unmapped entry never makes a node current. It counts for the closure checks and for prune.
