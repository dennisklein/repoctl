Signing and trust

This chapter specifies how repoctl signs a publish and how the clients trust a key. It gives the client facts, the options for team keys, the choice, the trust chain and the gates before the first signature. It also gives the release package and the life of a key from onboarding to offboarding.

  • Each admin signs with a personal key (OpenPGP v4, on a YubiKey or in a file). No key is shared.
  • Clients trust all team keys through one key file in the release package. Each RPM and each repomd.xml.asc has exactly one signature.
  • Gate 1: the signer is active and valid. Gate 2: a human confirmed the deployment of the key in keys/deployed.yaml. Gate 3: the key format.
  • A signer probe asks for the PIN at the start of a publish, not in the sign step.
  • Publish verifies each target in its EL mock chroot, with the EL rpm and dnf and only the keys that the clients have.
  • A normal publish never re-signs old RPMs. repoctl repo resign does it as its own publish.
  • Key states: active, retiring, removed. An expiring key is a key change, not a new expiry date.
  • A release package cannot remove a key from the clients. Config management does it, and repoctl prints the commands.

Client facts

The clients run Rocky 9: rpm 4.16.1.3 with OpenSSL, dnf 4.14, librepo with gpgme. Next come Rocky 10 clients: rpm 4.19.1.1 with rpm-sequoia, dnf 4.20, librepo with the librpmio back end. The versions come from the CentOS Stream c9s and c10s spec files. The design depends on these facts.

Options

Five options give a team its signing keys. The client facts decide between them.

A. One shared key, encrypted with sops

The team keeps the armored secret key in git as a sops file. sops encrypts a file to many recipients: age keys (also SSH keys and age plugins), PGP, cloud KMS and HashiCorp Vault transit. sops updatekeys or sops rotate adds or removes a human.

The decrypt path keeps the key off the disk. repoctl makes a private GnuPG home in $XDG_RUNTIME_DIR/repoctl/g-<run> (mode 0700, a per-user tmpfs under systemd-logind). It pipes sops decrypt into gpg --batch --import and signs with rpmsign --define "_gpg_path <dir>". At the end, also on an error or SIGINT, it runs gpgconf --kill gpg-agent and deletes the directory. The path must be short, because GnuPG fails when the socket path is too long. sops exec-file --no-fifo writes a temporary file to /tmp and is not usable.

  • Each member holds the full private key in clear text during each publish. A member can copy it.
  • When a member leaves, a new recipient list is not enough: removed key owners can still have the old data key. The team must make a new signing key and re-sign all packages. Then it must ship the new public key and remove the old key on each client (F12, F13, F16). This is the highest offboarding cost of all options.
  • A signature does not show who published.

B. Personal keys, no sharing

Each admin has a personal signing key, on a YubiKey (OpenPGP card) where possible. The set lists all trusted public keys. The release package ships all of them in one file. Each publish signs with the key of the human who runs it.

  • Clients: one trusted key verifies an RPM (F2) and a repomd.xml.asc with one signature (F8, F9). dnf imports all keys from the file without a question when it runs with -y (F1, F14).
  • The .repo file stays stable: one gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-slurm line, and all keys in that one file. The key file is not %config, so an update always replaces it (F18).
  • YubiKey: the PIN stays in the gpg-agent session. The touch policy of the signature slot is "cached" (15 s) or "off". With "on", each RPM needs one touch.
  • Algorithm: RSA 4096 is the safe default. The clients verify Ed25519 (F17); the test on EL9 is open.

Two rules follow from F12 and F13. Gate 2 and the offboarding order enforce them.

  1. Add a human before the first signature. A client reads a new key only from its installed release package. If a new key signs repomd.xml.asc first, the client cannot read the metadata, and it cannot get the new release package either. Thus an old key publishes the new release package, and config management deploys it. Only then can the new key sign.
  2. Remove a human in this order: re-sign, ship the new key file, remove the key on the clients. If the key goes first, packages with the old signature fail to install.

C. One primary key, personal signing subkeys

The primary key stays offline, for example on an encrypted USB stick in a safe. Each admin gets a signing subkey on a YubiKey. Clients see one key identity.

  • EL9 and EL10 verify the signatures of a signing subkey (F11).
  • Onboarding breaks clients. A new subkey changes the certificate, but rpm 4.16 and 4.19 ignore the import of a known primary key (F12). The dnf repository keyring also skips the known key ID (F13). Config management must erase the key and delete the repository keyring on each client, for each new admin.
  • Offboarding is not cheaper. A subkey revocation reaches a client only by the same erase and import.
  • A longer expiry of the primary key has the same problem on EL10, where rpm-sequoia does not trust an expired key (F6). The key hpc-repo expires on 2030-01-20.
  • gpg needs -u <subkey-fingerprint>! to use one exact subkey.

D. Several signatures on one artifact

  • RPM: EL9 rpm 4.16 keeps one signature (F3). An rpm 6 or EL10.1 signer can add v6 signatures with --rpmv6 (F4, F5). The client then needs each signer key, because NOKEY fails (F6). What EL9 does with the extra tag needs a test (F7).
  • repomd.xml.asc: EL9 accepts it when one signature is valid (F8). EL10 fails on the second packet (F9).

E. Central signer, no sharing

One key on one machine. Admins send signing requests to it. Clients see one key that does not change when the staff changes.

The choice: personal keys, many trusted keys, one signature per file

repoctl uses option B. Two different things have the name "many keys":

  • Many trusted keys on the clients: yes. The release package installs the public keys of all admins. dnf and rpm accept a file when its signer is one of these keys (F1, F2, F8, F14). Different RPMs in one repository can carry signatures of different admins.
  • Many signatures on one file: no. rpm 4.16 (EL9) keeps only one signature per RPM (F3). EL10 can store more, but then it needs all signer keys (F6). EL10 librepo refuses a repomd.xml.asc with more than one signature (F9).

What repoctl does:

  • Each admin makes an RSA 4096 key on a YubiKey, with the touch policy "cached". The key hpc-repo of the bash scripts (GSI HPC repo <hpc-repo@gsi.de>, …7C3A 19F2) stays trusted in state retiring until no RPM in latest carries it.
  • repoctl signs each new RPM with rpmsign --resign. It passes %_gpg_name (rpm 4) and %_openpgp_sign_id (rpm 6) as the full fingerprint. It never uses --addsign and never passes --rpmv6, so the result is the same on rpm 4.16, 4.19 and 6.
  • repoctl writes repomd.xml.asc with one gpg --detach-sign --armor -u <FPR>!. It has exactly one signature packet. repoctl doctor checks this (sign.repomd).
  • The signer host is always Fedora (rpm 6 with rpm-sequoia). The EL chroot check covers the client side (verify-el).
  • Fingerprints are always full (40 hex characters) in the config, the output, the logs and the snapshot annotations. Short key IDs are for display only.
  • repoctl has no sops back end. Config management removes keys on the clients, and repoctl prints the commands.
  • MCP never signs. The web UI signs only through repoctl publish, after the typed confirmation.

The set config says which keys the clients trust: sign.keys[] (id, file, fingerprint, state), sign.release.keyfile and sign.checks (key_expiry_warn: 180d, key_min_validity: 30d). The user config says which key this human signs with: sign.key, an id of sign.keys or a full fingerprint. sign.gpg_name and REPOCTL_GPG_NAME are aliases of sign.key and REPOCTL_SIGN_KEY. The keys are in config.html#set-config, config.html#user-config and config.html#env.

A client installs a package only when two checks pass: dnf checks repomd.xml.asc (repo_gpgcheck=1), and rpm checks the RPM signature (gpgcheck=1). Both use the keys that the client got from the release package.

Signer probe

Step 1 of a publish (publish order) runs a signer probe. The probe signs a random 32-byte value with gpg --detach-sign -u <FPR>! and verifies it. Thus gpg-agent asks for the PIN or passphrase at the start, and not in the middle of the sign step.

  • CLI: pinentry asks in the terminal or on the desktop. repoctl suspends the progress display for it.
  • Web UI: the UI is for the local user only, so pinentry shows on the local desktop. The browser never asks for a PIN. Step 1 of the publish page shows the probe state: card missing, waiting for the PIN on the desktop, touch your key, ready. When a signature takes more than 1 s, the UI shows "touch your key" over SSE (ui-publish.html#progress).
  • If the probe fails or the human cancels pinentry: sign.locked, exit 9. The hint gives gpg --card-status.

The preflight of publish also checks rpmsign, createrepo_c, gpg, the secret key of sign.key and a usable pinentry. A missing card gives sign.card-absent, a missing pinentry gives sign.no-pinentry (both exit 9). A failure in the sign step gives sign.failed. The full table is contract.html#problems.

Rule: first publish

Gate 2 does not apply when the registry has no snapshot of the target and the publish is not an import. No client uses such a target yet. The summary then says "first publish of el10: no clients yet; the signer must be in the key file of this release". A key that a publish adds can never sign that publish.

Gate 2 reads only the committed record. The record is in the pushed set commit (publish.html#checks), so all admins see the same record.

Why a human confirms

Config management gives no feedback to repoctl. A published release package does not prove that the clients have it. If a key signs before the clients have it, dnf on the clients cannot read the metadata. Thus a human checks the clients and confirms the deployment.

Deployment record

repoctl sign deployed ID --release NVR --target ID records that config management installed the release NVR on all clients of the target. The record is per target. repoctl checks that the release is in latest of each selected target and that its key file holds the key. For an import, --path DIR names the tree instead of latest. Then it asks the human to type the key id, writes keys/deployed.yaml and makes a set commit. The human pushes it.

The command needs a terminal or the UI dialog "Confirm deployment" (ui-publish.html#signing). It has no unattended mode and no MCP tool. Command: sign deployed.

The file also holds the entries of the other keys. d.klein has slurm-release-26.05-2 for el9 (confirmed by d.klein on 2026-09-10) and for el10 (2026-09-15). hpc-repo has slurm-release-26.05-1 for el9 only, confirmed by d.klein on 2026-08-28 with the import; el10 had no clients then. a.admin gets the el10 record only after slurm-release-26.05-3 is in latest of el10, and that publish waits for the fix of slurm@el10.

A key is deployed for a command when gate 2 passes for each target in scope that has a latest. The scope is the selected targets of a publish, or the targets of the command. Thus repoctl sign ls shows hpc-repo as not deployed: el10 has a latest, and hpc-repo has no el10 record. hpc-repo signs nothing new, because it is retiring.

When the release package of a publish has a new key file, the summary shows the trust block. No second admin reviews the change. The block is for the human who publishes, and it needs a typed answer even with --yes. The story publish of slurm-release-26.05-3 by d.klein:

Verify in the EL chroot

repoctl runs on Fedora, with rpm 6 and rpm-sequoia. The clients use EL9 rpm 4.16 and EL10 rpm 4.19. Thus step 4 (verify on the host) can pass while a client fails. Step 5 (verify-el) checks each target with the client tools:

  1. repoctl mock update also makes one verify root per target (build.html#mock). A verify root is the mock config of the target, plus rpm, dnf and gnupg2.
  2. Step 5 mounts the new tree and the key file read-only into that root (mock bind_mount plugin).
  3. Inside the root, repoctl imports the key file into a temporary rpmdb and runs rpmkeys --checksig on each RPM.
  4. Inside the root, repoctl runs dnf makecache on a temporary installroot. The new tree is a file:// repository with gpgcheck=1, repo_gpgcheck=1 and gpgkey= the key file. This runs the librepo signature check of the client.

Rule: client trust set

Step 5 uses the key file of the release that the clients have: the release in the deployment record of the signer. It does not use the key file of a release that this publish adds. For a first publish, it uses the key file of this publish.

A failure gives verify.el-failed (exit 10), and repoctl keeps the tree. repoctl repo verify --el runs the same check on demand. The default key set of repo verify is the client trust set (repo verify).

Rule

repoctl re-signs an RPM only when both conditions are true. Its signature verifies with a key in sign.keys. Its sha256 is in the base snapshot, which has a valid repomd.xml.asc. RPMs of different admins stay side by side. A change of the human who publishes never re-signs old RPMs.

repoctl repo resign --signer ID gives a new signature to each RPM of the key ID. It signs with the key of the human who runs the command. It is a publish run of kind resign, with the full publish order and gates. The summary shows the count per target and per repository, debuginfo included, and the size of the new blobs. --repo splits the work. When no RPM carries the key, the command exits with 4. A new signature changes the sha256 of the file. Thus resign also writes new supply chain records for each build that it touches (supply-chain.html#layout).

repo restore also re-signs the RPMs of a removed key in the older snapshot (publish.html#restore). Command: repo resign.

In the story, the publish of el9 keeps 170 RPMs: 120 of d.klein and 50 of the retiring key hpc-repo. It re-signs none.

Release package

The release package has one form: an in-tree package in the set repository, for example packages/slurm-release/, with role: release in repoctl.yaml.

  • The build identity of an in-tree package is the last set commit that changed its path, plus the target. repoctl builds it from a checkout of that commit. A key change is a commit on that path, so the plan says build with the reason commit-changed (build.html#plan).
  • The spec uses %autorelease and %autochangelog. The changelog then shows the commit message of each key change, for example "Trust key a.admin C2F9…52A7". Admins see each trust change in rpm -q --changelog.
  • repoctl release write local write writes the key file RPM-GPG-KEY-slurm from sign.keys: the keys in state active and retiring, sorted by id. It also writes the baseurl lines of the .repo file from repo.url. It does not commit. sign add, sign retire and sign remove call it and commit both files with the key change. In a new set, the human runs it in step 3 of help new-set. Command: release write.
  • The .repo file keeps one gpgkey= URL. It does not change when the team changes (F18).
  • The release package cannot remove keys from the clients (F16). repoctl sign offboard ID prints the commands for config management.
  • For the bootstrap of a new client, repoctl sign keyfile --checksum prints the sha256 of the key file (sign keyfile).

Doctor checks sign.keyfile (the key file equals sign.keys) and release.url (the baseurl lines equal repo.url). The release-version check release.version compares the Version of the release package with the version in the set name: 26.05 for slurm-26.05. A difference is a warning. A set name without a version, for example repoctl, has no release-version check (the "generic" test). A stale key file stops publish with sign.keyfile-stale (exit 5); the hint is repoctl release write, then commit.

In the story, the key file of slurm-release-26.05-1 holds hpc-repo, and slurm-release-26.05-2 adds d.klein. The set commit 7e21d0a adds a.admin, so the next build gives slurm-release-26.05-3.

Key expiry

rpm does not update an imported key (F12). EL10 does not trust an expired key (F6). Thus a new expiry date does not reach the clients.

Rule

Treat an expiring key as a key change. Add a new key, deploy it, retire the old key, re-sign, and remove the old key (offboarding and rotation). Do not extend the expiry date of a key that clients already have.

  • Doctor sign.expiry warns when a key expires inside key_expiry_warn (180 days). Its fix line is repoctl sign onboard NEW-ID, then repoctl sign retire OLD-ID.
  • Gate 1 refuses a signer that expires inside key_min_validity (30 days): sign.key-expiring, exit 12.
  • repoctl check reports published RPMs whose signer expires inside the warn window: advisory sign.expiring, level warn (advisories.html#codes).

The story keys expire on these dates: a.admin 2028-03-01, d.klein 2029-11-01, hpc-repo 2030-01-20.

sign remove IDlocal writeRefuses while latest of a target holds an RPM of the key (sign.key-in-use, exit 12, hint repoctl repo resign --signer ID). Then sets state removed, writes a key file without it, makes one set commit.

sign lsreadLists the keys with state, deployment record, expiry and the count of RPMs per target in latest.
sign keyfile --checksumreadPrints the sha256 of the key file for the bootstrap.

The result kinds are SignerList and OnboardReport (contract.html#kinds). The MCP read tools are repoctl_sign_ls and repoctl_sign_onboard. MCP has no tool for the other sign commands (agents.html#mcp-tools). The Signing page of the web UI shows the same keys and onboarding steps (ui-publish.html#signing).

Offboarding and rotation

Offboarding removes the trust in one key. The order protects the clients: re-sign first, then the new key file, then the key removal on the clients.

  1. repoctl sign retire ID: state retiring, set commit. The key cannot sign any more.
  2. repoctl repo resign --signer ID per target, by an admin with an active, deployed key. Each RPM of that key gets a new signature.
  3. repoctl sign remove ID. It refuses while latest of a target holds an RPM of that key. Then: state removed, a new key file without the key, set commit.
  4. Build and publish the new release package. Config management rolls it out.
  5. Config management removes the key on each client. repoctl sign offboard ID prints the commands.
  6. Remove the human from the GitHub team. The entry in keys/deployed.yaml can stay, because gate 1 refuses a removed key.

In the story, hpc-repo is the next key to leave. It is in state retiring, and 50 RPMs in latest of el9 carry it; el10 has none. After steps 1 to 4, repoctl sign offboard hpc-repo prints the client commands:

Run on every client after "dnf upgrade slurm-release":
  EL9:    rpm -e gpg-pubkey-7c3a19f2
  EL10:   rpmkeys --erase 7c3a19f2      # EL10.1 and later; else use the EL9 line
  both:   rm -rf /var/cache/dnf/slurm*/pubring

A rotation is an onboarding of the new key, then an offboarding of the old key. An expiring key uses the same rotation (key expiry). A move to a central signer (option E) also uses it: add the central key, then offboard the personal keys.

Help topics

These are the texts of repoctl help signing and repoctl help team. The list of all topics is in cli.html#topics.

repoctl help signing

SIGNING

Each admin signs with an own key. repoctl.yaml lists the keys that
the clients trust (sign.keys), each with a state:
  active    can sign after its deployment; clients trust it
  retiring  cannot sign; its RPMs stay; re-sign them, then remove it
  removed   no RPM in latest carries it; clients must not trust it
A key is "deployed" when keys/deployed.yaml records that config
management installed a release package that holds the key.

Add a key:      repoctl sign add ID --fingerprint FPR
                (writes the key file of the release package, commits)
See the steps:  repoctl sign onboard ID
Confirm:        repoctl sign deployed ID --release NVR
Replace a key:  add and deploy the new key, then "repoctl sign retire
                OLD", "repoctl repo resign --signer OLD", "repoctl
                sign remove OLD", and publish the new release package.
Clients:        "repoctl sign offboard ID" prints the commands.

A new expiry date does not reach the clients. Treat an expiring key
as a key change.

publish signs only with an active, deployed key. It re-signs no old
RPM; only "repoctl repo resign" does. "repoctl doctor" checks sign.*.

repoctl help team

TEAM

Add a second admin host:
  1. dnf install repoctl
  2. git clone the set repository (branch builder/SET); cd into it
  3. repoctl doctor           a missing secret key is a warning here
  4. repoctl checkout         the worktrees of the lock
  5. repoctl repo pull        the local copy of latest from the registry
  6. repoctl status           shows what differs from latest
To publish, the new admin needs a key (repoctl help signing) and
write access to the registry packages (repoctl doctor: registry.write).
Each admin works as an own user and/or on an own host. The state of
a host is not shared. The registry and git are shared. Two admins
coordinate in the team channel; repoctl does not lock between hosts.
If latest moved, publish stops with state.behind (exit 13): run
"repoctl repo pull".
