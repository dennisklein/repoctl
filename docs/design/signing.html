Signing and trust

This chapter specifies how repoctl signs a publish and how the clients trust a key. It gives the client facts, the options for team keys, the choice, the trust chain and the gates before the first signature. It also gives the release package and the life of a key from onboarding to offboarding.

  • Each admin signs with a personal key (OpenPGP v4, on a YubiKey or in a file). No key is shared.
  • Clients trust all team keys through one key file in the release package. Each RPM and each repomd.xml.asc has exactly one signature.
  • Gate 1: the signer is active and valid. Gate 2: a human confirmed the deployment of the key in keys/deployed.yaml. Gate 3: the key format.
  • A signer probe asks for the PIN at the start of a publish, not in the sign step.
  • Publish verifies each target in its EL mock chroot, with the EL rpm and dnf and only the keys that the clients have.
  • A normal publish never re-signs old RPMs. repoctl repo resign does it as its own publish.
  • Key states: active, retiring, removed, revoked. An expiring key is a key change, not a new expiry date.
  • A release package cannot remove a key from the clients. Config management does it, and repoctl prints the commands.

Client facts

The clients run Rocky 9: rpm 4.16.1.3 with OpenSSL, dnf 4.14, librepo with gpgme. Next come Rocky 10 clients: rpm 4.19.1.1 with rpm-sequoia, dnf 4.20, librepo with the librpmio back end. The versions come from the CentOS Stream c9s and c10s spec files. The design depends on these facts.

Options

Five options give a team its signing keys. The client facts decide between them.

A. One shared key, encrypted with sops

The team keeps the armored secret key in git as a sops file. sops encrypts a file to many recipients: age keys (also SSH keys and age plugins), PGP, cloud KMS and HashiCorp Vault transit. sops updatekeys or sops rotate adds or removes a human.

The decrypt path keeps the key off the disk. repoctl makes a private GnuPG home in $XDG_RUNTIME_DIR/repoctl/g-<run> (mode 0700, a per-user tmpfs under systemd-logind). It pipes sops decrypt into gpg --batch --import and signs with rpmsign --define "_gpg_path <dir>". At the end, also on an error or SIGINT, it runs gpgconf --kill gpg-agent and deletes the directory. The path must be short, because GnuPG fails when the socket path is too long. sops exec-file --no-fifo writes a temporary file to /tmp and is not usable.

  • Each member holds the full private key in clear text during each publish. A member can copy it.
  • When a member leaves, a new recipient list is not enough: removed key owners can still have the old data key. The team must make a new signing key and re-sign all packages. Then it must ship the new public key and remove the old key on each client (F12, F13, F16). This is the highest offboarding cost of all options.
  • A signature does not show who published.

B. Personal keys, no sharing

Each admin has a personal signing key, on a YubiKey (OpenPGP card) where possible. The set lists all trusted public keys. The release package ships all of them in one file. Each publish signs with the key of the human who runs it.

  • Clients: one trusted key verifies an RPM (F2) and a repomd.xml.asc with one signature (F8, F9). dnf imports all keys from the file without a question when it runs with -y (F1, F14).
  • The .repo file stays stable: one gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-slurm line, and all keys in that one file. The key file is not %config, so an update always replaces it (F18).
  • YubiKey: the PIN stays in the gpg-agent session. The touch policy of the signature slot is "cached" (15 s) or "off". With "on", each RPM needs one touch.
  • Algorithm: RSA 4096 is the safe default. The clients verify Ed25519 (F17); the test on EL9 is open.

Two rules follow from F12 and F13. Gate 2 and the offboarding order enforce them.

  1. Add a human before the first signature. A client reads a new key only from its installed release package. If a new key signs repomd.xml.asc first, the client cannot read the metadata, and it cannot get the new release package either. Thus an old key publishes the new release package, and config management deploys it. Only then can the new key sign.
  2. Remove a human in this order: re-sign, ship the new key file, remove the key on the clients. If the key goes first, packages with the old signature fail to install.

C. One primary key, personal signing subkeys

The primary key stays offline, for example on an encrypted USB stick in a safe. Each admin gets a signing subkey on a YubiKey. Clients see one key identity.

  • EL9 and EL10 verify the signatures of a signing subkey (F11).
  • Onboarding breaks clients. A new subkey changes the certificate, but rpm 4.16 and 4.19 ignore the import of a known primary key (F12). The dnf repository keyring also skips the known key ID (F13). Config management must erase the key and delete the repository keyring on each client, for each new admin.
  • Offboarding is not cheaper. A subkey revocation reaches a client only by the same erase and import.
  • A longer expiry of the primary key has the same problem on EL10, where rpm-sequoia does not trust an expired key (F6). The key hpc-repo expires on 2030-01-20.
  • gpg needs -u <subkey-fingerprint>! to use one exact subkey.

D. Several signatures on one artifact

  • RPM: EL9 rpm 4.16 keeps one signature (F3). An rpm 6 or EL10.1 signer can add v6 signatures with --rpmv6 (F4, F5). The client then needs each signer key, because NOKEY fails (F6). What EL9 does with the extra tag needs a test (F7).
  • repomd.xml.asc: EL9 accepts it when one signature is valid (F8). EL10 fails on the second packet (F9).

E. Central signer, no sharing

One key on one machine. Admins send signing requests to it. Clients see one key that does not change when the staff changes.

The choice: personal keys, many trusted keys, one signature per file

repoctl uses option B. Two different things have the name "many keys":

  • Many trusted keys on the clients: yes. The release package installs the public keys of all admins. dnf and rpm accept a file when its signer is one of these keys (F1, F2, F8, F14). Different RPMs in one repository can carry signatures of different admins.
  • Many signatures on one file: no. rpm 4.16 (EL9) keeps only one signature per RPM (F3). EL10 can store more, but then it needs all signer keys (F6). EL10 librepo refuses a repomd.xml.asc with more than one signature (F9).

What repoctl does:

  • Each admin makes an RSA 4096 key on a YubiKey, with the touch policy "cached" and an expiry of 3 years or less (help key). The key hpc-repo of the bash scripts (GSI HPC repo <hpc-repo@gsi.de>, …7C3A 19F2) stays trusted in state retiring until no RPM in latest carries it.
  • repoctl signs each new RPM with rpmsign --resign. It passes %_gpg_name (rpm 4) and %_openpgp_sign_id (rpm 6) as the full fingerprint. It never uses --addsign and never passes --rpmv6, so the result is the same on rpm 4.16, 4.19 and 6.
  • repoctl writes repomd.xml.asc with one gpg --detach-sign --armor -u <FPR>!. It has exactly one signature packet. repoctl doctor checks this (sign.repomd).
  • The signer host is always Fedora (rpm 6 with rpm-sequoia). The EL chroot check covers the client side (verify-el).
  • Fingerprints are always full (40 hex characters) in the config, the output, the logs and the snapshot annotations. Short key IDs are for display only.
  • repoctl has no sops back end. Config management removes keys on the clients, and repoctl prints the commands.
  • MCP never signs. The web UI signs only through repoctl publish, after the typed confirmation.

The set config says which keys the clients trust: sign.keys[] (id, file, fingerprint, state), sign.release.keyfile and sign.checks (key_expiry_warn: 180d, key_min_validity: 30d). The user config says which key this human signs with: sign.key, an id of sign.keys or a full fingerprint. sign.gpg_name and REPOCTL_GPG_NAME are aliases of sign.key and REPOCTL_SIGN_KEY. The keys are in config.html#set-config, config.html#user-config and config.html#env.

Client trust chain

A client installs a package only when two checks pass: dnf checks repomd.xml.asc (repo_gpgcheck=1), and rpm checks the RPM signature (gpgcheck=1). Both use the keys that the client got from the release package.

Client bootstrap

Each snapshot has two root files next to the three repositories (publish.html#format): the key file, for example RPM-GPG-KEY-slurm, and <release package>.rpm, for example slurm-release.rpm. Both come from the release RPM with the highest NVR in the binary repository of the snapshot. Thus <repo.url>/<target.path>/ always has a stable link to the newest release and its key file. Config management does the client bootstrap of a new client of target el9 in four steps:

  1. Download https://repo.example.org/slurm-26.05/el9/RPM-GPG-KEY-slurm. Compare its sha256 with the pin. A different sum stops the client bootstrap, and nothing changes on the client.
  2. Import the file: rpm --import RPM-GPG-KEY-slurm.
  3. Download slurm-release.rpm from the same directory. Check it with rpmkeys --checksig slurm-release.rpm. Install it with dnf install ./slurm-release.rpm.
  4. Stop the management of the key file. The release package now owns the key file and the .repo file, and each update replaces them.

Rule: the pin

The pin is the sha256 of the key file in latest of the target. repoctl sign keyfile --target el9 --checksum prints it. It changes with each release that changes the key file. repoctl sign deployed prints the new pin of the target, and the human puts it into config management. Config management manages the key file only until the release package is installed. Else it puts the old key file back after each key change.

A client bootstrap with an old pin stops in step 1, so it fails safe. A client that missed a release can fail later: when a key of that release signs repomd.xml.asc, dnf on that client cannot read the metadata (V13). The repair is the client bootstrap again, with the current pin. It installs the newest release, and the client trusts the new key. Test V33 checks the client bootstrap on EL9 and EL10 (delivery.html#verification).

Signer probe

Step 1 of a publish (publish order) runs a signer probe. The probe signs a random 32-byte value with gpg --detach-sign -u <FPR>! and verifies it. Thus gpg-agent asks for the PIN or passphrase at the start, and not in the middle of the sign step.

  • CLI: pinentry asks in the terminal or on the desktop. repoctl suspends the progress display for it.
  • Web UI: the UI is for the local user only, so pinentry shows on the local desktop. The browser never asks for a PIN. Step 1 of the publish page shows the probe state: card missing, waiting for the PIN on the desktop, touch your key, ready. When a signature takes more than 1 s, the UI shows "touch your key" over SSE (ui-publish.html#progress).
  • If the probe fails or the human cancels pinentry: sign.locked, exit 9. The hint gives gpg --card-status.

The preflight of publish also checks rpmsign, createrepo_c, gpg, the secret key of sign.key and a usable pinentry. A missing card gives sign.card-absent, a missing pinentry gives sign.no-pinentry (both exit 9). A failure in the sign step gives sign.failed. The full table is contract.html#problems.

Rule: first publish

Gate 2 does not apply when the registry has no snapshot of the target, the local copy has none, keys/deployed.yaml has no record for the target, and the publish is not an import. No client uses such a target yet. When the local copy or a record exists, the OCI package is lost, and publish stops with snapshot.missing (publish.html#disaster). The summary then says "first publish of el10: no clients yet; the signer must be in the key file of this release". A key that a publish adds can never sign that publish.

Gate 2 reads only the committed record. The record is in the pushed set commit (publish.html#checks). Publish also stops when the remote branch has another repoctl.yaml or keys/ than the set commit (sign.trust-behind, exit 13, security.html#remote-tip). Thus each publish reads the newest record, and all admins see the same record.

Why a human confirms

Config management gives no feedback to repoctl. A published release package does not prove that the clients have it. If a key signs before the clients have it, dnf on the clients cannot read the metadata. Thus a human checks the clients and confirms the deployment.

Deployment record

repoctl sign deployed ID --release NVR --target ID... records that config management installed the release NVR on all clients of the target. Config management also put the key file of that release at the keyring of the mirror line of the target (publish.html#mirror). The record is per target, and --target is required: without it, the command stops with a usage error (exit 2). repoctl checks that the release is in latest of each selected target and that its key file holds the key. For an import, --path DIR names the tree instead of latest. Then it asks the human to type the key id, writes keys/deployed.yaml and makes a set commit. The human pushes it. The command also prints the pin of the client bootstrap for the target (bootstrap). --dry-run runs the checks and shows the entries, and writes nothing.

Rule: who confirms

repoctl signs the set commit of the record with the key of sign.key, and confirmedBy is the id of that key. The key must be active. It must not be the key of the record while another key is active: sign.self-confirm, exit 12. Publish checks the signature of each record (security.html#set-inputs).

The command needs a terminal or the UI dialog "Confirm deployment" (ui-publish.html#signing). It has no unattended mode and no MCP tool. Command: sign deployed.

A record has one of two forms per target. A release record names the release NVR. A key file record names the sha256 of a key file and the set commit of that key file: repoctl sign deployed ID --keyfile SHA256 --target ID. It records that config management installed this key file on all clients and on the HTTP server, outside a release package, as for the bootstrap of a client. repoctl checks that SHA256 is the sum that repoctl sign keyfile --checksum prints for the committed key file, that the key file holds the key and that the target has a latest.

Rule: the file keys/deployed.yaml

  • Each entry has key, target, the full fingerprint, release (the NVR with the dist tag), confirmedBy, at and an optional note. The fingerprint must equal the fingerprint of the key in sign.keys; else gate 2 does not count the entry.
  • repoctl writes one entry per key and target, sorted by key, then by target. A new record of a key and target replaces the old entry. The git history keeps the old one.
  • When the file has two entries for one key and target, for example after a git merge, the entry with the newest at wins. The next command that writes the file keeps only that entry.
  • repoctl schema deployments prints the JSON Schema of the file (contract.html#schemas).

After a git conflict in keys/deployed.yaml, keep the entries of both sides and commit. After a conflict in sign.keys of repoctl.yaml, keep the keys of both sides, run repoctl release write for the key file and the .repo files, and commit. repoctl help signing gives the same steps.

A key is deployed for a command when gate 2 passes for each target in scope that has a latest. The scope is the selected targets of a publish, or the targets of the command. Thus repoctl sign ls shows hpc-repo as not deployed: el10 has a latest, and hpc-repo has no el10 record. hpc-repo signs nothing new, because it is retiring.

Withdraw a record and repair missed clients

A human can confirm a deployment too early: some clients do not have the release yet. When the key then signs a publish, these clients cannot read the metadata (V13). repoctl sign deployed ID --target T --withdraw removes the entry of the key and the target. It is a shared-state command, as the record is: a dry run, the typed key id, a set commit "Withdraw deployment of ID on T", no unattended mode and no MCP tool. Without an entry, it stops with sign.not-deployed (exit 12). After the withdrawal, gate 2 stops each publish of the key on that target.

The repair when the key signed files in latest of the target:

  1. Withdraw the record: repoctl sign deployed a.admin --target el9 --withdraw --note "3 clients of cluster B miss slurm-release-26.05-3". When latest holds files of the key, the hint is the next step.
  2. An admin with an other deployed key runs repoctl repo resign --signer a.admin --target el9. The new snapshot has no file of a.admin, so each client reads it again.
  3. Config management installs the release on the missed clients. A client that cannot read the repository gets the client bootstrap with the current pin (bootstrap).
  4. A human checks all clients again and records the deployment again: repoctl sign deployed a.admin --release slurm-release-26.05-3 --target el9.

When only a few clients missed the release, step 3 alone repairs them, and the record can stay. The web UI has no withdraw action.

Trust block

When the release package of a publish has a new key file or a new .repo file, the summary shows the trust block. For a .repo file, the block shows each changed line. The block is for the human who publishes, and it needs a typed answer even with --yes. That human is the second key holder of the change: a key that the release adds cannot sign this publish (gate 2). For each change, the block gives the set commit and the key that signed it (security.html#set-inputs). The story publish of slurm-release-26.05-3 by d.klein:

trust    slurm-release-26.05-3 changes the key file of all clients
         + a.admin  C2F9 7713 05AB E4D6 18C3  9F2B 70DE A5C1 E93F 52A7
                    added in set commit 7e21d0a by A. Admin <a.admin@gsi.de>, signed by a.admin

Type the key id of each added key to continue: a.admin

A change of the .repo file without an added key needs no key id. Then the typed set name is the answer, and --yes does not skip it. Without the answer, publish stops with sign.trust-change (exit 6). The web UI asks for the same key id in step 2 Confirm (ui-publish.html#confirm).

Verify in the EL chroot

repoctl runs on Fedora, with rpm 6 and rpm-sequoia. The clients use EL9 rpm 4.16 and EL10 rpm 4.19. Thus step 4 (verify on the host) can pass while a client fails. Step 5 (verify-el) checks each target with the client tools:

  1. repoctl mock update also makes one verify root per target (build.html#mock). A verify root is the mock config of the target, plus rpm, dnf and gnupg2.
  2. Step 5 mounts the new tree and the key file read-only into that root (mock bind_mount plugin).
  3. Inside the root, repoctl imports the key file into a temporary rpmdb and runs rpmkeys --checksig on each RPM.
  4. Inside the root, repoctl runs dnf makecache on a temporary installroot. It uses the .repo file of the release in the client trust set, with each baseurl changed to the file:// URL of the new tree. Thus the check has the gpgcheck, repo_gpgcheck and gpgkey lines of the clients. This runs the librepo signature check of the client.

Rule: client trust set

Step 5 uses the key file that the clients have: the key file of the release in the deployment record of the signer, or the key file of a key file record. It does not use the key file of a release that this publish adds. For a first publish, it uses the key file of this publish. The client trust set never holds a revoked key.

A failure gives verify.el-failed (exit 10), and repoctl keeps the tree. repoctl repo verify --el runs the same check on demand. The default key set of repo verify is the client trust set (repo verify).

Rule

repoctl re-signs an RPM only when both conditions are true. Its signature verifies with a key in sign.keys, at the time of the signature (after the expiry). Its sha256 is in the base snapshot, which has a valid repomd.xml.asc. RPMs of different admins stay side by side. A change of the human who publishes never re-signs old RPMs.

repoctl repo resign --signer ID gives a new signature to each RPM of the key ID. It signs with the key of the human who runs the command. It is a publish run of kind resign, with the full publish order and gates 1 to 3 (checks per kind). The summary shows the count per target and per repository, debuginfo included, and the size of the new blobs. --repo splits the work. When no RPM carries the key, the command exits with 4. A new signature changes the sha256 of the file. Thus resign also writes new supply chain records for each build that it touches (supply-chain.html#layout).

repo restore also re-signs the RPMs of a removed or revoked key in the older snapshot (publish.html#restore). Command: repo resign.

In the story, the publish of el9 keeps 170 RPMs: 120 of d.klein and 50 of the retiring key hpc-repo. It re-signs none.

Release package

The release package has one form: an in-tree package in the set repository, for example packages/slurm-release/, with role: release in repoctl.yaml. A set has at most one. A second role: release, or one on a package with branch, gives config.invalid (config rules).

  • The build identity of an in-tree package is the last set commit that changed its path, plus the target. repoctl builds it from a checkout of that commit. A key change is a commit on that path, so the plan says build with the reason commit-changed (build.html#plan).
  • The spec uses %autorelease and %autochangelog. The changelog then shows the commit message of each key change, for example "Trust key a.admin C2F9…52A7". Admins see each trust change in rpm -q --changelog.
  • repoctl release write local write writes the key file RPM-GPG-KEY-slurm from sign.keys: the keys in state active and retiring, sorted by id. It also writes the whole .repo file of each target (the .repo file). It does not commit. sign add, sign retire and sign remove call it and commit the files with the key change. In a new set, the human runs it in step 3 of help new-set. Command: release write.
  • The .repo file keeps one gpgkey= URL. It does not change when the team changes (F18).
  • The release package cannot remove keys from the clients (F16). repoctl sign offboard ID prints the commands for config management.
  • For the client bootstrap, repoctl sign keyfile --target ID --checksum prints the sha256 of the key file in latest of the target (client bootstrap, sign keyfile).

Doctor checks sign.keyfile (the key file equals sign.keys), release.url (the baseurl lines equal repo.url and targets[].path) and release.repo (each .repo file equals the file that release write writes). The release-version check release.version compares the Version of the release package with the version in the set name: 26.05 for slurm-26.05. A difference is a warning. A set name without a version, for example repoctl, has no release-version check (the "generic" test). A stale key file stops publish with sign.keyfile-stale (exit 5). A .repo file that differs stops publish with sign.repofile-stale (exit 5). For both, the hint is repoctl release write, then commit.

In the story, the key file of slurm-release-26.05-1 holds hpc-repo, and slurm-release-26.05-2 adds d.klein. The set commit 7e21d0a adds a.admin, so the next build gives slurm-release-26.05-3.

Rule: the spec of the release package

  • repoctl defines the macro %repoctl_target (the target id) in each rpmspec and mock call of the package with role: release. The spec uses it to select its file: Source1: slurm-%{repoctl_target}.repo.
  • The spec installs that file as /etc/yum.repos.d/<repo.name>.repo and the key file as /etc/pki/rpm-gpg/<sign.release.keyfile>.
  • The spec marks the .repo file %config, not %config(noreplace). An update then replaces a file that a human changed, and rpm keeps the old file as .rpmsave. Thus a new repo.url or gpgkey= line reaches each client (F18 gives the problem of noreplace).

Do not change the .repo file on a client. For one dnf call, use dnf --enablerepo=slurm-source or --disablerepo=slurm. A change to the trust lines is a change of the set: edit repoctl.yaml, run repoctl release write and commit.

Key expiry

rpm does not update an imported key (F12). EL10 does not trust an expired key (F6). Thus a new expiry date does not reach the clients.

Rule

Treat an expiring key as a key change. Add a new key, deploy it, retire the old key, re-sign, and remove the old key (offboarding and rotation). Do not extend the expiry date of a key that clients already have.

Three checks read the expiry date of a key. Each one has its own id and limit. The limits are sign.checks.key_expiry_warn (default 180 days) and sign.checks.key_min_validity (default 30 days).

After the expiry

An RPM keeps its signature when the key expires. EL10 rpm then refuses the RPM (F6). EL9 rpm, the Fedora rpm of the signer host and the mirror job need the test V7 (delivery.html#verification). The design does not depend on its result:

Rule: a signature counts at the time it was made

repoctl checks an RPM signature in its own process, with the public key in keys/ID.asc, at the creation time of the signature. Thus host verify (step 4), repo pull, repo verify and the re-sign rule accept a signature that a key of sign.keys made before the key expired. For each such RPM they give the warning sign.expired-signer. verify-el uses the rpm of the target. A publish of an EL10 target with such an RPM in the base therefore stops with verify.el-failed (exit 10). repoctl repo resign --signer ID replaces the signatures, and it is the only way out.

Thus re-sign the RPMs of a key before it expires. The advisory sign.expiring becomes required 30 days before the expiry date.

The team membership is the last step, and an organization owner adds it. Until then, the new admin cannot push: an admin of the team pushes the set commit of sign add with the same commit id, for example from a fork of the new admin. Offboarding removes the membership first (offboarding).

Each set has its own sign.keys, release package and mirror lines. Do steps 1 to 4 in each set that the key must sign. A set that misses them fails safe: gate 2 stops a publish there, and its mirror lines keep the old tree. repoctl doctor names each set whose keys differ (sign.cross-set, doctor checks).

A new admin host follows the steps of help team. The registry rules for the team are in publish.html#registry.

Offboarding and rotation

Offboarding removes the trust in one key. The order protects the clients: first the access of the human, then the re-sign, then the new key file, then the key removal on the clients.

  1. When the human leaves the team: an organization owner removes the human from the GitHub team, and the human deletes the registry token. The team removal alone ends the write access to the set repository and to the packages, because the token has its access only through the team (publish.html#registry). Skip this step for a key without a team member, for example hpc-repo, and for a rotation.
  2. repoctl sign retire ID: state retiring, set commit. The key cannot sign any more. An other admin pushes the commit.
  3. repoctl repo resign --signer ID per target, by an admin with an active, deployed key. Each RPM of that key gets a new signature.
  4. repoctl sign remove ID. It refuses while latest of a target holds an RPM of that key. Then: state removed, a new key file without the key, set commit.
  5. Build and publish the new release package for each target. Config management rolls it out to the clients and to the keyring of each mirror line.
  6. Config management removes the key on each client. repoctl sign offboard ID prints the commands. Then a human records it per target: repoctl sign removed ID --target T (removal record).

Rule: each set that trusts the key

Each set has its own sign.keys, release package and mirror lines. Do steps 2 to 5 in each set whose sign.keys has the fingerprint. Do step 6 only after that: rpm -e gpg-pubkey-… removes the key for all repositories of a client, so a set that still has RPMs of the key breaks on that client. The doctor check sign.cross-set names each set that still has the key.

In the story, hpc-repo is the next key to leave. It is in state retiring, and 50 RPMs in latest of el9 carry it; el10 has none. After steps 2 to 5, repoctl sign offboard hpc-repo prints the client commands:

Run on every client after "dnf upgrade slurm-release":
  EL9:    rpm -e gpg-pubkey-7c3a19f2
  EL10:   rpmkeys --erase 7c3a19f2      # EL10.1 and later; else use the EL9 line
  both:   rm -rf /var/cache/dnf/slurm*/pubring

A rotation is an onboarding of the new key, then an offboarding of the old key. An expiring key uses the same rotation (key expiry). A move to a central signer (option E) also uses it: add the central key, then offboard the personal keys.

Removal record

Config management gives no feedback, so a human confirms the key removal of step 6, as for a deployment. repoctl sign removed ID --target ID... [--note TEXT] [--dry-run] records that config management removed the key from all clients of each target. It is a shared-state command: the typed key id, a set commit, no unattended mode and no MCP tool. It checks that the key is in state removed and that the key file in latest of each target does not hold it. Else it stops with sign.not-removed (exit 12).

The command writes one entry per key and target into the list removals of keys/deployed.yaml: key, target, fingerprint, confirmedBy, at and an optional note. The rules of the file apply (deployment record). The deployment entry of the key stays, because gate 1 refuses a removed key.

Until the removal record exists, repoctl sign ls shows a removed key with "clients: unconfirmed" for that target, and sign offboard shows step 6 as open. After the record, it shows "clients: removed", with the human and the date.

Emergency: a lost or a compromised key

Two failures do not fit the normal order of onboarding and offboarding. A compromised key must lose the trust of the clients at once. A lost key can leave a target without a deployed signer. Both use a key file that config management installs without a release package, because a release package needs a deployed signer and a publishable target. The runbook Key compromise or lost key gives the steps for a human.

Key compromise

A key is compromised when another human can sign with it: a copied file key, a stolen card with a known PIN, or a host with the key in the hands of an attacker. A lost card that another human can find counts as compromised. The trust of the clients in the key must end at once. The normal offboarding order keeps that trust until step 5, so it does not apply.

  1. Stop the access. When the human leaves, an organization owner removes the human from the GitHub team. Delete the registry tokens of each host that held the key.
  2. Run repoctl sign revoke ID and type the key id. The key gets state revoked, and the key file loses it in one set commit. Push the set commit.
  3. Run repoctl sign offboard ID. It prints the client commands and the sha256 of the new key file. Config management installs that key file with the pinned sum, erases the key and deletes the dnf repository keyring: first on the HTTP server, then on each client. Do not wait for a release package. From now on, the mirror job serves no snapshot with a file of the key, and the clients refuse these files.
  4. Check each snapshot that sign offboard lists. The team must know each publish: compare the publish id, the user and the host with the team channel. When a publish is not known, first run repoctl repo restore REF with the newest known snapshot.
  5. A human with another active, deployed key runs repoctl repo resign --signer ID for each target. The new snapshot has no file of the revoked key. The mirror job serves it, and the clients work again.
  6. Publish the release package with the new key file at the next publish of each target.

When no other key is deployed, add the new key before step 3 (repoctl sign add NEW). Thus the key file of step 3 holds it. After step 3, record it with repoctl sign deployed NEW --keyfile SHA256 (recovery). Then NEW does step 5.

Rule: revoked key

A revoked key never signs again, and it never comes back. It is not in the key file, and the client trust set of verify-el and repo verify never holds it. A normal publish refuses a base with a file that it signed (sign.removed-signer, exit 12). Only repo resign and repo restore replace these signatures. repo pull accepts them with the warning sign.removed-signer, so that a host can get the base of the re-sign.

Recovery without a deployed signer

A key is lost when its secret key is gone, for example a broken card or a lost disk. Its signatures stay valid, and the clients still trust it. Retire it: sign retire needs no secret key. When another active key is deployed for each target with a latest, the rest is a normal rotation (offboarding and rotation).

When the lost key is the last deployed signer of a target, sign retire refuses (sign.last-signer), and no key can sign a release package with a new key. Do these steps:

  1. Make a new key and run repoctl sign add NEW --fingerprint FPR. Push the set commit.
  2. Run repoctl sign keyfile --checksum. It prints the sha256 of the new key file.
  3. Config management installs the key file with this pinned sum on all clients and on the HTTP server of each target, as for the bootstrap of a client.
  4. For each target, run repoctl sign deployed NEW --keyfile SHA256 --target ID, and push the set commit. Now NEW passes gate 2.
  5. Retire the lost key. Then re-sign its RPMs with NEW, remove it and publish the new release package (offboarding and rotation).

Rule: two deployed signers

Keep two active keys or more with a deployment record for each target. Then a lost key is a normal rotation, and sign.last-signer never stops a retire.

These are the texts of repoctl help signing, repoctl help key, repoctl help emergency and repoctl help team. The list of all topics is in cli.html#topics.

repoctl help signing

SIGNING

Each admin signs with an own key. repoctl.yaml lists the keys that
the clients trust (sign.keys), each with a state:
  active    can sign after its deployment; clients trust it
  retiring  cannot sign; its RPMs stay; re-sign them, then remove it
  removed   no RPM in latest carries it; clients must not trust it
  revoked   compromised; clients must stop to trust it at once; final
A key is "deployed" when keys/deployed.yaml records that config
management installed a release package that holds the key.

Make a key:     repoctl help key
Add a key:      repoctl sign add ID --fingerprint FPR
                (writes the key file of the release package, commits)
See the steps:  repoctl sign onboard ID
Undo a retire:  repoctl sign activate ID
Confirm:        repoctl sign deployed ID --release NVR --target T
                (one entry per key and target in keys/deployed.yaml)
                or --keyfile SHA256, when config management
                installed the key file without a release package
Withdraw:       repoctl sign deployed ID --target T --withdraw
                (a confirmation that came too early; then re-sign)
Replace a key:  add and deploy the new key, then "repoctl sign retire
                OLD", "repoctl repo resign --signer OLD", "repoctl
                sign remove OLD", and publish the new release package.
Clients:        "repoctl sign offboard ID" prints the commands. Then
                record it: repoctl sign removed ID --target T
Several sets:   each set has its own sign.keys and release package.
                Repeat the steps in each set that the key signs.
Set commits:    sign each commit that changes repoctl.yaml,
                repoctl.lock, keys/, a macros file or an in-tree
                package (git config commit.gpgsign true). publish
                refuses a change without a signature of an active
                key, or of the key that the change adds.
Compromise:     "repoctl sign revoke ID" ends the trust at once
                (repoctl help emergency).

A new expiry date does not reach the clients. Treat an expiring key
as a key change, and re-sign its RPMs before it expires.

Git conflict in keys/deployed.yaml: keep the entries of both sides,
then commit. The newest "at" wins for one key and target.
Git conflict in sign.keys: keep the keys of both sides, then run
"repoctl release write" and commit.

publish signs only with an active, deployed key. It re-signs no old
RPM; only "repoctl repo resign" does. "repoctl doctor" checks sign.*.

repoctl help key

KEY

Make a signing key on a YubiKey (OpenPGP card). The card makes the
secret key, and the key never leaves the card. There is no backup:
a lost card is a key change (repoctl help emergency).
  1. ykman openpgp reset                    only for a new card
  2. ykman openpgp access change-pin        default PIN 123456
     ykman openpgp access change-admin-pin  default 12345678
     ykman openpgp access change-reset-code
  3. ykman openpgp keys set-touch sig cached
  4. gpg --card-edit, then: admin, key-attr (RSA 4096), generate
     no off-card backup; expiry 3y or less
  5. gpg --list-keys --with-fingerprint     the full fingerprint
  6. repoctl sign add ID --fingerprint FPR
A file key, without a card:
  gpg --quick-gen-key "NAME <MAIL>" rsa4096 sign 3y
Make the next key 180 days before this key expires (repoctl doctor:
sign.expiry). Keep two deployed keys for each target.

repoctl help emergency

EMERGENCY

A key is compromised (another human can sign with it):
  1. Remove the access: GitHub team, registry tokens of its hosts.
  2. repoctl sign revoke ID          type the key id; push the commit
  3. repoctl sign offboard ID        the commands for config management:
     install the new key file (pinned sum), erase the key, rm pubring;
     on the HTTP server first, then on every client. Do not wait.
     Clients refuse the files of the key until step 5.
  4. Check each listed publish. An unknown one: repoctl repo restore REF
  5. repoctl repo resign --signer ID --target T   (another deployed key)
  6. Publish the release package with the next publish.

A key is lost (card broken, all PINs blocked, file key deleted):
  repoctl sign retire ID, then the normal rotation (help signing).
  The last deployed signer is lost:
    repoctl sign add NEW --fingerprint FPR; push
    repoctl sign keyfile --checksum; config management installs it
    repoctl sign deployed NEW --keyfile SHA256 --target T; push

Keep two deployed keys for each target.

repoctl help team

TEAM

Add a second admin host:
  1. dnf install repoctl-release, check the key fingerprint, then
     dnf install repoctl; the steps are in
     https://dennisklein.github.io/repoctl/design/decision.html#tool-bootstrap
  2. git clone the set repository (branch builder/SET); cd into it
  3. repoctl doctor           a missing secret key is a warning here
  4. repoctl checkout         the worktrees of the lock
  5. repoctl repo pull        the local copy of latest from the registry
  6. repoctl mock update      the mock chroots and the verify roots
  7. repoctl check --install-timer   the daily check of the set
  8. repoctl status           shows what differs from latest
To publish, the new admin needs:
  - a key (repoctl help key) and sign.key in the user config
    (repoctl config show)
  - a registry login with write:packages (repoctl doctor:
    registry.login, registry.write)
Each admin works as an own user and/or on an own host. The state of
a host is not shared. The registry and git are shared. Two admins
coordinate in the team channel; repoctl does not lock between hosts.
If latest moved, publish stops with state.behind (exit 13): run
"repoctl repo pull". If another admin pushed a change of
repoctl.yaml or keys/, publish stops with sign.trust-behind
(exit 13): run "git pull --ff-only".

Stand in for an admin who is away:
  1. git pull; repoctl checkout; repoctl repo pull
  2. repoctl status         "in flight" counts the pinned nodes that
                            latest does not hold, and how many build here
  3. repoctl plan; repoctl build
                            the staging of the other admin is not on this
                            host, so these nodes build again here
  4. repoctl sign ls        publish only the targets where your key has
                            a deployment record (gate 2)
  5. repoctl publish --target TARGET
                            for a failed node that is not urgent, see
                            "repoctl help urgent"

Push each set commit (sign add, sign deployed, the lock after pin)
and each commit of an external clone at once. A lost host loses
each commit that is not pushed. "repoctl doctor" lists them
(git.unpushed).

Retire a host:
  1. repoctl status           no unpushed publish; else "repoctl repo
                              push", or "repoctl clean --publish ID"
  2. repoctl doctor --only set   git.unpushed: push each commit
  3. repoctl check --remove-timer
  4. a file key on the host: delete it, or offboard it if it was the
     only copy (repoctl help signing)
  5. oras logout ghcr.io, and delete the token of the host
  6. delete the set directory and ~/.local/share/repoctl/SET
