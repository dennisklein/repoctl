Signing and trust

This chapter specifies how repoctl signs a publish and how the clients trust a key. It gives the client facts and the key model, then the trust chain, the gates, the release package and the life of a key.

  • Each admin signs with a personal key (OpenPGP v4, on a YubiKey or in a file). No key is shared.
  • Clients trust all team keys through one key file in the release package. Each RPM and each repomd.xml.asc has exactly one signature.
  • A signer probe asks for the PIN at the start of a publish. Gate 1: the signer is active and valid. Gate 2: a human confirmed the deployment of the key in keys/deployed.yaml. Gate 3: the key format.
  • Publish verifies each target in its EL mock chroot, with the EL rpm and dnf and only the keys that the clients have.
  • A normal publish never re-signs old RPMs. repoctl repo resign does it as its own publish.
  • Key states: active, retiring, removed, revoked. An expiring key is a key change, not a new expiry date.
  • A release package cannot remove a key from the clients. Config management does it, and repoctl prints the commands.

Options

Five options give a team its signing keys. The client facts decide between them.

A. One shared key, encrypted with sops

The team keeps the armored secret key in git as a sops file. sops encrypts a file to many recipients: age keys (also SSH keys and age plugins), PGP, cloud KMS and HashiCorp Vault transit. sops updatekeys or sops rotate adds or removes a human.

The decrypt path keeps the key off the disk:

  • repoctl makes a private GnuPG home in $XDG_RUNTIME_DIR/repoctl/g-<run> (mode 0700, a per-user tmpfs under systemd-logind). The path must be short: GnuPG fails when the socket path is too long.
  • It pipes sops decrypt into gpg --batch --import and signs with rpmsign --define "_gpg_path <dir>".
  • At the end, also on an error or SIGINT, it runs gpgconf --kill gpg-agent and deletes the directory.
  • sops exec-file --no-fifo is not usable: it writes a temporary file to /tmp.

The problems of this option:

  • Each member holds the full private key in clear text during each publish, and can copy it.
  • A new recipient list does not offboard a member: removed key owners can still have the old data key. The team must make a new signing key and re-sign all packages. Then it ships the new public key and removes the old key on each client (F12, F13, F16).

B. Personal keys, no sharing

Each admin has a personal signing key, on a YubiKey (OpenPGP card) where possible. The set lists all trusted public keys, and the release package ships all of them in one file. Each publish signs with the key of the human who runs it.

  • The .repo file stays stable: one gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-slurm line for all keys. The key file is not %config, so an update always replaces it (F18).
  • YubiKey: the PIN stays in the gpg-agent session. The touch policy of the signature slot is "cached" (15 s) or "off". With "on", each RPM needs one touch.
  • Algorithm: RSA 4096 is the safe default. The clients verify Ed25519 (F17); the test on EL9 is open.

Two rules follow from F12 and F13. Gate 2 and the offboarding order enforce them.

  1. Add a human before the first signature. A client reads a new key only from its installed release package. If a new key signs repomd.xml.asc first, the client cannot read the metadata, so it cannot get the new release package either. Thus an old key publishes the new release package, and config management deploys it. Only then can the new key sign.
  2. Remove a human in this order: re-sign, ship the new key file, remove the key on the clients. If the key goes first, packages with the old signature fail to install.

C. One primary key, personal signing subkeys

The primary key stays offline, for example on an encrypted USB stick in a safe. Each admin gets a signing subkey on a YubiKey. Clients see one key identity.

  • EL9 and EL10 verify the signatures of a signing subkey (F11).
  • Onboarding breaks clients. A new subkey changes the certificate, but rpm 4.16 and 4.19 ignore the import of a known primary key (F12). The dnf repository keyring also skips the known key ID (F13). Thus config management must erase both on each client, for each new admin.
  • Offboarding is not cheaper: a subkey revocation reaches a client only by the same erase and import.
  • A longer expiry of the primary key has the same problem on EL10, where rpm-sequoia does not trust an expired key (F6). The key hpc-repo expires on 2030-01-20.
  • gpg needs -u <subkey-fingerprint>! to use one exact subkey.

D. Several signatures on one artifact

  • RPM: EL9 rpm 4.16 keeps one signature (F3). An rpm 6 or EL10.1 signer can add v6 signatures with --rpmv6 (F4, F5). The client then needs each signer key, because NOKEY fails (F6). What EL9 does with the extra tag needs a test (F7).
  • repomd.xml.asc: EL9 accepts it when one signature is valid (F8). EL10 fails on the second packet (F9).

E. Central signer, no sharing

One key on one machine. Admins send signing requests to it. Clients see one key that does not change when the staff changes.

The choice: personal keys, many trusted keys, one signature per file

repoctl uses option B. Two different things have the name "many keys":

  • Many trusted keys on the clients: yes. The release package installs the public keys of all admins. dnf and rpm accept a file when its signer is one of these keys (F1, F2, F8, F14). Different RPMs in one repository can carry signatures of different admins.
  • Many signatures on one file: no. rpm 4.16 (EL9) keeps only one signature per RPM (F3). EL10 can store more, but then it needs all signer keys (F6). EL10 librepo refuses a repomd.xml.asc with more than one signature (F9).

What repoctl does:

  • Each admin makes an RSA 4096 key on a YubiKey, with the touch policy "cached" and an expiry of 3 years or less (help key). The key hpc-repo of the bash scripts (GSI HPC repo <hpc-repo@gsi.de>, …7C3A 19F2) stays trusted in state retiring until no RPM in latest carries it.
  • repoctl signs each new RPM with rpmsign --resign. It passes %_gpg_name (rpm 4) and %_openpgp_sign_id (rpm 6) as the full fingerprint. It never uses --addsign or --rpmv6, so the result is the same on rpm 4.16, 4.19 and 6.
  • repoctl writes repomd.xml.asc with one gpg --detach-sign --armor -u <FPR>!: exactly one signature packet (doctor sign.repomd).
  • Fingerprints are always full (40 hex characters) in the config, the output, the logs and the snapshot annotations. Short key IDs are for display only.
  • repoctl has no sops back end.
  • MCP never signs. The web UI signs only through repoctl publish, after the typed confirmation.

The set config lists the keys that the clients trust (sign.keys[], sign.release.keyfile, sign.checks: config.html#set-config). The user config key sign.key names the key of this human (config.html#user-config).

Client trust chain

A client installs a package only when two checks pass: dnf checks repomd.xml.asc (repo_gpgcheck=1), and rpm checks the RPM signature (gpgcheck=1). Both use the keys that the client got from the release package.

Client bootstrap

A new client has no key. The root files of each snapshot give <repo.url>/<target.path>/ a stable link to the newest release package and its key file (publish.html#format). Config management does the client bootstrap of a new client of target el9:

  1. Download https://repo.example.org/slurm-26.05/el9/RPM-GPG-KEY-slurm. Compare its sha256 with the pin. A different sum stops the client bootstrap, and nothing changes on the client.
  2. Import the file: rpm --import RPM-GPG-KEY-slurm.
  3. Download slurm-release.rpm from the same directory. Check it with rpmkeys --checksig slurm-release.rpm. Install it with dnf install ./slurm-release.rpm.
  4. Stop the management of the key file. The release package now owns the key file and the .repo file, and each update replaces them. Else config management puts the old key file back after each key change.

Rule: the pin

The pin is the sha256 of the key file in latest of the target: repoctl sign keyfile --target el9 --checksum prints it. It changes with each release that changes the key file. repoctl sign deployed prints the new pin of the target, and the human puts it into config management.

A client bootstrap with an old pin stops in step 1, so it fails safe. Test V33 checks the client bootstrap on EL9 and EL10 (delivery.html#verification).

A client that missed a release fails when a key of that release signs repomd.xml.asc: dnf cannot read the metadata (V13). The repair is a new client bootstrap with the current pin: the client gets the newest release and trusts the new key.

Signer probe

Step 1 of a publish (publish order) runs a signer probe. It signs a random 32-byte value with gpg --detach-sign -u <FPR>! and verifies it. Thus gpg-agent asks for the PIN or passphrase at the start, not in the middle of the sign step.

  • CLI: pinentry asks in the terminal or on the desktop. repoctl suspends the progress display for it.
  • Web UI: the UI is for the local user only, so pinentry shows on the local desktop. The browser never asks for a PIN. Step 1 of the publish page shows the probe state: card missing, waiting for the PIN on the desktop, touch your key, ready. When a signature takes more than 1 s, the UI shows "touch your key" over SSE (ui-publish.html#progress).

The preflight of publish also checks rpmsign, createrepo_c, gpg, the secret key of sign.key and a usable pinentry.

Rule: first publish

Gate 2 does not apply to a first publish of a target: no client uses the target yet. publish.html#first-publish gives the checks that prove it.

  • A served repoctl-snapshot.json of another set or target gives set.renamed (exit 12). A set name or a target id never changes (config rules).
  • A served repomd.xml gives publish.served-exists (exit 12). Clients can then exist: a bash-era repo that needs the import, or a changed store.oci.
  • An import is not a first publish, and gate 2 applies to it.

The summary then says "first publish of el10: no clients yet; the signer must be in the key file of this release". A key that a publish adds can never sign that publish.

Why a human confirms

Config management gives no feedback to repoctl. A published release package does not prove that the clients have it. Thus a human checks the clients and confirms the deployment (rule 1 of option B).

Rule: entries of the file

  • Each entry has key, target, the full fingerprint, release (the NVR with the dist tag), confirmedBy, at and an optional note. Gate 2 counts an entry only when its fingerprint equals the fingerprint of the key in sign.keys.
  • repoctl writes one entry per key and target, sorted by key, then by target. A new record replaces the old entry, and the git history keeps the old one.
  • Two entries for one key and target, for example after a git merge: the entry with the newest at wins. The next command that writes the file keeps only that entry.
  • A git conflict in the file: keep the entries of both sides and commit. A conflict in sign.keys of repoctl.yaml: keep the keys of both sides, run repoctl release write and commit.
  • repoctl schema deployments prints the JSON Schema of the file (contract.html#schemas).

A key is deployed for a command when gate 2 passes for each target in scope that has a latest. The scope is the selected targets of a publish, or the targets of the command. Thus repoctl sign ls shows hpc-repo as not deployed: el10 has a latest but no hpc-repo record. hpc-repo signs nothing new, because it is retiring.

Withdraw a record and repair missed clients

A human can confirm a deployment too early, before some clients have the release. When the key then signs a publish, these clients cannot read the metadata (V13). repoctl sign deployed ID --target T --withdraw removes the entry of the key and the target. Then gate 2 stops each publish of the key on that target.

The withdrawal is a shared-state command, as the record is: a dry run, the typed key id, no unattended mode and no MCP tool. Its set commit is "Withdraw deployment of ID on T". The web UI has no withdraw action. Without an entry, it stops with sign.not-deployed (exit 12).

The repair when the key signed files in latest of the target:

  1. Withdraw the record: repoctl sign deployed a.admin --target el9 --withdraw --note "3 clients of cluster B miss slurm-release-26.05-3". When latest holds files of the key, the hint gives the next step.
  2. An admin with another deployed key runs repoctl repo resign --signer a.admin --target el9. The new snapshot has no file of a.admin, so each client reads it again.
  3. Config management installs the release on the missed clients. A client that cannot read the repository gets a client bootstrap with the current pin.
  4. A human checks all clients again and records the deployment again: repoctl sign deployed a.admin --release slurm-release-26.05-3 --target el9.

When only a few clients missed the release, step 3 alone repairs them, and the record can stay.

Verify in the EL chroot

The signer host is always Fedora, with rpm 6 and rpm-sequoia. The clients use EL9 rpm 4.16 and EL10 rpm 4.19. Thus step 4 (verify on the host) can pass while a client fails. Step 5 (verify-el) checks each target with the client tools:

  1. repoctl mock update also makes one verify root per target (build.html#mock).
  2. Step 5 mounts the new tree and the key file read-only into that root (mock bind_mount plugin).
  3. Inside the root, repoctl imports the key file into a temporary rpmdb and runs rpmkeys --checksig on each RPM.
  4. Inside the root, repoctl runs dnf makecache on a temporary installroot. It uses the .repo file of the release in the client trust set. Each baseurl in it changes to the file:// URL of the new tree. Thus the librepo signature check runs with the gpgcheck, repo_gpgcheck and gpgkey lines of the clients.

Rule: client trust set

Step 5 uses the key file of the clients: of the release in the deployment record of the signer, or of a key file record. It does not use the key file of a release that this publish adds. A first publish uses the key file of this publish. The client trust set never holds a revoked key.

A failure gives verify.el-failed (exit 10), and repoctl keeps the tree. repoctl repo verify --el runs the same check on demand. The default key set of repo verify is the client trust set (repo verify).

Rule

repoctl re-signs an RPM only when both conditions are true. Its signature verifies with a key in sign.keys, at the time of the signature (after the expiry). Its sha256 is in the base snapshot, which has a valid repomd.xml.asc. RPMs of different admins stay side by side: a change of the human who publishes never re-signs old RPMs.

repoctl repo resign --signer ID is a publish run of kind resign, with the full publish order and gates 1 to 3 (checks per kind):

  • It gives a new signature to each RPM of the key ID, with the key of the human who runs the command.
  • The summary shows the count per target and per repository, debuginfo included, and the size of the new blobs. --repo splits the work.
  • When no RPM carries the key, it exits with 4.
  • A new signature changes the sha256 of the file. Thus resign writes new supply chain records for each build that it touches (supply-chain.html#layout).

repo restore also re-signs the RPMs of a removed or revoked key in the older snapshot (publish.html#restore). In the story, the publish of el9 keeps 170 RPMs: 120 of d.klein and 50 of the retiring key hpc-repo. It re-signs none.

Release package

The release package has one form: an in-tree package in the set repository, for example packages/slurm-release/, with role: release in repoctl.yaml. A set has at most one, and a package with branch cannot have the role (config.invalid, config rules).

  • The build identity of an in-tree package is the last set commit that changed its path, plus the target. repoctl builds it from a source clone of the set repository at that commit (source clone). A key change is a commit on that path, so the plan says build with the reason commit-changed (build.html#plan).
  • The spec has a plain Release and %changelog, because the rpmautospec plugin works only in a package repository. repoctl release write raises the Release by one and adds a %changelog entry each time it changes the key file or a .repo file. Thus rpm -q --changelog shows each key change, for example "Trust key a.admin C2F9…52A7".
  • repoctl release write local write writes the key file RPM-GPG-KEY-slurm from sign.keys: the keys in state active and retiring, sorted by id. It also writes the whole .repo file of each target. When a file changes, it raises the Release of the spec and adds a %changelog entry. The entry is the message of the sign command, else "Update the key file and the repo files". It does not commit. sign add, sign retire, sign activate, sign remove and sign revoke call it and commit the files with the key change. In a new set, the human runs it in step 3 of help new-set.

A stale key file stops publish with sign.keyfile-stale (exit 5). A .repo file that differs stops publish with sign.repofile-stale (exit 5). For both, the hint is repoctl release write, then commit. The doctor checks sign.keyfile, release.url, release.repo and release.version find the same (doctor checks).

In the story, the key file of slurm-release-26.05-1 holds hpc-repo, and slurm-release-26.05-2 adds d.klein. The set commit 7e21d0a adds a.admin, so the next build gives slurm-release-26.05-3.

Rule: the spec of the release package

  • repoctl defines the macro %repoctl_target (the target id) in each rpmspec and mock call of the package with role: release. The spec uses it to select its file: Source1: slurm-%{repoctl_target}.repo.
  • The spec installs that file as /etc/yum.repos.d/<repo.name>.repo and the key file as /etc/pki/rpm-gpg/<sign.release.keyfile>.
  • The spec marks the .repo file %config, not %config(noreplace) (F18). An update then replaces a file that a human changed, and rpm keeps the old file as .rpmsave. Thus a new repo.url or gpgkey= line reaches each client.

Do not change the .repo file on a client. For one dnf call, use dnf --enablerepo=slurm-source or --disablerepo=slurm. A change to the trust lines is a change of the set: edit repoctl.yaml, run repoctl release write and commit.

Key expiry

rpm does not update an imported key (F12). EL10 does not trust an expired key (F6). Thus a new expiry date does not reach the clients.

Rule

Treat an expiring key as a key change. Add a new key, deploy it, retire the old key, re-sign, and remove the old key (offboarding and rotation). Do not extend the expiry date of a key that clients already have.

Three checks read the expiry date of a key, each with its own id and limit. The limits are sign.checks.key_expiry_warn (default 180 days) and sign.checks.key_min_validity (default 30 days).

After the expiry

An RPM keeps its signature when the key expires. EL10 rpm then refuses the RPM (F6). EL9 rpm, the Fedora rpm of the signer host and the mirror job need the test V7 (delivery.html#verification). The design does not depend on its result:

Rule: a signature counts at the time it was made

repoctl checks an RPM signature in its own process, with the public key in keys/ID.asc, at the creation time of the signature. Thus host verify (step 4), repo pull, repo verify and the re-sign rule accept a signature that a key of sign.keys made before it expired. For each such RPM they give the warning sign.expired-signer.

verify-el uses the rpm of the target. Thus a publish of an EL10 target with such an RPM in the base stops with verify.el-failed (exit 10). The only way out is repoctl repo resign --signer ID, which replaces the signatures.

Thus re-sign the RPMs of a key before it expires.

repoctl sign ls lists the keys with state, deployment record, expiry and the count of RPMs per target in latest. repoctl sign keyfile --target ID --checksum prints the pin of the client bootstrap. The sections below give the other sign commands.

Rule: keep the entry of a removed or revoked key

A removed or revoked key stays in sign.keys, with its keys/ID.asc, while a snapshot in the registry holds a file that the key signed. repo pull, repo restore and repo verify need the key for these snapshots, and gc keeps some of them (publish.html#gc).

When repoctl repo snapshots --all lists no such snapshot, a human can delete both in one set commit. Then the id is free again.

Rule: each set that trusts the key

Each set has its own sign.keys, release package and mirror lines. Do the onboarding steps 1 to 4 in each set that the key must sign. A set that misses them fails safe: gate 2 stops a publish there, and its mirror lines keep the old tree.

Do the offboarding steps 2 to 5 in each set whose sign.keys has the fingerprint, and only then step 6. rpm -e gpg-pubkey-… removes the key for all repositories of a client. Thus a set that still has RPMs of the key breaks on that client. The doctor check sign.cross-set names each set whose keys differ.

The result kinds are SignerList and OnboardReport (contract.html#kinds). MCP has only the read tools repoctl_sign_ls, repoctl_sign_onboard, repoctl_sign_offboard and repoctl_sign_keyfile (agents.html#mcp-tools). The Signing page of the web UI shows the same keys, onboarding steps and offboarding steps (ui-publish.html#signing).

An organization owner adds the team membership as the last step. Until then, the new admin cannot push. An admin of the team pushes the same set commit of sign add, for example from a fork of the new admin. Offboarding removes the membership first.

A new admin host follows the steps of help team. The registry rules for the team are in publish.html#registry.

Offboarding and rotation

Offboarding removes the trust in one key. Its order protects the clients (rule 2 of option B): the key removal on the clients comes last.

  1. When the human leaves the team, an organization owner removes the human from the GitHub team. The human deletes the registry token. The team removal alone ends the write access to the set repository and the packages. The token has its access only through the team (publish.html#registry). Skip this step for a key without a team member (hpc-repo) and for a rotation.
  2. repoctl sign retire ID: state retiring, set commit. The key cannot sign any more. Another admin pushes the commit.
  3. repoctl repo resign --signer ID per target, by an admin with an active, deployed key. Each RPM of that key gets a new signature.
  4. repoctl sign remove ID. It refuses while latest of a target holds an RPM of that key. Then: state removed, a new key file without the key, set commit.
  5. Build and publish the new release package for each target. Config management rolls it out to the clients and to the keyring of each mirror line.
  6. Config management removes the key on each client. repoctl sign offboard ID checks the six offboarding steps and prints the commands for the clients. Then a human records it per target: repoctl sign removed ID --target T (removal record).
  7. The admin who leaves runs repoctl check --remove-timer on each of their hosts (check timer). sign offboard does not check this step, because the timers are on the hosts of that admin. The timers of the other admins still run.

Step 6 waits for steps 2 to 5 in each set that trusts the key (rule). An offboarding skips a retired target and a retired set. Their clients use another target or set, so their RPMs keep their signatures (end of a set).

In the story, hpc-repo is the next key to leave. It is in state retiring, and 50 RPMs in latest of el9 carry it; el10 has none. After steps 2 to 5, repoctl sign offboard hpc-repo prints the client commands:

Run on every client after "dnf upgrade slurm-release":
  EL9:    rpm -e gpg-pubkey-7c3a19f2
  EL10:   rpmkeys --erase 7c3a19f2      # EL10.1 and later; else use the EL9 line
  both:   rm -rf /var/cache/dnf/slurm*/pubring

A rotation is an onboarding of the new key, then an offboarding of the old key. An expiring key (key expiry) and a move to option E use the same rotation.

Removal record

As for a deployment, a human confirms the key removal of step 6. repoctl sign removed ID --target ID... [--note TEXT] [--dry-run] records that config management removed the key from all clients of each target. It is a shared-state command: the typed key id, a set commit, no unattended mode and no MCP tool.

The command checks that the key is in state removed and that the key file in latest of each target does not hold it. Else it stops with sign.not-removed (exit 12).

It writes one entry per key and target into the list removals of keys/deployed.yaml, with the rules of the file (deployment record). The fields are key, target, fingerprint, confirmedBy, at and an optional note.

The deployment entry of the key stays, because gate 1 refuses a removed key. Until the removal record exists, repoctl sign ls shows the key with "clients: unconfirmed" for that target, and sign offboard shows step 6 as open. After the record, sign ls shows "clients: removed", with the human and the date.

Emergency: a lost or a compromised key

Two failures do not fit the normal order. A compromised key must lose the trust of the clients at once, and a lost key can leave a target without a deployed signer. Both use a key file that config management installs without a release package, which needs a deployed signer and a publishable target.

The runbook Replace a compromised or lost key gives the steps for a human.

Key compromise

A key is compromised when another human can sign with it. Examples: a copied file key, a stolen card with a known PIN, a key on a host of an attacker. A lost card that another human can find counts as compromised. The normal offboarding order keeps the trust of the clients until step 6, so it does not apply.

The steps are in help emergency and in the runbook. The rules of the order:

  • Step 3 does not wait for a release package. repoctl sign offboard ID prints the client commands and the sha256 of the new key file. First on the HTTP server, then on each client, config management installs that key file with the pinned sum. It also erases the key and deletes the dnf repository keyring.
  • After step 3, the mirror job serves no snapshot with a file of the key, and the clients refuse these files.
  • Step 4: the team must know each publish that sign offboard lists. Compare the publish id, the user and the host with the team channel. Before the re-sign, restore (repoctl repo restore REF) the newest known snapshot over a publish that is not known.
  • Step 5: a human with another active, deployed key runs repoctl repo resign --signer ID for each target. The new snapshot has no file of the revoked key, so the mirror job serves it, and the clients work again.

When no other key is deployed, add the new key before step 3 (repoctl sign add NEW). Thus the key file of step 3 holds it. After step 3, record it with repoctl sign deployed NEW --keyfile SHA256 (recovery). Then NEW does step 5.

Rule: revoked key

A revoked key never signs again, and it never comes back. It is not in the key file or in the client trust set.

A normal publish refuses a base with a file that it signed (sign.removed-signer, exit 12). Only repo resign and repo restore replace these signatures. repo pull accepts them with the warning sign.removed-signer, so that a host can get the base of the re-sign.

For a revoked key, sign offboard also lists the snapshots in the registry with files of the key. A variant where a.admin is revoked (not the story):

$ repoctl sign offboard a.admin

  all:    install RPM-GPG-KEY-slurm with sha256 SUM (repoctl sign keyfile --checksum)
  EL9:    rpm -e gpg-pubkey-e93f52a7
  EL10:   rpmkeys --erase e93f52a7      # EL10.1 and later; else use the EL9 line
  both:   rm -rf /var/cache/dnf/slurm*/pubring

Recovery without a deployed signer

A key is lost when its secret key is gone, for example a broken card or a lost disk. Its signatures stay valid, and the clients still trust it. Retire it: sign retire needs no secret key. When another active key is deployed for each target with a latest, the rest is a normal rotation (offboarding and rotation).

When the lost key is the last deployed signer of a target, sign retire refuses (sign.last-signer). Then no key can sign a release package with a new key. A key file record deploys a new key NEW without a release package (help emergency gives the steps):

  • repoctl sign add NEW --fingerprint FPR adds NEW. Push the set commit.
  • repoctl sign keyfile --checksum prints the sha256 of the new key file.
  • Config management installs the key file with this pinned sum on all clients and the HTTP server of each target, as for a client bootstrap.
  • repoctl sign deployed NEW --keyfile SHA256 --target ID for each target records it. Push each set commit. Now NEW passes gate 2.
  • Then retire the lost key, re-sign its RPMs with NEW, remove it and publish the new release package.

Rule: two deployed signers

Keep two active keys or more with a deployment record for each target. Then a lost key is a normal rotation, and sign.last-signer never stops a retire.

  5. repoctl repo resign --signer ID --target T   (another deployed key)
  6. Publish the release package with the next publish.

A key is lost (card broken, all PINs blocked, file key deleted):
  repoctl sign retire ID, then the normal rotation (help signing).
  The last deployed signer is lost:
    repoctl sign add NEW --fingerprint FPR; push
    repoctl sign keyfile --checksum; config management installs it
    repoctl sign deployed NEW --keyfile SHA256 --target T; push

Keep two deployed keys for each target.

repoctl help team

TEAM

Add a second admin host:
  1. dnf install repoctl-release, check the key fingerprint, then
     dnf install repoctl; the steps are in
     https://dennisklein.github.io/repoctl/manual/install.html#first-install
  2. git clone the set repository (branch set/SET); cd into it
  3. repoctl doctor           a missing secret key is a warning here
  4. repoctl checkout         the worktrees of the lock
  5. repoctl repo pull        the local copy of latest from the registry
  6. repoctl mock update      the mock chroots and the verify roots
  7. repoctl check --install-timer   the daily check of the set
  8. repoctl status           shows what differs from latest
To publish, the new admin needs:
  - a key (repoctl help key) and sign.key in the user config
    (repoctl config show)
  - a registry login with write:packages (repoctl doctor:
    registry.login, registry.write)
Each admin works as an own user and/or on an own host. The state of
a host is not shared. The registry and git are shared. Two admins
coordinate in the team channel; repoctl does not lock between hosts.
If latest moved, publish stops with state.behind (exit 13): run
"repoctl repo pull". If another admin pushed a change of
repoctl.yaml or keys/, publish stops with sign.trust-behind
(exit 13): run "git pull --ff-only".

Stand in for an admin who is away:
  1. git pull; repoctl checkout; repoctl repo pull
  2. repoctl status         "in flight" counts the pinned nodes that
                            latest does not hold, and how many build here
  3. repoctl plan; repoctl build
                            the staging of the other admin is not on this
                            host, so these nodes build again here
  4. repoctl sign ls        publish only the targets where your key has
                            a deployment record (gate 2)
  5. repoctl publish --target TARGET
                            for a failed node that is not urgent, see
                            "repoctl help urgent"

Push each set commit (sign add, sign deployed, the lock after pin)
and each commit of an external clone at once. A lost host loses
each commit that is not pushed. "repoctl doctor" lists them
(git.unpushed).

Retire a host:
  1. repoctl status           no unpushed publish; else "repoctl repo
                              push", or "repoctl clean --publish ID"
  2. repoctl doctor --only set   git.unpushed: push each commit
  3. repoctl check --remove-timer
  4. a file key on the host: delete it, or offboard it if it was the
     only copy (repoctl help signing)
  5. oras logout ghcr.io, and delete the token of the host
  6. delete the set directory and ~/.local/share/repoctl/SET
