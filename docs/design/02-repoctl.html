repoctl: design

Design record. Later documents change parts of this one. 03-build-state.html section 9 lists the changes. Index: index.html.

Updated 2026-11-03. Sections 3.2 to 3.5, 4, 5 and 6 follow 03, 05 and 06: the build identity is the package commit plus the target (no node key, no node cache), GHCR is the authority and the HTTP server is a mirror (store.oci, repo.url; no publish path), the release package is in the set tree, and advisories replace automatic rebuilds. 1. Summary

  • Name: repoctl. Binary, RPM and Go module use this name.
  • Unit of work: a "package set". One repoctl.yaml describes one set: its packages, its build targets, its output repos. builder/slurm-26.05 is one set. Other sets (for example Lustre or Apptainer) use the same tool with a different file.
  • Three config files. repoctl.yaml (what to build, committed), repoctl.lock (pinned commits, written by the tool), and a user file in $XDG_CONFIG_HOME (how to build on this machine).
  • XDG directories hold all temporary and generated files. The set directory holds only committed files and the package worktrees. Clones of external package repositories are in the data directory.
  • GHCR is the authority. A publish makes a snapshot in an OCI registry (store.oci). The HTTP server that clients use (repo.url) is a mirror that a separate job fills. The set has no publish path.
  • LLM skills: logic ships with repoctl, data ships with the set. Generic skills are versioned with the CLI that they call. Package facts (upstream repo, tag filter, notes) go into repoctl.yaml. A set can add its own skills for local policy. See section 6.

3. Configuration

3.1 Layers and precedence

3.2 Set config: repoctl.yaml

repoctl finds this file the same way git finds .git: it goes up from the current directory. -C <dir> sets another start directory. Example for builder/slurm-26.05:

apiVersion: repoctl/v1alpha1
name: slurm-26.05                  # set id, used in XDG paths

repo:
  name: slurm                      # gives slurm, slurm-source, slurm-debuginfo
  debuginfo: true
  source: true
  url: https://repo.example.org/slurm-26.05   # what clients use (the mirror); needed to publish

store:
  oci: ghcr.io/gsi-hpc/slurm-repo  # registry path; one package - per target

sign:                              # trusted keys; "repoctl sign add" fills this
  keys:
    - {id: d.klein, file: keys/d.klein.asc, state: active}
  release: {keyfile: RPM-GPG-KEY-slurm}
  checks: {key_min_validity: 30d}

retention:
  snapshots: {keep: 10, keep_days: 90d}

targets:                           # 1..n; each target is one mock chroot
  - id: el9
    mock: rocky+epel-9-x86_64
    plugins: [rpmautospec]         # required: a rebuild commit needs it
    macros: [rpm/macros]
    path: el9                      # path below repo.url
  - id: el10
    mock: rocky+epel-10-x86_64
    plugins: [rpmautospec]
    macros: [rpm/macros]
    path: el10
    repos:                         # extra RPM repos for build deps (mock --addrepo)
      - https://repo.example.org/el10/extra

defaults:
  git:
    remote: origin                 # package branches are in this repo

packages:
  - dir: munge
    branch: munge/slurm-26.05
    upstream: {github: dun/munge, fedora: munge}
  - dir: ucx
    branch: ucx/slurm-26.05
    upstream: {github: openucx/ucx, fedora: ucx}
  - dir: pmix
    branch: pmix/slurm-26.05
    upstream: {github: openpmix/openpmix, tags: '^v6', fedora: pmix}
  - dir: pmix_v4
    branch: pmix/slurm-26.05-v4
    upstream: {github: openpmix/openpmix, tags: '^v4'}
    notes: Upstream 4.x is frozen at 4.2.9.
  - dir: rocm-smi
    git: {url: https://git.gsi.de/SDE/packages/rocm-smi.git}  # external repo (example)
    branch: slurm-26.05
    targets: [el9]                 # build only for these targets
    upstream: {github: ROCm/rocm-systems, tags: '^therock-[0-9]'}
    notes: Follow the TheRock stream. rocm-X.Y.Z is frozen at 7.2.4.
  - dir: slurm
    branch: slurm/slurm-26.05
    upstream: {github: SchedMD/slurm, tags: '^slurm-', fedora: slurm}
  # ... prrte, pmix_v5, openmpi, slurm-singularity-exec
  - dir: slurm-release
    path: packages/slurm-release   # in the set tree, no branch; %autorelease in its spec
    role: release                  # key file and .repo come from "repoctl release write"

skills: [.claude/skills]           # optional set-local skills, section 6

Rules:

  • An unknown key is an error. apiVersion lets the schema change later without silent errors.
  • No build order in the file. repoctl makes the graph from rpmspec --buildrequires and the Provides of each package.
  • No secrets and no host paths in the file. The file has no publish path and no registry credentials. Credentials come from the container credential store of the user.
  • superseded publish: {path: …} and the publish backends (rsync, GitHub Pages). store.oci and repo.url replace them. A mirror job on the HTTP server pulls latest and serves it.
  • Every target has plugins: [rpmautospec]. Without it a rebuild commit gives no new NVR (config.invalid).
  • repoctl schema prints a JSON Schema. Editors and agents use it to check the file.

3.3 Lock: repoctl.lock

# Written by repoctl pin. Do not edit.
apiVersion: repoctl/v1alpha1
packages:
  munge:   {branch: munge/slurm-26.05,  commit: 3a244fd4728f94342beba4a7634c463370a7b877}
  pmix_v4: {branch: pmix/slurm-26.05-v4, commit: 75255956ca468de54df4cbda1e9a455f6cd81534}
  slurm:   {branch: slurm/slurm-26.05,  commit: d42f66a56a3f3f0f788e79fb723e451da2d67ba7}
  rocm-smi:
    url: https://git.gsi.de/SDE/packages/rocm-smi.git
    branch: slurm-26.05
    commit: cae3663bc5c9f97abb8e49c8adebfc4bedde98a0

The lock is a separate file, like go.sum. A version bump changes one line in the lock and nothing in repoctl.yaml. repoctl migrate converts packages.lock once. A package in repoctl.yaml without a lock line is unpinned. A lock line without a package is orphaned. A missing lock file counts as an empty lock.

3.4 User config

# $XDG_CONFIG_HOME/repoctl/config.yaml
jobs: 4
sign:
  key: d.klein@gsi.de              # your personal key: user id or fingerprint
                                   # else: rpm --eval %{_gpg_name}

The user config holds values that belong to one person or one host: the job count, the signing key, the agent command. superseded sets.<set>.publish.path: a set has no publish path. sign.gpg_name stays as an alias of sign.key. Each admin has a personal key, and the set config lists the keys that clients trust (sign.keys).

3.5 Many targets and external package repos (v1)

  • Node = package × target. repoctl builds each package for each target in its targets: list (default: all targets). The build identity of a node is the package commit plus the target. There is no node key (03).
  • One graph per target. repoctl builds the SRPM in the mock chroot of the target and reads its requires. Thus, %if 0%{?rhel} >= 10 in a spec gives correct edges. Dynamic BuildRequires (%generate_buildrequires) are not seen before the build. repoctl logs a warning for them.
  • Missing dependency for a target. If slurm@el10 requires rocm-smi, but rocm-smi is el9 only, the plan shows the gap before the build: "slurm@el10 needs rocm-smi-devel; rocm-smi is not built for el10".
  • Staging and publish per target. Each target has its own staging repo and its own OCI package (<set>-el9, <set>-el10). A run can build all targets. A publish takes the plan and covers the targets that are ready. A failed el10 node does not stop el9.
  • Extra RPM repos per target (targets[].repos) go to mock as --addrepo. A change in these repos can change a build result. repoctl does not rebuild by itself. It shows an advisory (buildroot.drift), and the person decides.
  • External package repos. git.url on a package (or in defaults.git) points to any git server. repoctl keeps one bare clone per URL with full history in the data directory, because rpmautospec needs it. checkout fetches the clone and makes the worktree. The lock stores URL, branch and commit.
  • Credentials come from the user's git and ssh setup. The config never holds them. repoctl doctor checks that each external URL is reachable.

4. XDG directories

  • Only the cache is safe to delete. repoctl clean --cache deletes it. The next build is slower, not different. The data directory holds staged nodes, clones of external packages and the local copy of latest. repoctl clean keeps staged nodes.
  • superseded Shared node cache with a node key (hash of commit, target, macros and dependency keys). There is no node key and no node cache. What is built is decided by the manifest of latest and by the staged nodes of the set (03).
  • The registry decides what is published. No file on this host does. published.yaml is superseded by the annotations of latest.
  • State is kept. Journals feed repoctl logs, the web UI and the agent. repoctl config paths prints the paths of this set with their sizes.
  • Defaults follow the XDG spec when a variable is not set: ~/.config, ~/.cache, ~/.local/state, ~/.local/share.

Test for "generic". The main branch gets its own repoctl.yaml: set repoctl, target current Fedora, packages repoctl and repoctl-release. The v1 form of the test is: repoctl builds and publishes this set from a Fedora host with a personal key. The snapshot goes to GHCR, and the mirror job puts the repo on GitHub Pages. That repo is also the install source of repoctl for the build hosts (Fedora only, or the release RPMs). A CI job that signs without a person is a later feature. The release-version check of publish has a version only for sets whose name has one. For this set it is off. If mock in a privileged container in CI is a problem, CI can use plain rpmbuild for the check.

6. Where the LLM skills live

6.1 Decision

Skill logic ships with repoctl. Package facts ship with the set config. A set can add local skills for local policy only.

6.2 Why

QuestionShips with repoctlShips with set config
Skill calls repoctl … --json. Who keeps skill and CLI in step?Same commit, same version. No drift.Each set must update its skills when the CLI changes. Drift is likely.
A fix to a skillOne release reaches all sets.Must go to each builder branch (problem P6 again).
Package facts (filters, upstream repo)Wrong place. The skill would know about slurm.Right place. In repoctl.yaml the deterministic CLI can use them too.
Local rules (who may publish, rollout order)Wrong place.Right place, as an optional set-local skill.
Skill works without an agent?The facts in repoctl.yaml work without an agent: repoctl upstream gives the same table as the skill, without the release-note summary.

6.3 Today's skills after the change

TodayAfter
package-info (bash script + skill)The script becomes repoctl upstream [dir] --json. The skill is not necessary any more.
list-package-updatesGeneric skill package-updates in repoctl. It calls repoctl upstream --json, reads release notes, writes the table.
(new) bump-package, triage-build, rebuild-checkGeneric skills in repoctl. bump-package has two modes: draft (a diff and a message, no commit; the UI button) and apply (commits on a package branch; the terminal). rebuild-check answers "is a rebuild necessary?" for an advisory. Tool lists per task are in 04, C.7.
(new) repoctlGeneric skill: how to use the CLI, the config schema and the safety rules (never call mock or rpmsign directly, never run publish, repo push or any other shared-state command without the person's OK). The MCP server has a read-only mode (--tools read) for the UI agent.
