Core model

This chapter gives the mental model of repoctl. It defines the words that all other chapters use, and it shows how one change goes from a commit to the clients. Read it first.

  • A set is one repoctl.yaml on one builder branch. It builds one repository per target.
  • A node is one package on one target, written DIR@TARGET. Its build identity is the package commit plus the target.
  • The published repo is the build state. Each target repo carries a signed RepoManifest. Only commits that are not in it build.
  • A rebuild is an empty commit. rpmautospec raises the release, so every build has a new NVR.
  • repoctl does not rebuild dependents by itself. Advisories suggest a step, and the human decides.
  • The GHCR tag latest is the only authority for what is published. All other records are copies.
  • Each command has a safety class. Only a human changes shared state.
  • The CLI, the web UI, the MCP server and the skills share one core and one set of words.

The story in the examples

Dennis Klein (Unix user dklein, key d.klein) works on the Fedora host hpc-a1 in ~/src/slurm-repo. On 2026-11-02 he bumps ucx from 1.22.0 to 1.22.1 and adds rebuild commits for slurm, openmpi and slurm-singularity-exec. Run r-20261102-1750-a3f builds 8 nodes: 6 are ok, slurm@el10 fails and slurm-singularity-exec@el10 is blocked. On 2026-11-03 he publishes el9 as p-20261103-1412-5e1.

Package set

A set (package set) is a group of packages that repoctl builds and publishes together. One repoctl.yaml describes one set: its packages, its targets and its output repositories (config.html#set-config). The set name is in all local paths and in the OCI package names. The story set is slurm-26.05.

Each set lives on one builder branch, builder/<set>. The branch holds only data: repoctl.yaml and repoctl.lock, the macro files, the in-tree release package packages/slurm-release, keys/ with the public keys and the deployment records, .repoctl/advisories.yaml with the dismissals, and CLAUDE.md.

The set directory is a git work tree of the builder branch, for example /home/dklein/src/slurm-repo. repoctl checks out each package as a git worktree in packages/<dir>, which git ignores.

A package is one dir entry in repoctl.yaml. Its source is a package branch <pkg>/<set>[-<variant>] of the same repository (pmix/slurm-26.05-v4), a branch of an external git repository (rocm-smi on git.gsi.de), or an in-tree path (packages/slurm-release).

The set slurm-26.05 has 11 packages. Other sets use the same tool with their own file, for example slurm-25.11 in ~/src/slurm-repo-25.11. A new set forks its branches from the previous set (lifecycle.html#new-set).

Targets

A target is one build platform: one mock chroot with one architecture. The set slurm-26.05 has two targets: el9 (rocky+epel-9-x86_64) and el10 (rocky+epel-10-x86_64).

repoctl keeps the targets apart. Each target has its own build graph, its own staging repo in each run, its own OCI package (…/slurm-26.05-el9) with its own latest and RepoManifest, and its own client path below repo.url.

A run can build all targets. A publish covers the targets that are ready. In the story, slurm@el10 fails, so el9 publishes and el10 waits. The configuration chapter has the keys (config.html#targets).

Nodes

A node is one package on one target. Its id is DIR@TARGET, for example slurm@el10. repoctl builds each package for each target in its targets list. The default is all targets.

slurm@el10 requires rocm-smi-devel, but rocm-smi is not built for el10. plan shows this gap before the build as the warning dep.not-for-target (build.html#graph).

All surfaces use these words with one meaning. The build chapter gives the transitions (build.html#states).

There is no queued run (humans and hosts). The story run ends failed after 41m07s with exit 3.

Build identity

The build identity of a node is the package commit plus the target. repoctl builds each identity once. rpmautospec computes the release from the git history. Thus one commit gives one NVR, and each new commit gives a new release.

The mock config, the macros, the extra repos and the builds of the dependencies are not part of the identity. A change there gives an advisory, for example mock.drift, buildroot.drift or soname.removed. The human decides whether a rebuild is necessary.

Why the commit is the identity

A hash over the commit, the configs and the hashes of all dependencies rebuilds every dependent after each change. It can also give a second build with the same NVR and other content, and clients do not update to it. With the commit as identity, every build has its own NVR, and the git history explains each one. repoctl trusts the ABI promise of upstream, as the bash scripts do. The soname check after each build tells when this trust fails.

For an in-tree package, the commit is the last set commit that changes its path. For an external package, the lock records the URL, the branch and the commit (config.html#lock). repoctl has no build cache of its own: the published repo and the unpublished staging hold all builds.

The repo is the build state

repoctl keeps no build database. The published repo of each target is the build state. Its RepoManifest lists the commit of each published build. plan compares the lock with this manifest, and a publish writes a new manifest. Thus the next plan sees the new state.

Every admin host reads the same state. repoctl repo pull makes the local copy equal to latest, so a second admin plans from the same manifest. A lost host loses only its runs and its staging (records).

RepoManifest

Each target repo carries one RepoManifest. repoctl adds it to the repodata of the binary repository (slurm/) with modifyrepo_c --mdtype=repoctl. repomd.xml lists it with its checksum, and repomd.xml.asc signs it. Thus clients and admins can trust the manifest as much as the RPMs. The manifest also lists the sha256 of each supply chain record, so the same signature covers the records (supply-chain.html#verify).

The manifest has one entry per build. An entry lists the source RPM, the binary RPMs and the debuginfo RPMs of one node build. Thus slurm-source and slurm-debuginfo need no manifest. A rebuild is a commit

repoctl rebuild DIR... --reason TEXT adds an empty commit Rebuild: TEXT to each package branch and pins it. rpmautospec raises the release for this commit, as it does for Fedora mass rebuilds. Thus every build has a new NVR. repoctl never pushes. The hint gives the push command.

In the story, Dennis runs repoctl rebuild slurm openmpi slurm-singularity-exec --reason "ucx 1.22.1" after the ucx bump. The new NVRs are slurm 26.05.4-2, openmpi 5.0.11-2 and slurm-singularity-exec 3.2.0-2. The soname check of ucx then says "sonames unchanged: rebuild not necessary", because libucp.so.0 stays. The rebuilds are his choice, not a need.

A rebuild is always a decision of the human. repoctl never makes a rebuild commit by itself. The command is in cli.html#cmd-rebuild, and the rules are in build.html#rebuild.

Advisories

An advisory is the result of a deterministic check. It tells the human that a rebuild or another step can be necessary. It suggests a step, and the human decides. The id is CODE/SUBJECT, for example closure.broken/pmix@el9. repoctl computes advisories in plan, after each node build and in repoctl check, which a daily timer runs on each admin host.

A required advisory blocks only a publish that changes a package in its closure. --accept-advisory ID --reason TEXT overrides it for one publish. A dismissal hides an info or warn advisory for the team. In the story, the check of 2026-11-02 06:00 finds closure.broken/pmix@el9: pmix-6.1.0-1.el9 needs libhwloc.so.15, and EPEL 9 now gives only libhwloc.so.16. The el9 publish does not change pmix, so the advisory does not block it. The advisories chapter has the codes, the states and the gate (advisories.html#codes, advisories.html#gate).

Snapshots

A publish makes a snapshot: one OCI artifact that holds all files of one set and target, with one blob per file. GHCR stores it in the OCI package of the target with the tag latest and the tag of its publish id. A mirror job on the HTTP server pulls latest, verifies it with the client keys and serves it at repo.url. A publish adds. All old versions stay, and a prune is explicit. A restore makes a new snapshot, so latest moves forward. In the story, p-20261103-1412-5e1 adds 38 new RPMs to the 170 RPMs of its base p-20260912-1403-c21. The publish chapter specifies the order, the format and the commands (publish.html#order, publish.html#format).

No file on an admin host says what is published. After a lost host, repoctl repo pull gives back the local copy. The runs, journals and staged nodes of the lost host are lost. They are personal, and nothing depends on them. The freshness check is in publish.html#freshness.

Humans and hosts

  • Fedora only. repoctl runs on Fedora. The mock chroots are EL9 and EL10. Admins install repoctl from the Fedora repo on GitHub Pages or from the release RPMs (decision.html#home).
  • Own user, own host, own key. Each admin builds as an own Unix user and/or on an own host, and signs with a personal key. Dennis Klein is dklein on hpc-a1 with key d.klein. A. Admin uses hpc-a2 with key a.admin.
  • No build queue. One user on one host runs one build per set at a time. A second build stops at once with exit 7 (set.busy) and names the running run. The set lock does this (build.html#lock).
  • No lease between admins. Two admins have two set locks on two hosts. Publish compares latest with its base in step 1 and again just before the tag moves (publish.html#admins). The team coordinates in its own channel.
  • Local web UI. The web UI is for the local user only. It has no remote access (ui.html#auth).
  • Clients never talk to repoctl. They read the served tree over HTTP with dnf, and they trust the keys of the release package.

Safety classes

Each command has one safety class. The class says what the command can change, and it sets the rules. The CLI, the web UI and MCP apply the same rules. The command tree gives the class of each command (cli.html#tree).

Rule

Every shared-state command shows a summary and has a dry run. A human confirms in a terminal or in the web UI. The human types the set name. For a trust change, the human also types each added key id. sign deployed asks for the key id. The command takes the set lock, writes a journal and has no MCP tool. The full rules are in cli.html#safety. The variable for unattended jobs is in config.html#env.
