Core model

This chapter gives the mental model of repoctl. It defines the words that all other chapters use, and it shows how one change goes from a commit to the clients. Read it first.

  • A set is one repoctl.yaml on one builder branch. It builds one repository per target.
  • A node is one package on one target, written DIR@TARGET. Its build identity is the package commit plus the target.
  • The published repo is the build state. Each target repo carries a signed RepoManifest. Only commits that are not in it build.
  • A rebuild is an empty commit. rpmautospec raises the release, so every build has a new NVR.
  • repoctl does not rebuild dependents by itself. Advisories suggest a step, and the human decides.
  • The GHCR tag latest is the only authority for what is published. All other records are copies.
  • Each command has a safety class. Only a human changes shared state.

The story in the examples

Dennis Klein (Unix user dklein, key d.klein) works on the Fedora host hpc-a1 in ~/src/slurm-repo. On 2026-11-02 he bumps ucx from 1.22.0 to 1.22.1 and adds rebuild commits for slurm, openmpi and slurm-singularity-exec. Run r-20261102-1750-a3f builds 8 nodes: 6 are ok, slurm@el10 fails and slurm-singularity-exec@el10 is blocked. On 2026-11-03 he publishes el9 as p-20261103-1412-5e1.

Package set

A set (package set) is a group of packages that repoctl builds and publishes together. One repoctl.yaml describes one set: its packages, its targets and its output repositories (config.html#set-config). The set name is in all local paths and in the OCI package names.

The story set slurm-26.05 has 11 packages. Other sets use the same tool with their own file, for example slurm-25.11 in ~/src/slurm-repo-25.11. A new set forks its branches from the previous set (lifecycle.html#new-set).

Each set lives on one builder branch, builder/<set>. The branch holds only data:

  • repoctl.yaml, repoctl.lock and the macro files;
  • the in-tree release package packages/slurm-release;
  • keys/ with the public keys and the deployment records;
  • .repoctl/advisories.yaml with the dismissals;
  • CLAUDE.md.

The set directory is a git work tree of the builder branch, for example /home/dklein/src/slurm-repo. repoctl checks out each package as a git worktree in packages/<dir>, which git ignores.

A package is one dir entry in repoctl.yaml. Its source is one of these:

  • a package branch <pkg>/<set>[-<variant>] of the same repository, for example pmix/slurm-26.05-v4;
  • a branch of an external git repository, for example rocm-smi on git.gsi.de;
  • an in-tree path, for example packages/slurm-release.

Targets

A target is one build platform: one mock chroot with one architecture. The set slurm-26.05 has two targets: el9 (rocky+epel-9-x86_64) and el10 (rocky+epel-10-x86_64). The keys are in config.html#targets.

repoctl keeps the targets apart. The OCI package of a target (…/slurm-26.05-el9) has its own latest and RepoManifest. A run can build all targets. A publish covers the targets that are ready.

Nodes

A node is one package on one target. Its id is DIR@TARGET, for example slurm@el10. repoctl builds each package for each target in its targets list. The default is all targets.

slurm@el10 requires rocm-smi-devel, but rocm-smi is not built for el10. plan shows this gap before the build as the warning dep.not-for-target (build.html#graph).

There is no queued run (humans and hosts). The story run ends failed after 41m07s with exit 3.

Build identity

The build identity of a node is the package commit plus the target. repoctl builds each identity once. rpmautospec computes the release from the git history. Thus one commit gives one NVR, and each new commit gives a new release.

For an in-tree package, the commit is the last set commit that changes its path. For an external package, the lock records the URL, the branch and the commit (config.html#lock). repoctl has no build cache of its own: the published repo and the unpublished staging hold all builds.

The mock config, the macros, the extra repos and the builds of the dependencies are not part of the identity. A change there gives an advisory, for example mock.drift, buildroot.drift or soname.removed, and no build (what starts a build). The human decides whether a rebuild is necessary.

Why the commit is the identity

A hash over the commit, the configs and the hashes of all dependencies rebuilds every dependent after each change. It can also give a second build with the same NVR and other content, and clients do not update to it.

With the commit as identity, every build has its own NVR, and the git history explains each one. repoctl trusts the ABI promise of upstream, as the bash scripts do. The soname check after each build tells when this trust fails.

The repo is the build state

repoctl keeps no build database. The published repo of each target is the build state: its RepoManifest lists the commit of each published build. plan compares the lock with this manifest. A publish writes a new manifest, so the next plan sees the new state.

Every admin host reads the same state. repoctl repo pull makes the local copy equal to latest, so a second admin plans from the same manifest (records).

RepoManifest

Each target repo carries one RepoManifest in the repodata of its binary repository (slurm/). repoctl adds it with modifyrepo_c --mdtype=repoctl. repomd.xml lists it with its checksum, and repomd.xml.asc signs it. Thus clients and admins can trust the manifest as much as the RPMs.

The manifest has one entry per node build, with its source RPM, binary RPMs and debuginfo RPMs. Thus slurm-source and slurm-debuginfo need no manifest. The manifest also lists the sha256 of each supply chain record, so the same signature covers the records (supply-chain.html#verify).

Rule: the match key

The match key of an entry is the commit, the target and the source package name (the Name of the SRPM). plan finds the build of a node by this key.

  • The name tells apart two in-tree packages with the same set commit.
  • For the reason commit-changed, plan compares with the newest entry of the same dir, else of the same source package name.
  • dir, branch and url are information only. Thus a rename of a dir or a branch, and a move of the history to another git server, keep the node current.

The lists change in this way:

  • A publish keeps the entries of its base and adds its own. Thus the entry of ucx 1.22.0-2 stays.
  • builds[] grows with each publish and gets smaller with a prune or a restore.
  • removed[] and history[] only grow. Each snapshot copies them from its base and adds its own history[] entry. Thus plan and publish know every NVR that clients can still have.
  • gc deletes snapshots, but latest keeps history[]. Thus history[] is the audit record of the target (publish.html#format).
  • repoctl repo ls --removed lists removed[].
  • A set lives for one Slurm release series and gets some publishes per month, so the manifest stays small. V25 measures it with the records (delivery.html#verification).

repoctl reads the RepoManifest of a snapshot in plan, build, publish, repo pull and the repo commands. It validates the manifest against the schema manifest (repoctl schema manifest). A publish reads the manifest of its base and writes the new manifest in the apiVersion of repoctl.yaml (stored files).

CaseResult
The manifest does not agree with the schema.The command stops with manifest.invalid (exit 1).
This binary does not read the apiVersion of the manifest.The command stops with contract.newer-file (exit 1). The hint is to update repoctl.

A rebuild is a commit

repoctl rebuild DIR... --reason TEXT adds an empty commit Rebuild: TEXT to each package branch and pins it. rpmautospec raises the release for this commit, as it does for Fedora mass rebuilds. Thus every build has a new NVR.

A rebuild is always a decision of the human. repoctl never makes a rebuild commit by itself. The rules are in build.html#rebuild.

In the story, Dennis runs repoctl rebuild slurm openmpi slurm-singularity-exec --reason "ucx 1.22.1" after the ucx bump. The new NVRs are slurm 26.05.4-2, openmpi 5.0.11-2 and slurm-singularity-exec 3.2.0-2. The soname check of ucx then says "sonames unchanged: rebuild not necessary", because libucp.so.0 stays. The rebuilds are his choice, not a need.

Advisories

An advisory is the result of a deterministic check in plan, after each node build or in repoctl check. It suggests a step, for example a rebuild, and the human decides. A required advisory blocks only a publish that changes a package in its closure (advisories.html#codes, advisories.html#gate).

Snapshots

A publish makes a snapshot: one OCI artifact that holds all files of one set and target. GHCR tags it latest and with its publish id, and a mirror job serves latest at repo.url. A publish only adds, and a prune or a restore makes a new snapshot, so latest moves forward (publish.html#order, publish.html#format).

No file on an admin host says what is published. After a lost host, repoctl repo pull gives back the local copy. The runs, journals and staged nodes of the lost host are lost, but nothing depends on them. The freshness check is in publish.html#freshness.

Rule: push the commits at once

A set commit holds a team record. A lost host loses each of these commits that is not on its remote:

  • the commits of the sign commands, for example sign add and sign deployed;
  • the commits of the human: repoctl.lock after pin, .repoctl/advisories.yaml after a dismiss;
  • the commits of an external package, in its bare clone on the host.

Thus push each commit at once. The set check git.unpushed of repoctl doctor lists each commit that is not pushed. The runbook Lost admin host gives the steps after a loss.

Humans and hosts

  • Fedora only. repoctl runs on Fedora. The mock chroots are EL9 and EL10. Admins install repoctl from the Fedora repo on GitHub Pages or from the release RPMs (tool.html#pages).
  • Own user, own host, own key. Each admin builds as an own Unix user and/or on an own host, and signs with a personal key. Dennis Klein is dklein on hpc-a1 with key d.klein. A. Admin uses hpc-a2 with key a.admin.
  • No build queue. One user on one host runs one build per set at a time. A second build stops at once with exit 7 (set.busy) and names the running run. The set lock does this (build.html#lock).
  • No lease between admins. Two admins have two set locks on two hosts. Publish compares latest with its base in step 1 and again just before the tag moves (publish.html#admins). The team coordinates in its own channel.
  • Local web UI. The web UI is for the local user only. It has no remote access (ui.html#auth).
  • Clients never talk to repoctl. They read the served tree over HTTP with dnf, and they trust the keys of the release package.
