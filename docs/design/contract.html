Machine contract

This chapter specifies what programs read from repoctl: the JSON envelope of every --json result, the shared names and enums, the kinds and their schemas, the problem codes and the run journal. The CLI, the web UI, the MCP server and the skills encode the same Go types from one package, internal/api. Thus all surfaces give the same data.

  • Every --json result is one envelope: apiVersion, kind, metadata, items[], warnings[], errors[]. The MCP server returns the same envelope as structuredContent.
  • One version string, repoctl/v1alpha1, covers the JSON output, the MCP results and the set files. The journal has its own integer version v.
  • A stored file takes only additions within one apiVersion. A binary never rewrites a file with a field that it does not know.
  • Programs match on codes and enum values. Text fields are for humans.
  • A problem code names the cause. The exit code names the class of the result.
  • A run writes two JSON Lines files: the journal runs/<run>.jsonl and the go-clikit progress log runs/<run>.progress.jsonl.
  • One function, journal.Fold, gives the node state to the CLI, the web UI and the MCP server.
  • The files in contract/schema/ are the source. Tests compare them with the Go types and validate every example.

Output envelope

With --json, a command writes exactly one JSON document to stdout: the envelope. cliout.WriteJSON writes it with a two-space indent, a final newline and escaped control characters. The MCP server puts the same document into structuredContent (result shape).

Rule

  • items is always an array, also for one object. A consumer reads .items[] for every command.
  • Exit code 0 means that errors is empty. Each error carries the exitCode that it causes. Warnings never change the exit code.
  • A command that fails still writes an envelope with the items that it has. Example: a failed build writes the Run with the failed node.
  • A usage error (exit code 2) writes no envelope.
  • Text fields (message, hint, log lines, commit subjects) can change in any release. Match on code and on enum values.

Progress never goes to stdout. In a pipe or in CI, use --progress plain or --progress none for a clean stderr (Output rules).

  • Times are RFC 3339 in UTC, with milliseconds: 2026-11-02T17:50:04.112Z.
  • Durations are integer milliseconds (durationMs). Sizes are integer bytes. Paths are absolute.
  • Commits have 40 hex digits. Digests are sha256: and 64 hex digits. Fingerprints have 40 upper-case hex digits. A UI shortens them. The contract does not.

Streams and the schema command

  • repoctl runs RUN --follow --json writes journal lines (Event names), not envelopes.
  • repoctl logs RUN NODE --follow --json writes one NodeLog object per log line.
  • repoctl schema [NAME] prints a JSON Schema without an envelope: config (default), lock, user-config, manifest, output, events or one kind (repoctl schema).

Rules for consumers

  • Compare apiVersion as a string. If it is different, stop and say so.
  • Ignore fields that you do not know.
  • The open enums are PlanReasonCode, FailureClass, AdvisoryCode, ProblemCode, EventType, HumanAction.action and NextStep.action. Show an unknown value as "other", with its message. All other enums are closed. From v1beta1, a new value in a closed enum is a breaking change.
  • CI scripts pin the repoctl version and check jq -e '.apiVersion == "repoctl/v1alpha1"'.

The skills and the web UI are in the binary of the CLI. repoctl doctor warns (skills.version-mismatch) when an installed copy of a skill is older than the binary.

Stored files and mixed versions

The stored files are the four committed set files (repoctl.yaml, repoctl.lock, keys/deployed.yaml, .repoctl/advisories.yaml) and the RepoManifest of each snapshot. Two admins can run two releases of repoctl on one set, and the registry keeps the snapshots of old releases. A publish copies the entries of the base manifest. Thus an old binary could drop a field that a newer binary wrote. These rules prevent it.

Rules for stored files

  • Within one apiVersion, a stored file takes only additions: a new optional field, or a new value of an open enum. A rename, a removal, a new required field, a new value of a closed enum or a change of meaning needs the next apiVersion. This rule applies from v1alpha1.
  • repoctl reads each apiVersion of a stored file that a release of repoctl wrote. readApiVersions lists them. Thus restore, repo diff and repo verify read the RepoManifest of each old snapshot.
  • A command that only reads a stored file ignores a field that it does not know, and gives the warning contract.newer-file.
  • A command that writes a stored file stops when the file has a field or a closed enum value that the binary does not know: contract.newer-file, exit 1, hint "upgrade repoctl". Publish, restore, prune and resign write a new RepoManifest from the base, so they stop when the base manifest has such a field.
  • A file with an apiVersion that the binary does not read stops each command that reads it, with contract.newer-file (exit 1).
  • minRepoctl in repoctl.yaml is the oldest release that can work on the set. repoctl reads apiVersion and minRepoctl before it checks the other keys. An older binary stops each command that reads the set with contract.newer-file (exit 1), not with config.unknown-key. doctor reports it as the failed check set.repoctl-version.
  • A command writes a stored file in the apiVersion that the file has. If the binary only reads that apiVersion, the command stops with contract.old-file (exit 1). The hint is repoctl migrate --api.
  • A new snapshot gets its RepoManifest in the apiVersion of repoctl.yaml. Publish converts the entries of the base to it. An old snapshot never changes.

The move to the next apiVersion is one set commit. First, all admins install a release that writes the new apiVersion. Then one admin runs repoctl migrate --api (cli.html#cmd-migrate). It converts the four set files and sets minRepoctl to the version of the binary. The admin commits and pushes the change. The next publish writes the RepoManifest in the new apiVersion. The mirror job must read it first (mirror job).

The Next: line of a command (cli.html#next) is the field next, a list of NextStep objects. A kind with one item holds it in the item: Status, Run and SignerList. A --dry-run publish gives the same Run with state: planning. repoctl runs lists Runs with empty nodes.

Problem codes

errors[] and warnings[] hold the same Problem object: code, message, optional node, dir, target, run, path, hint, humanAction, and for errors exitCode. The same code goes into Run.publishBlockers[], the journal event warning and the MCP result. The exit code also goes into Run.exitCode and the MCP _meta["repoctl/exitCode"]. Exit codes gives the meaning of each exit code.

  • The list is open. A consumer treats an unknown code as a generic error or warning.
  • hint is one sentence: what to do next. The terminal prints it as hint: WHAT TO DO. run: CMD (Error messages).
  • When only a human can resolve a refusal, the problem has a humanAction with the exact command. The MCP text then starts with NEEDS HUMAN: (Needs human). The table gives the action in parentheses.
  • DoctorReport.checks[].name holds the check id of repoctl doctor, for example sign.keyfile, sign.release or sign.retiring. A check id that is also a problem code is in the table. repoctl doctor lists all check ids.

Event journal

A run writes two JSON Lines files. The journal runs/<run>.jsonl holds the repoctl events: plan reasons, node states, NVRs, artifacts, advisories and error excerpts. The progress log runs/<run>.progress.jsonl is the go-clikit event log v1, without changes. Both files have the run id and the W3C trace id. Each journal line names its go-clikit span.

Why two files

The go-clikit log is a closed interface. Its fields are progress.Fields, and it never holds the text of an output line. repoctl must record plan reasons, commits, NVRs, artifacts, advisories and error excerpts, so these go into the journal. The progress log stays as go-clikit writes it, so every go-clikit reader works with it.

Line format

Every line has the keys v (1), run, seq, time and type. Optional keys are span and parent (go-clikit span ids) and node. repoctl leaves out a key whose value is empty, except exitCode. The other keys depend on the type.

Order

  • seq starts at 1 and has no gaps. The order of the file is the order of seq.
  • The Reporter changes the span first and writes the journal line second, in the same call.
  • plan.ready gives every node its first state. Build nodes start waiting. repoctl writes no node.state line for a first state.
  • When the dependencies of a node are done, the node goes to running if a job slot is free. If no slot is free, it goes to queued.
  • A terminal state is the last node.state line of the node. run.finished is the last line of the run.
  • A run that stops in its plan has no plan.ready line and no nodes (run states).

Writing and retention

  • The journal writer has the rules of progress.Log: whole lines, O_APPEND, file mode 0600, a trusted state directory. It flushes every 250 ms, and at once after a terminal node.state and after run.finished.
  • Text from mock goes through progress.Sanitize. At 32 MiB, repoctl stops the node.log lines of the run and writes the warning journal.sampling-stopped. State lines continue.
  • A killed process leaves a journal without run.finished. A reader then shows the run as abandoned (Cancel and abandoned runs).
  • Retention deletes the journal, the progress log and the node logs of a run. It runs at the start of a build, at the start of a publish, at the start of a check and in repoctl clean --logs. The table gives the one rule. The shared audit record is the publish history, not the journal (publish.html#format). activity.jsonl rotates at 8 MiB.

Rule

A program that shows node state reads it through journal.Fold or through a result that journal.Fold made. Thus repoctl runs, the web UI and the MCP tools always show the same state. MCP resources for runs are in Resources.

Rule: a followed run whose process ends

A tailer checks the holder of the set lock every 2 s: repoctl runs --follow, repoctl_run_wait and the store of the web UI. When no process of the run holds the set lock and the journal has no run.finished, the fold gives the run state abandoned. Its open nodes (waiting, queued, running) count as canceled. repoctl runs --follow then exits 1 with the error run.abandoned. repoctl_run_wait returns at once with the Run and the same error. The web UI shows the finished state abandoned (finished runs).

Rule: runs of another host

On a home directory that two hosts share, for example over NFS, the state and data directories hold runs of both hosts. The set lock is per host. The rules for a run whose origin.host is not this host:

  • A reader cannot check the set lock of another host. It never shows such a run as abandoned. Such a run without run.finished is running, and the reader names its host.
  • Retention and repoctl clean never delete the files or the staging of such a run.
  • The plan never stages a node of such a run. The node gets the action build.
  • repoctl runs, the web UI and MCP list only the runs of this host.

The doctor check host.shared-state warns when the state or the data directory is on a network file system.

Rule: the commit of a node

journal.Fold takes the commit of each node from commits of plan.ready. NodeResult.commit comes from there. The staged rule of the plan compares the commit and the target with this value of an earlier run whose selection.from is lock (plan actions). It never uses setCommit or the lock of today. setCommit and lockDigest record the set inputs of the run for a human.
