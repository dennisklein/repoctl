repoctl: publish, snapshots and signing

Date: 2026-11-03. Status: proposal for review. This document is work packages WP2 and WP4 of the UX review. It uses the answers of Dennis to Q1 to Q16. Where it differs from 03 or 04, this document applies. Section 14 lists the changes.

1. Summary

  • GHCR is the authority. The tag latest of each set and target says what is published. All other records are copies or caches.
  • Publish has one fixed order: check, sign, repodata, verify, verify in the EL chroot, push, tag, cache. Until the tag moves, nothing that other people see changes. A failed push or tag leaves the signed tree, and repoctl repo push completes it.
  • An HTTP server serves the clients. A mirror job on that server pulls latest, verifies it with the keys that the clients have, and swaps the tree. It uses only curl, jq, gpgv and rpmkeys. repoctl does not run there.
  • No lease between admins. Publish compares latest two times: in the check step and just before the tag moves. The team coordinates in its own channel.
  • A person confirms a key deployment. repoctl sign deployed writes a committed record. Gate 2 passes only with this record. Config management gives no feedback, so a person must check the clients.
  • Re-sign is explicit. A normal publish never re-signs old RPMs. repoctl repo resign does it as its own publish. Publish refuses RPMs from unknown signers.
  • The client rpm verifies. Publish verifies every target inside its EL mock chroot, with the EL rpm and dnf, and only with the keys that the clients have.
  • Every command that changes shared state has one safety class, with a dry run, a summary, a terminal confirmation and no MCP tool.

3.2 Mirror job

The mirror job is a shell script with systemd units. It ships in the repoctl repo as contrib/mirror/ and in the release RPMs (Q16). It runs on the HTTP server as an own system user.

# /etc/repoctl-mirror.conf: one line per set and target
# set          target  package                                         served path
slurm-26.05    el9     ghcr.io/gsi-hpc/slurm-repo/slurm-26.05-el9      /srv/repos/slurm-repo/slurm-26.05/el9
slurm-26.05    el10    ghcr.io/gsi-hpc/slurm-repo/slurm-26.05-el10     /srv/repos/slurm-repo/slurm-26.05/el10
KEYRING=/etc/pki/rpm-gpg/RPM-GPG-KEY-slurm   # from slurm-release on this host
KEEP_TREES=2

Each run of the job does these steps for each line:

  1. Get an anonymous pull token and the manifest of latest (OCI distribution API, curl). If the digest equals the served digest, stop.
  2. Download the missing blobs into .objects/sha256/. Check the sha256 of each blob.
  3. Make a new tree .trees/<set>-<target>/<digest>/ from hard links. Each file gets its path from the annotation org.opencontainers.image.title.
  4. Verify the tree with KEYRING: gpgv on each repomd.xml.asc (exactly one signature), the checksums in repomd.xml, and rpmkeys --checksig on each RPM with a temporary rpmdb.
  5. Write repoctl-snapshot.json into the tree: set, target, digest, publish id, time of the pull.
  6. Swap: replace the symlink of the served path in one rename. Keep KEEP_TREES old trees. Delete objects that no tree uses.
Rule. If a step fails, the job keeps the old tree, writes the error to the journal and exits with a failure. The next run tries again. The job never serves a tree that its keyring does not verify.

The keyring of the job is the key file of the slurm-release that config management installed on the HTTP server. Thus the job has the same trust as a client. A snapshot that a key signs before that key is deployed stays unserved. This is a second guard behind gate 2 (section 11).

repoctl status reads <repo.url>/<target.path>/repoctl-snapshot.json and shows served: same, served: behind or served: unknown.

5. Publish order

This order replaces the publish steps of 04 (check, sign, repodata, verify, swap) and the two orders in the figures of 03 (UX-01).

5.1 Steps

#Step (event name)What it doesOn failure
1checkAll checks of section 5.2. Signer probe (section 11.1).exit 5, 9, 10, 12 or 13. Nothing written.
2signCopy the base to a new tree publishes/p-…/tree/ (hard links). Add the new RPMs. rpmsign --resign the new RPMs only.exit 9 or 1. Delete the new tree.
3repodatacreaterepo_c --update, add the RepoManifest (modifyrepo_c --mdtype=repoctl), sign repomd.xml with one signature.exit 1. Delete the new tree.
4verifyChecksums, one signature packet, rpmkeys --checksig on the host with only the set keys.exit 10. Keep the tree for inspection.
5verify-elPer target, the same checks inside the EL mock chroot with the client trust set (section 11.4).exit 10, problem verify.el-failed. Keep the tree.
6pushUpload the blobs that GHCR does not have. Upload the manifest with the tag p-….exit 13, snapshot.push-failed or registry.denied. Keep the tree.
7tagRead latest. If it equals the base, move it to the new digest. Read it back.exit 13, snapshot.diverged (latest moved) or snapshot.push-failed (tag write failed).
8cacheMake the new tree the local copy. Write snapshot.json. Close the journal.warning only, exit 0. Hint: repoctl repo pull.
Rule. Steps 1 to 5 change only files of the person who publishes. Step 7 is the only step that changes what other people see. A publish is a success when step 7 is done.

A second Ctrl-C during step 6 or 7 stops repoctl at once. The signed tree stays. repoctl repo push p-… completes the publish, or repoctl clean --publish p-… deletes it.

5.3 What a publish takes

Publish works on the plan, not on one run (UX-11). For each selected target, publish takes every node whose plan action is staged: built for the current lock in any unpublished run of this user. The summary lists the source run of each node. --run RUN limits the publish to the nodes of one run.

A target is publishable when every node of the target is current (in the base) or staged. The soname rule of 03 changes from "in the same run" to "in the same publish".

5.4 Two admins

Changes are rare, and the team coordinates in its own channel. Thus repoctl has no lease in the registry (UX-06). The set lock stays a local lock. It protects the processes of one user on one host.

Rule. Publish compares latest with its base two times: in step 1 and in step 7, just before it moves the tag. If latest moved, publish stops with snapshot.diverged. The race window is the time between the read and the write of the tag in step 7, less than one second.

This rule replaces the sentence "the set lock convention covers it for a small team" in 03 section 6.

6. Snapshot format and names

The format of 03 section 6 stays: an OCI artifact with one blob per file. This section fixes the names and adds annotations.

ItemValue
Package<store.oci>/<set>-<target>
Tagslatest; one tag per publish id, for example p-20261103-1412-5e1. The set and target are in the package name, so the tags do not repeat them.
artifactTypeapplication/vnd.repoctl.repo.v1
LayersOne blob per file. Annotation org.opencontainers.image.title = path in the tree, for example slurm/Packages/u/ucx-1.22.1-1.el9.x86_64.rpm.
Annotationsorg.opencontainers.image.source (the GitHub repo), io.repoctl.set, .target, .publish, .kind (publish, restore, prune, resign, import), .parent (digest of the base), .set-commit, .signer (full fingerprint), .user, .host, .created, .repoctl-version

The annotation .parent makes a chain of snapshots. repoctl repo snapshots shows this chain. The user and host of the publisher are in the annotations (UX-19).

The RepoManifest of 03 section 3.2 is in the repodata of the binary repository (slurm/) only. Its entries list the source RPM and the debuginfo RPMs, so slurm-source and slurm-debuginfo need no manifest. One snapshot holds all three repositories of a target.

The RepoManifest gets one new list, removed[]. Each entry has nvr, sha256 of each RPM, publish and reason (prune, restore). Each new snapshot copies the list from its base. Thus plan and publish know every NVR that clients can still have, also when the repo no longer holds it.

Rules for shared state.
  1. Show a summary first. --dry-run shows only the summary. For prune and gc, the dry run is the default and --apply acts.

repoctl repo restore shared state

repoctl repo restore REF [--target ID]... [--dry-run] [--yes]

Make a new snapshot with the files of an older snapshot REF, and move latest to it (UX-13). latest moves forward to a new digest. It never moves back to the old digest. Restore is a publish run: steps 1 to 8, gates 1 and 2, verify and verify-el. RPMs in REF that a removed key signed get a new signature from the current signer (section 11.5).

The summary lists each NVR that leaves the repo and says: clients keep it, because dnf does not downgrade. These NVRs go into removed[]. After a restore, publish refuses a build that gives one of them again with other content (nvr.removed). The hint is repoctl rebuild DIR --reason "…".

Restore is for a broken repo, for example bad repodata. To take back a bad build, fix forward: make a new commit or a rebuild, so that the release goes up, and publish. Clients then update to the fix.

10. Client trust chain

A client installs a package only when two checks pass: dnf checks repomd.xml.asc (repo_gpgcheck=1), and rpm checks the RPM signature (gpgcheck=1). Both use keys that the client got from slurm-release. The figure shows where each key comes from and who checks what.

Figure 2. Trust flows from the set repo to the clients through slurm-release. Four checks see each publish. Only check 5 and the mirror job use the client rpm.

Set → key fileOne file can hold many keys (F14).repoctl release write writes the key file from the keys in state active and retiring, sorted by id. Publish and doctor refuse a key file that differs (sign.keyfile-stale, exit 5).
Key file → clientThe key file is not %config. An update replaces it (F18). dnf imports every key from gpgkey= when it meets an unknown key (F1, F13).The .repo file keeps one gpgkey= line. Its baseurl comes from repo.url (section 11.6).

11. Signing gates and re-sign rules

This section replaces Figure 3 and the re-sign sentence of 04 section 9.2, and section 5 of the publish page text in 04 (the 04j rule). All gates run in step 1, before the first signature.

Figure 3. Checks of the signer in step 1. Each box gives its problem code and exit code.

11.1 Signer probe

The probe signs a random 32-byte value with gpg --detach-sign -u <FPR>! and verifies it. Thus gpg-agent asks for the PIN or passphrase at the start, and not in the middle of the sign step (UX-25).

  • CLI: pinentry asks in the terminal or on the desktop. repoctl suspends the progress display.
  • Web UI: the UI is local only (Q15), so pinentry shows on the local desktop. The browser never asks for a PIN. Step 1 of the publish page shows the probe state: card missing, waiting for PIN on the desktop, touch your key, ready. If a signature takes more than 1 s, the UI shows "touch your key" over SSE.
  • If the probe fails or the person cancels pinentry: sign.locked, exit 9. The hint gives gpg --card-status.

The 04 sentence "MCP and the web UI never sign" changes to: MCP never signs. The web UI signs only through repoctl publish, after the typed confirmation.

11.4 Verify in the EL chroot

repoctl runs on Fedora, with rpm 6 and rpm-sequoia. The clients use EL9 rpm 4.16 and EL10 rpm 4.19. Thus step 4 alone can pass while a client fails (UX-67). Step 5 checks each target with the client tools.

  1. repoctl mock update also makes one verify root per target: the mock config of the target, plus rpm, dnf and gnupg2.
  2. Step 5 mounts the new tree and the key file read-only into that root (mock bind_mount plugin).
  3. Inside the root: import the key file into a temporary rpmdb, then rpmkeys --checksig on each RPM.
  4. Inside the root: dnf makecache on a temporary installroot with the new tree as a file:// repo, gpgcheck=1, repo_gpgcheck=1 and gpgkey= the key file. This runs the librepo signature check of the client.

Client trust set. Step 5 uses the key file of the release that the clients have: the release of the deployment record of the signer. It does not use the key file of a release that this publish adds. For a first publish, it uses the key file of this publish.

The signer host is always Fedora. The 04 text about a Rocky 9 signer host is removed.

11.5 Re-sign rules

One rule set replaces the two rules of 04 (UX-23, UX-24):

RPM in the base, signed byNormal publishrepo resign --signer ID
a key in state activekeepre-sign if ID is that key
a key in state retiringkeep; the summary shows the count and the resign hintre-sign if ID is that key
a key in state removedrefuse: sign.removed-signer, 12re-sign if ID is that key
an unknown key, or no signaturerefuse: sign.unknown-signer, 10, with the file namesrefuse

repoctl re-signs an RPM only when both conditions are true: its signature verifies with a key in sign.keys, and its sha256 is in the base snapshot, which has a valid repomd.xml.asc. RPMs of different admins stay side by side. A change of the person who publishes never re-signs old RPMs.

11.6 Release package in v1

v1 has one form of the release package (UX-21): an in-tree package in the set repo, for example packages/slurm-release/, with role: release.

  • Build identity of an in-tree package = the last set commit that changed its path, plus the target. repoctl builds it from a checkout of that commit. A key change is a commit on that path, so plan says build with reason commit-changed.
  • Release: the spec uses %autorelease and %autochangelog. The changelog then shows the commit message of each key change, for example "Trust key a.admin C2F9…52A7".
  • repoctl release write local write writes the key file from sign.keys and the baseurl lines of the .repo file from repo.url. It does not commit. sign add, sign retire and sign remove call it and commit both files with the key change. init --release (06) calls it for a new set.
  • doctor checks sign.release (key file = sign.keys) and release.url (baseurl = repo.url).

11.7 Key expiry

rpm does not update an imported key (F12). EL10 does not trust an expired key (F6). Thus a new expiry date does not help the clients (UX-35).

Rule. Treat an expiring key as a key change. Add a new key, deploy it, retire the old key, re-sign, remove the old key (section 12). Do not extend the expiry date of a key that clients already have.
  • doctor sign.expiry warns inside key_expiry_warn (180d). Its fix line: repoctl sign onboard NEW-ID, then repoctl sign retire OLD-ID.
  • Gate 1 refuses a signer inside key_min_validity (30d).
  • repoctl check reports published RPMs whose signer expires inside the warn window. The advisory code is sign.expiring, level warn (06 defines the kind).

12. Key lifecycle and sign commands

Figure 4. Key states. sign.keys[].state has three values: active, retiring, removed. "Deployed" is an active key with a record in keys/deployed.yaml.

12.1 Onboarding

The explainer plays the onboarding of a second admin with the deployment record (UX-04, UX-26).

12.2 Offboarding and rotation

  1. repoctl sign retire ID: state retiring, set commit. The key cannot sign any more.
  2. repoctl repo resign --signer ID per target, by an active admin. All RPMs of that key get a new signature.
  3. repoctl sign remove ID: refuses while latest of a target holds an RPM of that key. Then state removed, a new key file without it, set commit.
  4. Build and publish the new slurm-release. Config management rolls it out.
  5. Config management removes the key on each client. repoctl sign offboard ID prints the commands (04 section 9.3).
  6. Remove the person from the GitHub team. The record in keys/deployed.yaml can stay, because gate 1 refuses a removed key.

17. Assumptions and open questions

Assumptions

  • The HTTP server can run a systemd timer and has curl, jq, gnupg2 and rpm. Config management installs slurm-release on it, as on a client.
  • The mirror interval is 5 minutes. A shorter interval only adds HEAD requests.
  • GHCR has no tag compare-and-swap. The window in step 7 is acceptable after Dennis's rule on races.
  • The publish id format p-YYYYMMDD-HHMM-xxx of 04 stays. Imports use p-import-YYYYMMDD.
  • Host names, the server path /srv/repos/slurm-repo, the team name and the fingerprints in the examples are placeholders.

Open questions (no blocker)

  • Which host is the HTTP server, and who owns the mirror job?
  • Which name has the GitHub team in GSI-HPC?
  • Is 30 days a good default for key_min_validity?
