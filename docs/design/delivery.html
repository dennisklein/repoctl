Delivery and verification

This chapter gives the order in which repoctl is built, the limits of scale, time and disk that the design supports, and the tests that must pass before the code depends on a fact. It also lists the assumptions of the design and the questions that are still open.

  • Eight phases, 0 to 7. Each phase ends with a "done when" in the terms of the data story.
  • Phase 0 puts the tool on branch main, with CI and this docs site on GitHub Pages.
  • The bash-era scripts stay on the builder branches until the first publish with repoctl.
  • Tests V1 to V34 run on Rocky 9, Rocky 10 and the Fedora host. Each test names the phase that it gates.
  • Each open question names the phase that needs the answer.
  • The requirements give a value from the data story and a design limit for each scale, time and disk row.

Test strategy

The verification tests check facts of the environment. The test layers in this section check the code of repoctl. Each layer starts in the phase of the table. Each later phase adds the tests of its own commands to each layer. A phase is done when the tests of its "done when" pass in the end-to-end layer.

  • Story fixture. The story fixture is the data story as test data. It has the set slurm-26.05 with a builder branch and 11 package branches. The specs are small, but they keep the names, versions, BuildRequires and Provides of the story. A script replays the story: the bump of ucx, the rebuild commits, run r-20261102-1750-a3f with the failure of slurm@el10, and publish p-20261103-1412-5e1. The fixture also holds the recorded tool output: rpmspec output, buildroot_lock.json and the mock logs of the story.
  • Mock stub. The integration tests put a stub first in PATH with the name mock. It reads the arguments that repoctl gives, writes the recorded RPMs, logs and buildroot_lock.json of the node into --resultdir, and exits with the recorded exit code (0, 1 or 30). Thus CI needs no mock chroot and no network.
  • Golden files. A golden file is the expected output of one command or one UI fragment in the story state. go test -update writes the golden files again, and a human reviews the change. The mockups are the reference for what a human sees. When a golden file changes what a human sees, the same pull request changes the mockup and its screenshot.
  • Code. Unit tests are next to their Go package. The fixture is in testdata/story/. The helpers are in internal/testkit (Go packages). The end-to-end tests and the scale tests have the Go build tags e2e and scale, so that go test ./... does not run them.
  • Test keys. The integration tests use the keys A, B and C of the verification tests. No test uses a key of a set.

Assumptions

The design depends on these facts. A test or a human confirms each of them. When one is false, the chapter that it names must change.

  • The clients run Rocky 9 and Rocky 10 on x86_64 with the stock rpm, dnf and librepo of the c9s and c10s spec files. The facts F1 to F18 hold for these versions (client facts; V10 to V18).
  • Config management installs the release package on every client. On the HTTP server, it puts the key file of each set and target at the keyring of its mirror line. A human can tell when the rollout is complete (onboarding).
  • The HTTP server can run a systemd timer and has curl, jq, gnupg2 and rpm (mirror job; V1).
  • The mirror job runs every 5 minutes. A shorter interval only adds HEAD requests. Clients read a new repomd.xml after metadata_expire (one hour).
  • GHCR has no tag compare-and-swap. publish compares latest in step 1 and in step 7. The window between the two is acceptable, because the team coordinates in its own channel (two admins). A publish that loses the race leaves the chain of latest, and repo pull and status warn with snapshot.orphaned.
  • The GHCR packages are public, so the mirror job pulls without a token. A push needs a classic token with write:packages and a team with write access (registry access; V2, V3).
  • rpmautospec raises the release for each commit, also for an empty one (rebuild; V19). For an in-tree package, V6 shows which commits count.
  • go-clikit gives the span id (Span.TraceContext()), the doctor format and the progress log. repoctl needs no change in go-clikit for the journal (journal).
  • The UI agent is Claude Code (agent: {command: claude}). repoctl reads its stream-json output (agent config).
  • mock exits with 30 when dnf builddep fails (V20).
  • Host names, the server path /srv/repos/slurm-repo, the GitHub team name, the fingerprints and the commits in the examples are placeholders. The data story fixes them for all chapters.
