Delivery and verification

This chapter gives the delivery phases of repoctl and the limits of scale, time and disk that the design supports. It gives the tests that must pass before the code depends on a fact, the assumptions of the design and the open questions.

  • Eight phases, 0 to 7. Each phase gives a tool that works on its own and ends with a "done when" in the terms of the data story.
  • The bash-era scripts stay on the set branches until the first publish with repoctl.
  • Each requirement gives a value from the data story and a design limit for scale, time or disk.
  • Tests V1 to V40 run on Rocky 9, Rocky 10 and the Fedora host. Each test names the phase that it gates.
  • Each open question names the phase that needs the answer.

Delivery phases

A phase starts when the tests that gate it pass (verification). The command blocks are in the CLI reference.

Phase 0: foundation

Content
  • Orphan branch main in github.com/dennisklein/repoctl (where the tool lives).
  • Go module on GSI-HPC/go-clikit.
  • CI on GitHub Actions: build, test (test strategy), lint, and a check of each contract example against its schema.
  • This docs site on GitHub Pages.
Done when
  • main is the default branch, and CI passes on it.
  • The docs site is online at https://dennisklein.github.io/repoctl/.
  • The set branches do not change.

Phase 1: core commands and graph

Content
  • Config layers and set discovery. repoctl.yaml, repoctl.lock and the user config, with their schemas.
  • init, migrate, status, list, show, checkout, pin, graph, doctor, config, schema, mock update, version, completion.
  • The graph per target from the SRPM in the target chroot.
  • Lock states, exit codes and problem codes.
Done when
  • repoctl migrate on set/slurm-26.05 writes a lock with the same packages, branches and commits as packages.lock.
  • repoctl graph --target el9 shows 11 nodes, 14 edges and depth 4 (the real build graph). With the target el10 added, the el10 graph has 10 nodes.
  • checkout and pin give the same lock as the scripts.
  • repoctl doctor passes on hpc-a1.

Phase 2: build with staging and the manifest

Content
  • plan (actions and reasons). build: jobs, mock --uniqueext, keep going, --fail-fast.
  • The staging repo with the RepoManifest entry and the record draft of each node (mock plugin buildroot_lock, source sha256).
  • rebuild, runs, logs, cancel, clean.
  • The set lock and exit 7. The journal. The soname check.
  • Terminal output: exceptions plus a totals line, -v, --json.
Done when
  • Without latest, plan shows every node with the reason new-package: 11 on el9, 10 on el10. It warns with dep.not-for-target for slurm@el10.
  • repoctl rebuild slurm --reason … makes an empty commit. plan then shows slurm with the reason rebuild and the NVR 26.05.4-2.
  • A run with jobs 3 keeps going after slurm@el10 fails, marks slurm-singularity-exec@el10 blocked and exits with 3. The next plan shows the ok nodes as staged.
  • A second build of dklein on hpc-a1 stops with exit 7 (set.busy).
  • An unchanged commit gives the same NVR as the bash-era build.
  • The staged ucx@el9 has buildroot/ucx-1.22.1-1.el9.json with each buildroot RPM and its signer, and the sha256 of ucx-1.22.1.tar.gz.

Phase 3: publish to GHCR

Content
  • publish with the steps check, sign, repodata, verify, verify-el, push, tag, cache (publish order).
  • The repo commands, repo push --from included. The registry checks of doctor.
  • The sign commands, release write, keys/deployed.yaml, the signer probe, the verify roots and gates 1 to 3.
  • The mirror job in contrib/mirror/.
  • The supply chain records: provenance and SBOM of each build, the repository SBOM, and the record checks in verify, verify-el and the mirror job.
  • repo provenance, repo sbom and the doctor check sbom.license.
Done when
  • The publish of el9 from run r-20261102-1750-a3f signs 38 RPMs with d.klein and keeps 170.
  • Step tag moves latest from p-20260912-1403-c21 to p-20261103-1412-5e1.
  • publish --target el10 stops with publish.not-ready (exit 12).
  • The mirror job serves 5e1 within 5 minutes, and status shows "served: same".
  • Gate 2 refuses a.admin before its deployment record (sign.not-deployed, exit 12).
  • repo restore makes a new snapshot, and latest moves forward.
  • The publish of el9 holds 4 provenance records with the signed sha256 of 38 RPMs.
  • A changed byte in one record gives records.mismatch (exit 10), and the mirror job keeps the old tree.
  • repoctl repo sbom --target el9 --raw | grype lists ucx 1.22.1 with its upstream purl.

Phase 4: tool RPM, release RPM, Fedora repo on Pages

Content
  • The tool RPM repoctl, the release RPM repoctl-release and the noarch mirror job RPM repoctl-mirror, for EL and Fedora, in the RPM repo on GitHub Pages.
  • A GitHub Actions job builds them on each version tag. It signs them with the tool repository key, not a slurm key. The key is a secret of the protected environment tool-release.
  • The job publishes the dnf repo on GitHub Pages and the RPMs on the GitHub release. It writes GitHub artifact attestations (SLSA provenance) for the binary and the RPMs.
  • The yank job.
  • Then the import runbook converts the bash-era repos.
Done when
  • On a clean Fedora host, the first install with the sha256 and the fingerprint of Tool releases works.
  • dnf install repoctl from the Pages repo installs the tool. repoctl doctor passes with tool.repo-key, and gh attestation verify passes for the RPM.
  • On Rocky 9, dnf install repoctl-mirror installs the mirror job.
  • A workflow on a set branch cannot read TOOL_REPO_KEY.
  • The import of slurm-26.05 el9 gives p-import-20260828 (48 RPMs, signer hpc-repo), and no client changes a package.
  • After the first publish with repoctl (p-20260902-1010-4a7), the set branch has no scripts/ and no packages.lock.

Content

  • The publish gate with --accept-advisory ID --reason TEXT (gate).
  • init --from, checkout --create with its four start points, the lock states unpinned and orphaned, repo prune --package NAME --all (Sets and packages).

  • The el9 publish review shows the gate row "open, not changed by this publish" and does not block.

  • init --from and checkout --create --from-set fork slurm-26.11 with 10 branches at the lock commits. status lists the open setup steps.

Phase 6: skills and MCP

Content
  • mcp start with --tools read, mcp tools, skills install and the Claude Code plugin.
  • The skills repoctl, bump-package (draft, apply), triage-build, rebuild-check and package-updates, with a tool list per task.
Done when

  • rebuild-check on the ucx bump says "sonames unchanged: rebuild not necessary".
  • repoctl mcp start --tools read lists only read tools, and a call of repoctl_build fails with mcp.tool-not-allowed.
  • No MCP tool publishes, signs or pushes.

Phase 7: web UI

Content
  • repoctl ui for the local user, with the token launch URL.
  • Server-rendered pages with htmx and one SSE connection per tab. The calm rules R1 to R13.
  • The pages of the sitemap, the agent buttons and the agent panel.
  • At the end of the phase, the move to v1beta1 (versioning): the converters of the stored files, migrate --api and the mirror job that reads both apiVersions.

  • Explain failure on slurm@el10 runs triage-build with the read-only MCP server and names the fix for rocm-smi-devel.
  • The el9 publish review at 14:05 shows 38 new and 170 kept, and the publish asks for the typed set name.

Requirements

The design limit of a non-functional requirement is the largest value that the design supports. A result outside the limit is a bug, not a new design question. A change of a limit changes this table. The scale tests and the end-to-end tests measure the rows (test strategy).

The times are for an admin host like hpc-a1. They do not include the time in mock, the time of the human (confirmation, PIN, touch) and the network transfer.

Test strategy

The verification tests check facts of the environment. The test layers check the code of repoctl. Each later phase adds the tests of its own commands to each layer. A phase is done when the tests of its "done when" pass in the end-to-end layer.

  • Story fixture. The story fixture is the data story as test data: the set slurm-26.05 with a set branch and 11 package branches. The specs are small, but they keep the names, versions, BuildRequires and Provides of the story. A script replays the story: the bump of ucx, the rebuild commits, run r-20261102-1750-a3f with the failure of slurm@el10, and publish p-20261103-1412-5e1. The fixture also holds the recorded tool output: rpmspec output, buildroot_lock.json and the mock logs of the story.
  • Mock stub. The integration tests put a stub with the name mock first in PATH. It reads the arguments of repoctl and writes the recorded RPMs, logs and buildroot_lock.json of the node into --resultdir. It exits with the recorded exit code (0, 1, 11 or 30). It answers --chroot with the recorded rpm -qa lines of the buildroot facts, --debug-config with a recorded config, and --orphanskill and --clean with exit 0. Thus CI needs no mock chroot and no network.
  • Golden files. A golden file is the expected output of one command or one UI fragment in the story state. go test -update writes the golden files again, and a human reviews the change. The mockups are the reference for what a human sees. When a golden file changes what a human sees, the same pull request changes the mockup and its screenshot.
  • Code. Unit tests are next to their Go package. The fixture is in testdata/story/, the helpers are in internal/testkit (Go packages). The end-to-end tests and the scale tests have the Go build tags e2e and scale, so go test ./... does not run them.
  • Test keys. The integration tests use the keys A, B and C of the verification tests. No test uses a key of a set.

Assumptions

The design depends on these facts. The test of the row confirms a fact; without a test, a human confirms it. When a fact is false, the chapter of the row must change.

AssumptionChapterTest
The clients run Rocky 9 and Rocky 10 on x86_64 with the stock rpm, dnf and librepo of the c9s and c10s spec files. The facts F1 to F18 hold for these versions.client factsV10 to V18
Config management installs the release package on every client. On the HTTP server, it puts the key file of each set and target at the keyring of its mirror line. A human can tell when the rollout is complete.onboarding—
The HTTP server can run a systemd timer and has curl, jq, gnupg2 and rpm.mirror jobV1
The mirror job runs every 5 minutes. A shorter interval only adds HEAD requests. Clients read a new repomd.xml after metadata_expire (one hour).mirror job—
GHCR has no tag compare-and-swap. The race window between the checks of latest in step 1 and step 7 is acceptable, because the team coordinates in its own channel.two admins—
The GHCR packages are public, so the mirror job pulls without a token. A push needs a classic token with write:packages and a team with write access.registry accessV2, V3
rpmautospec raises the release for each commit of a package branch, also for an empty one, when the sources directory is a full clone. It does nothing for an in-tree package or a git worktree.source cloneV19, V35, V6
mock runs as root through consolehelper. A signal of the user to mock gives EPERM, and mock --orphanskill stops a build.failuresV40
The signer field of buildroot_lock.json reads only SIGPGP. Rocky and EPEL RPMs have RSAHEADER, so repoctl reads the signer from the root.buildroot factsV23
go-clikit gives the span id (Span.TraceContext()), the doctor format and the progress log. repoctl needs no change in go-clikit for the journal.journal—
The UI agent is Claude Code (agent: {command: claude}). repoctl reads its stream-json output.agent config—

Host names, the server path /srv/repos/slurm-repo, the GitHub team name, the fingerprints and the commits in the examples are placeholders. The data story fixes them for all chapters.data story—
