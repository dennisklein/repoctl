repoctl: advisories and package lifecycle

Date: 2026-11-03. Status: proposal. This document specifies work packages WP3 and WP5 of the UX review. It uses the answers of Dennis to Q5, Q6, Q7, Q9 and Q10. It changes parts of 02, 03 and 04. Section 14 lists the changes. 05 specifies publish, snapshots and signing. This document refers to 05 for these topics.

Part A (sections 2 to 7) is about advisories. Part B (sections 8 to 13) is about the life of a package in a set. The import of the bash-era repos is a separate runbook for an agent: import-bash-era-repos.html.

1. Summary

  • An advisory is data with one id. The id is CODE/SUBJECT, for example closure.broken/pmix@el9. The CLI, the contract, MCP, the UI routes, the DOM, SSE and the journal use the same id.
  • repoctl computes advisories. It does not store them. It stores only two things: dismissals (a committed file in the set, per team) and acceptances (in the journal and in the snapshot annotations).
  • New commands: repoctl check, repoctl advisories ls|show|dismiss|undismiss and repoctl publish --accept-advisory ID --reason TEXT.
  • The gate is narrow. A required advisory blocks a publish only when the run adds or replaces a package in its closure. A run that fixes the problem passes. Other publishes show the advisory in the summary (Q9).
  • Each admin host runs its own daily check timer. The check is read-only, so two timers do no harm. Doctor and status show a missing, failed or old check (Q10).
  • Old package versions stay in the repo. Removal is explicit: repoctl repo prune --package NAME --all for a retired package (Q6).
  • A new set forks its branches from the previous set. repoctl init --from and repoctl checkout --create --from. An orphan branch needs --orphan. checkout --create checks the remote first (Q7).
  • Two new lock states: unpinned and orphaned.
  • Two new help topics: repoctl help new-set and repoctl help packages, with ordered steps.

Part A. Advisories

2. Advisory model

An advisory tells the person that a rebuild or another step can be necessary. It is the result of a deterministic check. It suggests a step. The person decides. The diagram shows where advisories come from and who reads them.

2.1 Id and subject

  • The id is CODE/SUBJECT. There is no other form. The 04l form closure.broken:pmix@el9 is superseded.
  • The subject is DIR@TARGET for each code that depends on a target. It is DIR for upstream.release, because an upstream release does not depend on a target.
  • The subject of a retired package is its source package name, because a retired package has no dir in repoctl.yaml (section 11).
  • repoctl makes one advisory per code and node. It does not group nodes. The UI can show nodes with the same facts in one row. This answers the open question in 04 "Should buildroot.drift group packages?".

An adopted manifest entry (from the import runbook) has no buildroot file. buildroot.drift, mock.drift and provider.changed skip such an entry. The next build of the node writes a buildroot.

2.3 States

  • pending: the check needs a build that did not finish. Example: soname.removed for a node that is still in the run. Only the UI and advisories ls during a run show this state.
  • open: the check found the problem now, and no dismissal matches.
  • dismissed: a dismissal in .repoctl/advisories.yaml has the same id and the same factsDigest. Only info and warn advisories can be dismissed (03 section 10).
  • gone: the check does not find the problem any more. repoctl does not keep gone advisories. The journal of the check records the change (event advisory.gone).

factsDigest is the SHA-256 of the canonical JSON of facts. When the facts change (for example, a newer upstream version), the digest changes. Thus, the dismissal does not match, and the advisory is open again.

2.5 Dismissal file

# .repoctl/advisories.yaml
# Written by repoctl advisories dismiss. Commit and push it.
apiVersion: repoctl/v1alpha1
dismissed:
  - id: buildroot.drift/pmix@el9
    facts: sha256:1c9e4f…                 # factsDigest at dismiss time
    note: hwloc-devel 2.11 adds nothing that pmix uses
    by: d.klein@gsi.de                    # git config user.email
    at: 2026-11-03T14:02:11Z
  - id: upstream.release/pmix_v4
    facts: sha256:77ab20…
    note: 4.x is frozen, see notes in repoctl.yaml
    by: a.admin@gsi.de
    at: 2026-11-03T15:40:02Z
  • repoctl writes the file atomically and keeps the entries sorted by id. Thus, two dismissals of different ids seldom give a git conflict.
  • repoctl does not commit the file. dismiss prints the commit and push command. status shows "advisories.yaml: not committed" when the file has changes.
  • Publish does not require that this file is committed. The file does not change the output of a build.
  • An entry whose id is gone, or whose digest does not match, is stale. advisories ls --dismissed marks it. advisories undismiss --stale removes all stale entries.
  • A new set does not copy this file from the old set (section 9).

3. Commands

These commands go into 04c section 11. The format is the same as there.

3.1 repoctl check

repoctl check [--target ID]... [--code CODE]... [--check] [--min-level L] [--quiet]
repoctl check --install-timer | --remove-timer

Compute all advisories that do not need a build, for each target. Inputs: the manifest and repodata of the -latest snapshot (05; check pulls only the repodata, not the RPMs), the upstream repos of the target, the upstream release feeds, and the mock config of this host.

FlagTypeDefaultMeaning
--targetid, repeatallCheck only these targets.
--codecode, repeatallRun only these checks.
--checkboolfalseExit 11 when at least one open advisory has a level of --min-level or higher.
--min-levelinfo|warn|requiredwarnLevel for --check.
--quietboolfalsePrint nothing on success. The timer uses it.
--install-timerboolfalseWrite and start the user timer for this set (section 6). Do no check.
--remove-timerboolfalseStop and remove the timer instance of this set.

Lock: none. The check is read-only. It runs while a build runs. Writes: check.json in the state dir, and a journal with kind: check. Kind: AdvisoryList. Exit: 0; 1 a check failed (for example, an upstream repo is not reachable; the other checks still run and check.json records the failure); 9 a required host tool is missing; 11 with --check; 13 the registry is not reachable (05).

3.2 repoctl advisories

repoctl advisories [ls] [--target ID] [--level L] [--dismissed] [--refresh]
List the advisories. The list is the last check result plus the advisories of the newest unpublished run. With --dismissed, list the dismissed and stale entries too. With --refresh, run repoctl check first. The head line gives the age and the source of the last check. Kind AdvisoryList. Exit 0.
repoctl advisories show ID
Show one advisory: level, state, facts, the closure (section 4), the suggested command, and the dismissal if there is one. Kind Advisory. Exit 0; 1 unknown id (advisory.unknown).
repoctl advisories dismiss ID... --note TEXT
Add a dismissal for each open id to .repoctl/advisories.yaml. The note is required, with at least 8 characters. A required advisory cannot be dismissed: exit 1, code advisory.not-dismissable, hint publish --accept-advisory. An id that is not open: exit 1, advisory.unknown. Next line: git add .repoctl/advisories.yaml && git commit -m "chore: dismiss ID" && git push.
repoctl advisories undismiss ID... | --stale
Remove dismissals from the file. The advisory is open again at the next check.

No lock. dismiss and undismiss write only .repoctl/advisories.yaml.

3.3 repoctl publish --accept-advisory

repoctl publish … [--accept-advisory ID]... [--reason TEXT]
  • --accept-advisory takes an id, not a code. One flag accepts one advisory. It does not accept a later advisory with the same code.
  • --reason is required when --accept-advisory is given, with at least 8 characters. One reason covers all ids of the call.
  • An id that does not block this publish is a usage error (exit 2). Thus, a person cannot accept an advisory in advance.
  • The acceptance is valid for this publish only. repoctl writes the event advisory.accepted (id, factsDigest, reason, user, host) to the journal. It writes the same list to the snapshot annotation io.repoctl.advisories.accepted (05).
  • --yes does not accept an advisory. An unattended publish with a blocking advisory fails with exit 12.

3.4 repoctl status

status gets one advisories line and, if necessary, one check line:

advisories  1 required (closure.broken/pmix@el9) · 0 warn · 3 info · 1 dismissed
check       last 2h ago (timer) · ok

The check line shows a problem in these words: last check failed 5h ago: upstream.unreachable (EPEL 9), last check 3 days ago: the timer is off, or never checked: run repoctl check --install-timer. A check is old after 36 hours.

4. Publish gate (Q9, UX-12)

The gate runs in the check step of publish (05 calls it "advisory gate (06)"). It runs for each target of the publish.

  1. Make the result tree of the target: the published repo of -latest, plus the nodes of the run. A node of the run replaces the older NVRs of the same name as the newest.
  2. Run dnf repoclosure --newest on the result tree plus the upstream repos of the target. The result is a list of broken requirements: (RPM p, requirement r).
  3. For each broken requirement, find its closure: the dir that built p, plus the dir whose newest published build provided r and whose build in the run does not provide it.
  4. A required advisory blocks the target when its closure contains a dir of the run on that target, and the person did not accept it.
  5. A required advisory whose closure has no dir of the run does not block. The summary shows it as "open, not changed by this run".
  6. A broken requirement of an old NVR (not the newest of its name) is never a block. The summary shows it as info, with a prune suggestion.
  7. A retired package is never in a closure. Its broken requirements are closure.broken at level warn (section 2.2).

The gate uses the result tree, not the last check result. Thus, a run that fixes the problem passes, and the advisory is gone after the publish.

A blocked publish fails with exit 12 (ExitNotPublishable). The problem code is advisory.open. Its humanAction is accept-advisory with the exact command:

error: publish of el9 refused: 1 required advisory changes with this run
  soname.removed/ucx@el9  libucp.so.0 removed; slurm, openmpi require it
hint: rebuild the dependents into this run:
        repoctl rebuild slurm openmpi --reason "ucx: libucp.so.0 → .so.1"
      or accept it for this publish:
        repoctl publish --target el9 --accept-advisory soname.removed/ucx@el9 --reason "…"

6. Check timer (Q10, UX-34)

Each admin host runs its own timer for each set that the admin works on. The check is read-only. Two timers thus give two equal results and do no harm. When an admin leaves, the timers of the other admins still run.

6.1 Units

repoctl check --install-timer writes the template pair once and starts one instance for the set. The instance name is the escaped set directory (systemd-escape --path).

# ~/.config/systemd/user/repoctl-check@.service
[Unit]
Description=repoctl check for the set in %I
After=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/bin/repoctl -C %I check --quiet
Nice=10
# ~/.config/systemd/user/repoctl-check@.timer
[Unit]
Description=Daily repoctl check for the set in %I

[Timer]
OnCalendar=daily
RandomizedDelaySec=1h
Persistent=true

[Install]
WantedBy=timers.target
$ repoctl check --install-timer

      Persistent=true runs a missed check at the next login.
      To run it always: loginctl enable-linger dennis

repoctl runs on Fedora hosts only (Q16). On a workstation, lingering is optional. Thus, the linger note is info, not a warning.

Part B. Package lifecycle

8. States of a package

A package has two kinds of state. The lock state compares repoctl.yaml, repoctl.lock and the worktree. The publish state compares the set with the -latest snapshot of each target.

8.1 Adopted manifest entries

The import runbook writes manifest entries for the RPMs that the bash-era scripts built (Q5). These entries use the RepoManifest of 03 section 3.2 with these values:

FieldValue
reasonadopted when a commit of the branch gives the NVR. adopted-unmapped when no commit gives it.
commitThe commit, or null for adopted-unmapped.
mockConfig, macros, buildroot, buildrootFile, runnull. The bash era did not record them.
provides, requiresFrom the RPM headers.
builtBUILDTIME of the SRPM.
publishThe import publish id p-import-DATE (05).
signerThe key id of the RPM signature.

plan reads an adopted entry as any other entry. When the pinned commit is in it, the node is current. An adopted-unmapped entry never makes a node current. It counts for the closure checks and for prune.

9. New set (Q7, UX-27, UX-29)

A new set forks each package branch from the previous set. Thus, the rpmautospec history and the changelogs continue. The builder branch also forks from the previous builder branch, as today.

9.1 repoctl init --from

repoctl init --from SET --name NAME [--force]

SET is a set directory or a builder branch (for example, builder/slurm-26.05). init reads its repoctl.yaml and writes a new one in the start directory:

  • name becomes NAME.
  • In each branch, repoctl replaces the old set name with the new one: pmix/slurm-26.05-v4 becomes pmix/slurm-26.11-v4. This is also true for an external package (slurm-26.05 becomes slurm-26.11).
  • A branch that does not contain the old set name stays the same. init lists it as "shared branch". Example: slurm-25.11 uses pmix/slurm-26.05-v4.
  • The other keys stay the same: targets, repo, upstream, notes, roles.
  • When the start directory is a fork of SET (its repoctl.yaml has the old set name), init changes the file in place without --force. Otherwise, init also copies the files that repoctl.yaml names: macro files and the release package path.
  • init does not copy repoctl.lock or .repoctl/advisories.yaml. The new set has new branches and new advisories.
  • init does not create branches. checkout --create --from does that.

init (with or without --from) prints the full Next list. It is the same list as repoctl help new-set (section 13), from the step after init.

9.2 repoctl checkout --create

repoctl checkout [DIR...] --create (--from REF | --from-set SET | --from fedora[:BRANCH] | --orphan)
FlagStart point of the new branch
--from-set SETFor each DIR: the commit of the same dir in the repoctl.lock of SET. This is the published state, not the branch tip. A dir that is not in SET fails with branch.start-missing.
--from REFAny git revision, for example pmix/slurm-26.05 or a commit. For one DIR, or for a second stream such as pmix_v4.
--from fedora[:BRANCH]The dist-git history of upstream.fedora on src.fedoraproject.org, branch rawhide by default. repoctl fetches it into a temporary ref.
--orphanA new branch without history. Only on request.
  • One of the four flags is required with --create. Without one: exit 2, "say --from-set, --from, --from fedora or --orphan".
  • Before it creates a branch, repoctl runs git ls-remote on the remote of the package. When the branch exists there, repoctl does not create it: exit 1, branch.exists-remote, hint repoctl checkout DIR.
  • For an external package, the server repository must exist. When ls-remote fails: exit 1, git.unreachable, hint "create the project on the git server first".
  • The output gives the start point of each branch: "forked from pmix/slurm-26.05 at 6644bdf" or "orphan".
  • repoctl does not push. The output ends with one push command for all new branches, then repoctl pin.

10. Lock states (UX-31)

Two values go into LockState:

StateMeaningstatus hint
unpinnedThe package is in repoctl.yaml. It has no entry in repoctl.lock.repoctl pin DIR
orphanedThe package is in repoctl.lock. It is not in repoctl.yaml.repoctl pin (removes it)
  • LockEntry.commit is required, except for state unpinned.
  • plan shows an unpinned node with the note "not pinned" and the action skip. With --from worktree, the action is build.
  • build --from lock with a selected unpinned node fails with exit 5, lock.missing-package, hint repoctl pin DIR.
  • checkout without --create for an unpinned package makes the worktree at the remote branch tip (detached) and prints "not pinned: run repoctl pin DIR". This is how a person checks out a colleague's new package.
  • pin without arguments removes orphaned entries and lists them. pin DIR for a dir that is not in repoctl.yaml is a usage error.
  • publish refuses a set with an orphaned entry: exit 5, lock.orphaned. The lock and repoctl.yaml must agree, so that the set commit fixes the output (Q8).

11. Package changes

Each case gives the ordered steps, the repository of each commit and the plan reason that the person must see. The same text goes into repoctl help packages (section 13).

11.1 Add a package in this repository

  1. Add the entry to repoctl.yaml: dir, branch, upstream.
  2. repoctl checkout --create DIR --from fedora (or --orphan).
  3. Write or change the spec in packages/DIR. Commit there. Repository: the package branch.
  4. git -C packages/DIR push origin BRANCH.
  5. repoctl pin DIR.
  6. git add repoctl.yaml repoctl.lock && git commit && git push. Repository: the builder branch.
  7. repoctl plan. Expected: DIR has reason new-package on each of its targets. When DIR provides a BuildRequires of a current node, provider.changed names the dependents.
  8. Follow the advisory: repoctl rebuild DEPENDENTS --reason "build against set DIR", then pin, commit and push. Or dismiss it with a note.
  9. repoctl build, then repoctl publish.

11.2 Add an external package (git.url)

The steps are the same as 11.1, with these changes:

  • Create the project on the git server first. repoctl cannot do this.
  • The entry has git: {url: …}.
  • The worktree comes from a bare clone in $XDG_DATA_HOME/repoctl/git/HASH.git (section 12). git -C packages/DIR push origin BRANCH pushes to the external server.

11.3 Add a second stream

Example: pmix_v4 next to pmix. Fork from the history of the first stream: repoctl checkout --create pmix_v4 --from pmix/slurm-26.05. The spec must rename the package and must not conflict with the Provides of the first stream. Then follow 11.1 from step 3.

11.4 Build a package for some targets only

Add targets: [el9] to the entry. plan shows the nodes on the other targets as removed from the set. A dependent on another target gets dep.not-for-target (warn, 03 D5). The published RPMs of the package on the other targets stay. They are retired on that target (11.5).

11.5 Remove (retire) a package (Q6, UX-05)

  1. Delete the entry from repoctl.yaml.
  2. repoctl pin. It removes the orphaned lock entry.
  3. git commit -am "feat!: remove DIR from the set" && git push.
  4. repoctl plan. Expected: no node for DIR. retired.published/NAME (info) gives the RPMs that stay published.
  5. The RPMs stay in the repo by default. Clients that installed them keep them.
  6. Optional, explicit: repoctl repo prune --target T --package NAME --all. This is a dry run. Read it. Then add --apply. 05 specifies how prune makes a new snapshot and records the removed NVRs.
  7. Optional, on the clients: remove the package through config management, or add Obsoletes to the release package.
  8. git worktree remove packages/DIR. Keep the package branch. It holds the history of the published NVRs.

Rules for repo prune --package NAME --all:

  • NAME is a source package name. It must be retired on the target. Otherwise: exit 1, prune.not-retired. The rule "never delete the newest NVR of a package" stays for kept packages.
  • The repoclosure check after the prune must pass. When a kept package requires NAME, the prune stops and names that package.
  • A retired package is not in any closure of the publish gate. It never blocks a publish, and repoctl never suggests a rebuild for it.

The publish summary does not show "removed" counts, because publish never removes. It shows "retired: N packages still published" instead. repo diff between two snapshots still marks removed files with -.

11.6 Rename

  • Rename the dir only (for example, rocm-smi to rocm-smi-lib): change dir in repoctl.yaml, run git worktree move and repoctl pin. plan matches manifest entries by branch or URL, commit and target, not by dir. Thus, the node stays current with the note "dir renamed from rocm-smi". Nothing builds.
  • Rename the RPM (Name in the spec): this is a spec change with a new commit. The new name builds. Add Obsoletes and Provides for the old name in the spec. The old source package name is then retired (11.5).
  • Rename the branch: push the new branch, change branch, run repoctl pin. The commit stays the same, so nothing builds.

11.7 Add or drop a target

  • Add: add the entry to targets. plan shows each node of the target with reason new-target. The first publish of the target makes its first snapshot (05). Add the target to the mirror job (05).
  • Drop: delete the entry. The published repo of the target, its GHCR package and the mirror stay. status shows "target el8: not in repoctl.yaml, still published". To stop serving it, remove it from the mirror job (05).

12. External package mirrors (UX-33)

  • The bare clone of an external package moves from $XDG_CACHE_HOME/repoctl/git to $XDG_DATA_HOME/repoctl/git/HASH.git. It can hold commits that are not pushed, so it is not cache.
  • repoctl makes it with git clone --bare URL and the fetch refspec +refs/heads/*:refs/remotes/origin/*. It does not set remote.origin.mirror. Thus, git -C packages/DIR push origin BRANCH works as in a normal clone.
  • repoctl clean does not touch $XDG_DATA_HOME/repoctl/git. repoctl clean --git deletes a clone only when it has no worktree and no commit that is not on the remote. Otherwise it lists the clone and keeps it (git.mirror-unpushed).
  • repoctl doctor warns about external clones with commits that are not pushed.
  • The pin warning "not on origin" and the rebuild banner print the push command for the package.
  • 02 section 4 and 04c help xdg change: "Cache is safe to delete" stays true, because the clones are not in the cache any more.
