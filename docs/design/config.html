Configuration

This chapter specifies the configuration of repoctl. It gives the layers and their precedence, the set discovery, repoctl.yaml, repoctl.lock, the user config, the environment variables and the XDG directories. It also says what the first release covers and where the schema stays open.

  • Three files: repoctl.yaml (what to build, committed), repoctl.lock (pinned commits, written by repoctl) and the user config (how and where on this host).
  • repoctl takes each value from the first layer that gives it: flag, REPOCTL_* variable, user config, set config, default.
  • Only the set config changes what repoctl builds. Thus the set commit fixes the output.
  • repoctl finds repoctl.yaml as git finds .git: it goes up from the start directory.
  • No secrets and no host paths in repoctl.yaml. Credentials come from git, ssh and the container credential store.
  • Only the cache is safe to delete. The data directory holds staging, the local copy of latest and the clones of external packages.
  • One set has many targets and can take packages from any git server.

Layers and precedence

  1. Command-line flag.
  2. REPOCTL_* variable (environment variables).
  3. User config $XDG_CONFIG_HOME/repoctl/config.yaml: the entry under sets.<set name> first, then the top-level entry.
  4. Set config: repoctl.yaml and repoctl.lock.
  5. Built-in default.

Rule

Layers 1 to 3 change only how and where, for example jobs, sign.key, sign.backend, lock_wait, progress, ui.* and agent. Only layer 4 changes what repoctl builds: packages, branches, commits, targets, mock configs, macros and repos. A key of layer 4 in the user config is an error (config.unknown-key, exit 1). Thus the set commit fixes the output.

repoctl config show prints each value and the layer that gave it (cli.html#cmd-config):

Set discovery

  • The start directory is -C DIR, else REPOCTL_DIR, else the current directory.
  • repoctl goes up from the start directory. The first directory with a repoctl.yaml is the set directory. repoctl does not stop at a .git file. Thus a command in packages/slurm (a worktree) finds the set above it.
  • repoctl stops at the file system root and at a mount point, as git does without GIT_DISCOVERY_ACROSS_FILESYSTEM.
  • The set directory must be in a git work tree. Else repoctl stops with exit 1.
  • The set name is name in repoctl.yaml. All XDG paths use it.
$ cd ~/src/slurm-repo/packages/ucx
$ repoctl status -q | head -1
set       slurm-26.05  ~/src/slurm-repo  (branch builder/slurm-26.05)
$ cd /tmp
$ repoctl status
repoctl: error: no set: no repoctl.yaml in /tmp or in a parent directory
hint: give the set directory. run: repoctl -C ~/src/slurm-repo status
hint: start a new set here. run: repoctl init

These commands work without a set: version, completion, help, schema, skills ls|show|path, mcp tools, config paths (user paths only), doctor (host checks only), init, migrate, repo ls --path DIR and ui (it opens the overview of the known sets).

Rules

  • An unknown key is an error (config.unknown-key, exit 1). apiVersion lets the schema change without silent errors. A key of a newer release also gives this error. Thus the team raises minRepoctl in the commit that first uses a new key, and an older binary stops with contract.newer-file and the hint to upgrade (stored files).
  • The schema also has keys for later releases (narrow now, open later). repoctl rejects them with config.unsupported.
  • The file has no build order. repoctl makes the graph from rpmspec --buildrequires and the Provides of each package (build.html#graph).
  • The file has no secrets and no host paths. It has no registry credentials and no publish path. Push credentials come from the container credential store of the user (publish.html#registry). Git credentials come from the git and ssh setup of the user.
  • Every target has plugins: [rpmautospec]. Without it, a rebuild commit gives no new NVR. Else config.invalid, exit 1. doctor and status show the plugins of each target.
  • A package has exactly one of branch and path.
  • At most one package has role: release, and that package has path. Else config.invalid, exit 1. The release package is in-tree (signing.html#release).
  • A target that has a latest stays in targets. To stop it, set state: retired. Without the entry, no repoctl command can act on its OCI package.
  • name and targets[].id never change after the first publish. They give the OCI package STORE/SET-TARGET, the XDG paths, the set lock and sets.NAME of the user config. A new name or id gives a new OCI package without the history of the old one. The first publish of that package stops with set.renamed, because the served tree names the old set or target (rule: first publish). To rename a set, start a new set. To rename a target, add a new target and retire the old one (rename).
  • Package facts (upstream repository, tag filter, notes) live in this file, not in a skill. Thus the CLI and the skills read the same facts.
  • publish needs repo.url, store.oci, sign.keys and sign.release.keyfile. doctor warns when one is missing.

repoctl.lock

The lock file holds the pinned commit of each package. This is the lock of the story run, after repoctl pin:

  pmix:     {branch: pmix/slurm-26.05,    commit: 6644bdf188c30a62ff595435a8170d6566283b70}
  pmix_v5:  {branch: pmix/slurm-26.05-v5, commit: 2dff24ab20d95858ff653a540a9fe4e8753b3aa0}
  pmix_v4:  {branch: pmix/slurm-26.05-v4, commit: 75255956ca468de54df4cbda1e9a455f6cd81534}
  prrte:    {branch: prrte/slurm-26.05,   commit: 58caa8c66db06076290d71dc3b25c5c6a1f2ee37}
  slurm:    {branch: slurm/slurm-26.05,   commit: d42f66a56a3f3f0f788e79fb723e451da2d67ba7}
  openmpi:  {branch: openmpi/slurm-26.05, commit: 65a37e5d2d440f2035a6710a44faa3252d01926d}
  slurm-singularity-exec:
    branch: slurm-singularity-exec/slurm-26.05
    commit: 093012de97ac201aa2063b37ee5d9c130b3703b2
  rocm-smi:
    url: https://git.gsi.de/SDE/packages/rocm-smi.git
    branch: slurm-26.05
    commit: cae3663bc5c9f97abb8e49c8adebfc4bedde98a0
  • Only pin, rebuild, init and migrate write the lock, with an atomic write under a file lock.
  • The lock is a separate file, like go.sum. A version bump changes one line in the lock and nothing in repoctl.yaml.
  • An entry has branch and commit. An external package also has url.
  • An in-tree package has no lock line, and it is never unpinned. Its commit is the last set commit that changes its path. Its lock state is in-tree, or dirty when a file under its path has a change. A Lock result gives it with path and that commit.
  • A dir that is two times in the file, for example after a git merge, gives config.invalid (exit 1). repoctl pin gives the steps after a merge conflict.
  • A missing lock file counts as an empty lock. repoctl migrate converts packages.lock once (cli.html#cmd-migrate).
  • A package without a lock line is unpinned. A lock line without a package is orphaned. The lock states are in lifecycle.html#lock-states.

User config

The user config holds the values of one human on one host. It never says what to build.

The set config lists the keys that the clients trust. The user config only selects the key of this human (signing.html#probe). A user config has no publish path, because no admin writes the served tree.

Environment variables

A REPOCTL_* variable stands in for a flag that the command line does not give. A variable with the empty string counts as not set. The help of each flag names its variable before the default. A value that repoctl cannot use fails the command with exit 1 and names the variable. REPOCTL_PROGRESS, REPOCTL_PROGRESS_LOG and REPOCTL_VERBOSE never fail a command: repoctl writes one note and continues without them.

Rule

repoctl ui and repoctl mcp start run each command without the variables that stand in for a flag, and with REPOCTL_PROGRESS=none. They also remove REPOCTL_ALLOW_UNATTENDED_PUBLISH. Thus a run does what its shown command says. repoctl never writes a token or a passphrase into a config file, a log or a --json result.

  • The data directory is build state. It holds the staged nodes, the local copy of latest and the external clones. A clone can hold commits that are not pushed, so it is not cache.

  • State is kept. The journals feed repoctl logs, the web UI and the agent.

repoctl config paths prints the paths of this set with their sizes (cli.html#cmd-config).

Many targets

  • Node = package × target. repoctl builds each package for each target in its targets list. The default is all targets (model.html#nodes).
  • One graph per target. repoctl builds the SRPM in the mock chroot of the target and reads its requires. Thus %if 0%{?rhel} >= 10 in a spec gives correct edges. repoctl cannot see dynamic BuildRequires (%generate_buildrequires) before the build, and it writes a warning for them.
  • Missing dependency for a target. plan shows the gap before the build: "slurm@el10 needs rocm-smi-devel; rocm-smi is not built for el10" (dep.not-for-target, warn).
  • Staging and publish per target. Each target has its own staging repo in a run and its own OCI package. A publish covers the targets that are ready.
  • Extra RPM repos (targets[].repos) go to mock as --addrepo. A change in these repos can change a build result. repoctl does not rebuild by itself. It shows the advisory buildroot.drift, and the human decides.
  • Client path. targets[].path is the path below repo.url. The mirror job serves each target there.
  • One architecture per target. The architecture of a target is the last part of its mock config name: x86_64 in rocky+epel-9-x86_64. This release supports only x86_64. Another architecture, or a mock config name that does not end with one, gives config.unsupported (exit 1). The client path names the target, so it has no $basearch. A noarch package builds on each target, with the dist tag of that target.
  • Macro files. repoctl gives targets[].macros to mock after the macros of the mock config. Thus a macro file can set %dist, for example %dist .el9~testing in a testing set (lifecycle.html#testing).

Build a package for some targets only, and add or retire a target: lifecycle.html#some-targets, lifecycle.html#targets.

External package repositories

  • git.url on a package points to any git server. The lock stores the URL, the branch and the commit.
  • repoctl keeps one bare clone per URL with the full history in $XDG_DATA_HOME/repoctl/git/HASH.git, because rpmautospec needs the history. HASH comes from the sha256 of the normalized URL, and the clone lock guards each git step on the clone (lifecycle.html#clones). repoctl checkout fetches the clone and makes the worktree.
  • repoctl makes the clone with git clone --bare URL and the fetch refspec +refs/heads/*:refs/remotes/origin/*. It does not set remote.origin.mirror. Thus git -C packages/DIR push origin BRANCH works as in a normal clone.
  • The worktree is attached to the local branch BRANCH of the clone. checkout creates it at the lock commit and moves it only forward (cli.html#local-branch).
  • repoctl clean does not touch the clones. repoctl clean --git runs git worktree prune first. Then it deletes a clone only when it has no worktree and no commit that is not on the remote. Else it lists the clone and keeps it (git.mirror-unpushed).
  • Credentials come from the git and ssh setup of the user. The config never holds them. repoctl doctor checks that each URL is reachable, and it warns about clones with commits that are not pushed.

The steps to add an external package are in lifecycle.html#add-external.

The "generic" test

repoctl must not know the word slurm. The test is the branch main as its own set. main gets a repoctl.yaml: name repoctl, one target for the current Fedora, and the packages repoctl and repoctl-release (in-tree, role: release).

The test passes when repoctl builds and publishes this set with the same commands as a slurm set. It runs on a Fedora host with a personal key, and the snapshot goes to GHCR. The release-version check (signing.html#release) compares the release package with the version in the set name. The name repoctl has no version, so the check is off for this set.

The Fedora RPM repo on GitHub Pages stays the output of the Pages job (decision.html#pages). A CI job that signs and publishes through repoctl without a human is a later feature.
