Build tooling redesign: decision report

Design record. Later documents change parts of this one. 03-build-state.html section 9 lists the changes. Index: index.html.

Date: 2026-11-02. Scope: builder/slurm-* branches of github.com/dennisklein/slurm-repo. Status: hybrid design accepted. Decisions in section 8.

1. Recommendation

Use a hybrid. Write one Go tool on GSI-HPC/go-clikit. The tool is the only part that builds, signs and publishes. Keep mock and rpmautospec as they are. The tool calls them.

Put a CLI, a local web UI and an MCP server on top of the same core. Agent skills call the tool. They do not call mock directly.

Do not use Dagger or BuildKit. The build graph is real, but it is small: 11 nodes, depth 4. Dagger adds a second container layer around mock, which already isolates each build. This layer needs root capabilities and gives little in return.

Do not use agent skills only. A signed release must be deterministic and repeatable. Use the agent for judgment work: version updates, release notes, failed build triage.

2. Current state

2.1 What the scripts do

  • scripts/checkout and scripts/pin manage one git worktree per package from packages.lock.
  • scripts/build calls build <dir> 11 times in a fixed order. Each call makes an SRPM, builds RPMs in mock, then signs and runs createrepo --update on result/el9/.
  • Each build adds result/el9/slurm as an extra repo (--addrepo). Thus, a package can use packages from earlier builds.
  • scripts/list, scripts/rpmlist, scripts/setup, clean, update are helpers.
  • Two agent skills exist: package-info and list-package-updates.

2.2 The real build graph

I read the BuildRequires of all spec files on builder/slurm-26.05. This is the graph. An arrow means "is necessary to build".

Facts from the graph:

  • 11 nodes, 14 edges, 4 levels. Up to 4 builds can run at the same time.
  • The longest chain is munge → pmix → prrte → openmpi.
  • slurm needs 6 other packages. slurm-release needs none.

2.3 Problems

#ProblemEffect
P1The build order is written by hand. munge is built after pmix, pmix_v5 and pmix_v4. All three need munge-devel.On an empty result/, pmix builds against the distribution munge-devel. On a second run, it builds against our munge. The result depends on old state. I did not test this with a real build.
P2Each run builds all 11 packages.A change to one spec costs a full rebuild.
P3All builds run one after the other.Long wall time. The graph allows 4 parallel builds.
P4Each package signs and updates result/ directly.If build 7 fails, result/ has 6 new packages and 5 old ones. The repository is in a mixed state.
P5Output is set -x and one sources.log.It is hard to see progress. An agent must parse free text.
P6The same scripts are on each builder/slurm-* branch.A fix to the tooling must go to 3 branches.

4. Options

A. Dagger (Go SDK), with mock inside

  • Dagger runs each step as a BuildKit container. It caches each step by its inputs. It gives a DAG and parallel runs for free.
  • mock needs root capabilities for its own chroot and mounts. In Dagger, this needs insecureRootCapabilities. The Dagger docs compare this to docker run --privileged.
  • The mock caches (root cache, dnf cache) must be Dagger cache volumes. Else each build downloads the buildroot again.
  • A git worktree has a .git file that points outside the directory. If you mount the worktree into a container, git does not work and rpmautospec fails. You must clone first. The current script already does this.
  • The GPG key must go into the engine as a secret. Signing in a container is possible but adds a trust question.
  • Gain: caching and parallel runs. Cost: a Dagger engine daemon, a second isolation layer, privileged containers, and a new API for the team.

Variant A2: Dagger without mock. Build each package in a clean rockylinux:9 container with dnf builddep and rpmbuild. This removes the privileged layer. But you lose the mock rpmautospec plugin and the standard Fedora/EL build path. You must copy that logic yourself. I do not recommend it.

B. Raw BuildKit (LLB or Dockerfile)

Same problems as A, with a lower-level API and no SDK for the graph logic. Not useful here.

C. Go tool on go-clikit

  • One binary. It reads packages.lock, runs rpmspec to get BuildRequires and Provides, and makes the graph from them. No hand order.
  • It calls git, mock, rpmsign and createrepo_c as child processes. mock stays the isolation layer.
  • go-clikit has the parts: cobratree (commands), progress + cliprogress (live tree, plain lines for CI, JSONL event log), fanout (bounded parallel pools), cliout (tables and JSON), doctor (setup checks), fsutil (atomic writes, locks), localweb (web UI with htmx and SSE), progress/mcpprogress (MCP progress).
  • sind and brig use the same pattern: CLI plus tool ui. sind also has an MCP server. skyhook/radar shows the same idea for Kubernetes: one binary, live graph UI, MCP server.
  • Cost: new Go code to maintain. My estimate: 2,000 to 4,000 lines for all phases. This is a guess.

D. Agent skills only

  • Claude reads the specs, decides the order, and runs the scripts.
  • Each run can be different. Each run costs tokens. A run needs Claude to be available.
  • This is not acceptable for a signed release. It is good for work that needs judgment.

E. Hybrid: C + agent skills + MCP (recommended)

The Go tool does all deterministic work. Skills and MCP give Claude a safe, typed interface to the tool. See section 6.

F. Other options I checked

  • Make with stamp files + mock. A Makefile gives a DAG and make -j. Very cheap. But the graph is still written by hand, and there is no UI and no JSON. A good fallback if you want no new code.
  • mock --chain. It builds a list of SRPMs and retries failed ones. It does not use the dependency graph. It does not sign or publish.
  • COPR, OBS, Koji. Full build systems with graphs and UIs. They need servers and operation work. Too large for 11 packages.

6. Recommended design

6.1 Layers

6.2 One build run

  • Input key of a node = hash of: package commit SHA, mock config and macros, and the keys of its dependencies. Same key means same input. The tool skips that node. rpmautospec gets the release from git history, so the same SHA gives the same NVR.
  • Each build uses --addrepo on the staging repo of this run, not on the published repo. This solves P1.
  • Parallel mock builds need a unique root per job (mock --uniqueext). The tool sets it.
  • The tool writes a JSONL event log for each run. The CLI, the web UI and MCP read the same events.

6.3 Commands (draft)

tool doctor              # replaces scripts/setup checks: mock group, gpg name, plugins, disk
tool checkout [dir...]   # replaces scripts/checkout
tool pin [dir...]        # replaces scripts/pin
tool graph [--json|--dot]
tool plan                # what will build, and why (which key changed)
tool build [dir...] [--jobs N] [--force]
tool publish             # sign, createrepo, swap into result/
tool list / tool query   # replaces scripts/list and scripts/rpmlist
tool logs <dir>
tool clean | tool update
tool ui                  # local web UI: graph, live logs, repo contents
tool mcp                 # MCP server over stdio for Claude

Each command has --json. Results go to stdout. Progress goes to the terminal or to the event log, as go-clikit requires.

6.4 Agent skills on top

SkillStatusWhat it does
package-info, list-package-updateskeepRead upstream releases. Later, read the package list from tool list --json.
bump-packagenewUpdate one spec on its package branch, commit, tool pin, tool build <dir>. Stop before publish.
triage-buildnewRead tool logs --json of a failed node. Find the cause. Propose a fix.

Rule: skills never call mock, rpmsign or createrepo directly. publish stays a human step.

6.5 Where the tool lives (decided)

A new orphan branch main in slurm-repo holds the Go module. main becomes the default branch. Each builder branch then holds only data: packages.lock, a small config file (mock target, repo name), packages/slurm-release, and CLAUDE.md. This solves P6.

GitHub Pages carries two things:

  • Docs site. Same structure as the GSI-HPC/sind site, but with its own color theme.
  • RPM repo for current Fedora. It has the tool RPM and a <name>-release RPM. The release RPM installs the GPG key and the .repo file. The tool RPM has Requires on all system tools. Thus, one dnf install gives a ready workstation.

Proposed CI flow: a tag on main builds the RPMs in a fedora container and attaches them to a GitHub Release. The Pages job collects the RPMs of all releases, runs createrepo_c, signs repomd.xml, and deploys docs and repo together. No gh-pages branch is necessary.
