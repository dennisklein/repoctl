Build

This chapter specifies how repoctl builds a set: the graph of each target, the plan, the run in mock, the staging repository, and the states of nodes and runs. It also specifies the set lock, the soname check, rebuilds, logs and the mock roots. Publish starts where this chapter ends (Publish and snapshots).

  • repoctl makes one graph per target. It builds each SRPM in the chroot of the target and reads its requires.
  • The plan gives each node one action: build, current, staged or skip. Only a new commit builds.
  • A run builds into its own staging repository. The published repository and latest do not change.
  • A failed node blocks its dependents. The other nodes continue. The good nodes stay staged for the next plan.
  • One build per user and host at a time. There is no queue: a second build stops with exit 7.
  • After each node build, the soname check compares the new build with the published build. "Unchanged" is a result, not an advisory.
  • A rebuild is an empty commit Rebuild: TEXT. rpmautospec raises the release, so each build has a new NVR.

Graph per target

A node is one package built for one target, written DIR@TARGET (nodes). repoctl makes one graph for each target. An edge from A to B means: B needs a package of A to build. The two nodes of an edge are always on the same target.

To find the edges, repoctl builds the SRPM of each package in the mock chroot of the target (mock --buildsrpm). It builds the SRPM from a detached worktree of the commit, never from packages/DIR (the run). It reads the requires of the SRPM and matches them against the Provides of the other set packages on the same target. rpmspec in the same chroot gives the Provides. Thus a condition such as %if 0%{?rhel} >= 10 in a spec gives the correct edges for each target.

The SRPM cache (~/.cache/repoctl/srpm/) keeps the result for each key. The key is the sha256 of four inputs: the package commit, the mock config of the target (the output of mock -r CONFIG --debug-config), the content of the macro files of the target, and the versions of mock and of the plugins of the target. All sets share the cache, but two sets with other macros or another mock config never share an entry. The first plan of a target builds all SRPMs and can take minutes. After that, only a new commit or a change of these inputs makes a new SRPM. repoctl writes each entry to a temporary file and then renames it. Thus a reader never sees a part of an entry, and two writers of one key give the same entry. The cache is safe to delete.

Sources

A package branch has the layout of Fedora dist-git. The spec, the patches and the small source files are in git. The large source archives are not in git, and .gitignore names them. The sources file sources gives the SHA-512 of each archive, one line per file. All package branches of the story have this layout, also the branches that do not come from Fedora, for example rocm-smi and slurm-singularity-exec. An in-tree package has the same layout below its path. This is the sources file of slurm at d42f66a:

SHA512 (slurm-26.05.4.tar.bz2) = 9ad6e078a6be67d8ad1dbcdd7e07d97af56c30c2e058a49ce3db3073ee77e26a29d6c12843e65605f1223ccbbfe778895ae53e3826dbf7037ac97b9b0147ed7e

repoctl reads the Source and Patch lines of the spec in the chroot of the target, as spectool does. Each line gives one file. repoctl puts the files into one directory and gives it to mock --buildsrpm --sources.

  • Fetch. The source cache is $XDG_CACHE_HOME/repoctl/sources/sha512/HEX/FILE, for all sets. The Fedora lookaside cache is https://src.fedoraproject.org/repo/pkgs/NAME/FILE/sha512/HEX/FILE, with NAME from upstream.fedora. repoctl writes each download to a temporary file, checks it, and then renames it into the source cache.
  • Checksum. repoctl accepts only the SHA512 form of a line. A file whose SHA-512 is not the value of its line is never used: source.mismatch. Thus a new archive with an old name stops the build.
  • No network. repoctl uses only the source cache. A file that is not in the cache gives source.unreachable. Thus a host builds without network after one plan of the same commits.
  • Failure. In plan and graph, a source problem is a warning on the node. The node keeps its plan action. In the build, the node then fails in step srpm with the failure class srpm, and error.code holds the problem code.

Rule

The sources file is part of the commit. Thus the commit fixes the content of every source, and a source never changes the build identity (build identity). To change an archive, change the spec and the sources file in one commit, for example with sha512sum --tag FILE for the new line.

repoctl checkout --create --from fedora forks a Fedora dist-git branch with this layout (checkout --create). repoctl clean --cache deletes the source cache (repoctl clean).

Plan

repoctl plan shows what repoctl build with the same arguments does, and why. It builds nothing and writes no run. repoctl build makes the same plan as its first step.

The baseline of the plan is latest: the RepoManifest in the local copy of latest of each target (RepoManifest). First, repoctl compares the digest of latest in the registry with the local copy (freshness check). When latest is newer, or when no local copy exists, plan and build stop with state.behind (exit 13), and the hint gives repoctl repo pull. When the registry is not reachable, the plan uses the local copy and prints the warning registry.unreachable.

The plan takes the package commits from repoctl.lock. A selected worktree that is not in-sync with the lock gives the error lock.dirty, as in build: the plan still shows all rows, and then exits 5. A worktree that is not in-sync and that no selected node uses gives only the warning worktree.dirty, and the plan still uses the lock. With --from worktree, it takes the HEAD commit of each worktree. A run from worktrees is unpinned and never publishable. repoctl never builds uncommitted changes, because rpmautospec reads commits.

Rule

A change in a dependency, in the mock config, in a macro file or in an upstream repo is never a plan reason. It gives an advisory (advisory codes). The human decides, and repoctl rebuild makes the build.

Why

The build identity is the package commit plus the target (build identity). A rebuild of all dependents after each library change gives new NVRs with no change in content. repoctl trusts the ABI promise of upstream, and the soname and closure checks tell when this trust is wrong.

Selection and dependencies

Selectors name the nodes (selectors). The selected nodes are the roots. A selected node with action build needs the RPMs of its dependencies:

  • A dependency with action build builds first, in the same run. Thus repoctl build slurm also builds ucx when ucx has a new commit.
  • A current dependency comes from the local copy of latest.
  • A staged dependency comes from the staged view of the plan (staging).

A change in ucx never selects slurm. --with-deps and --rdeps add the transitive dependencies or reverse dependencies to the selection. In a build, they change the result only with --force. A run of a subset is partial. Publish works on the plan, not on one run: it takes all staged nodes of a target, from any run of this user (what a publish takes).

The text output shows the exceptions and a totals line. Rows of a package with the same action and reason on all targets merge, and the current nodes fold into one line per target. -v shows all rows; --json always has them. --check exits 11 when a node would build, for CI and timers. The plan also says if an open advisory blocks a publish of this plan. This is the plan of the story at 17:49:

Staging and node reuse

Each run has its own staging repository for each target: $XDG_DATA_HOME/repoctl/SET/staging/RUN/TARGET/, with the sub-repos slurm, slurm-source and slurm-debuginfo (from repo.name). The staging is not signed. It is in the data directory, not in the cache, because it is build state (XDG directories).

A node that ends ok in a run is a staged node until a publish takes it. The next plan gives it the action staged and names its run (fromRun). A later build does not build it again. When a staged node is a dependency, mock gets it through the staged view. Thus a failed run keeps its good nodes.

  • Only a node with the terminal state ok in the journal of its run is staged. This is also true for a canceled or an abandoned run.
  • A node of an unpinned run (--from worktree) is never staged. Its RPMs stay in the staging of that run for a test. The next plan from the lock builds the node, also when the human pins the same commit later.
  • When two runs have an ok build of one node (same commit and target), the newest run wins. Example: a forced build of a staged node. The newest run is fromRun, and publish takes its files. The older copies are not staged, and repoctl clean can delete them.
  • Staging belongs to one user on one host. Another admin does not see it and builds the node again. A home directory that two hosts share does not change this: the plan stages only the nodes of runs whose origin.host is this host (runs of another host).
  • A new commit of the package ends the reuse. The plan action is then build.
  • The repodata of a staging lists only the RPMs of ok nodes. When a node fails or is canceled after some of its RPMs are in the staging, repoctl removes them and updates the repodata.
  • At plan.ready, repoctl makes one staged view per target in the work directory of the run. It is a repository with links to the artifact.added files of exactly the staged nodes of the plan, and its own repodata. mock gets the staged view, never the whole staging of an older run. Thus a build sees no RPM of a failed, canceled, older or abandoned node.
  • Each staged node keeps its record draft next to its RPMs: the buildroot lock of mock, the sha256 and URL of each source archive, and the run facts. Publish writes the supply chain records from it (supply-chain.html#capture).
  • repoctl clean keeps a staging that holds staged nodes or a publishable target (repoctl clean). A human can still delete a staging by hand. Thus the plan checks that each file of a staged node is there with its size. Else the node gets the action build with the reason staging-missing. Publish checks the sha256 of each file that it takes. A file that is gone or changed stops the publish with run.staging-missing, and the next plan builds the node again.

The run

repoctl build makes a plan, starts a run and builds each node with action build in mock. A run has an id r-YYYYMMDD-HHMM-xxx, an origin (cli, ui, mcp or ci) and a journal. The run holds the set lock from its start to its end (set lock).

  1. Preflight: repoctl checks mock, the mock group, the mock config of each selected target, the rpmautospec plugin and the free disk. The free disk must be at least 10 GiB in the data directory, 10 GiB in the cache directory, 1 GiB in the state directory and 20 GiB in /var/lib/mock (requirements). A failure stops the run before it starts (exit 9, host.not-ready). Build does not sign, so there is no GPG check.
  2. Plan: repoctl makes the plan (plan) and writes the event plan.ready.
  3. Nodes: a node starts when each dependency is ok, current or staged, and a job slot is free. Each node runs the steps srpm, rpm and stage. Step srpm makes a detached git worktree of the commit of the node in the work directory of the run, with the full history that rpmautospec reads. It makes the worktree from the repository of the package: the set repository, or the bare clone of an external package. An in-tree package gets a worktree of the set repository at its commit. Step rpm builds the SRPM of step srpm, and artifact.added records the sha256 of that SRPM. The soname check runs at the end of step rpm (soname check). Step stage copies the RPMs into the staging and runs createrepo_c --update, so that the next node sees them.
  4. Stage: step stage of one target runs for one node at a time. It holds a lock of the run and the target in the process of the run. createrepo_c writes the new repodata into a temporary directory, and repoctl then renames it into place. Thus a mock that reads the staging through --addrepo sees the old or the new repodata, never a part of it. A node becomes ok after the staging.updated event of its stage step. A dependent starts only after that.
  5. End: repoctl writes the final repodata of each staging, the run result and the event run.finished. After an ok run, the last line is the Next line, for example Next: repoctl publish. A failed run ends with hints and no Next line, for example hint: el9 is publishable now. run: repoctl publish --target el9.

Rule: a run reads no worktree

After plan.ready, repoctl never reads packages/DIR. A human can edit, commit or check out in a worktree during a run, and the run still builds the commits of its plan. The work directory of a run is $XDG_CACHE_HOME/repoctl/mock/SET/RUN/. repoctl deletes the worktrees in it at the end of the run.

Each mock call gets --uniqueext with the run and the job slot, so that parallel builds have their own roots. It also gets --resultdir in the work directory of the run, and the macros and plugins of the target (targets). --addrepo adds the local copy of latest, the staging of this run, the staged view of the plan and targets[].repos.

Why the staging of the run

A node builds against the new builds of its own run, never against a half-written published repository. Thus the build order comes from the graph, and the result does not depend on old state (problems of the scripts).

Jobs and order

The job count is the maximum number of nodes in mock at the same time. It comes from -j, then REPOCTL_JOBS, then jobs in the user config, else 2 (user config). Each mock build uses all CPUs, so a high value gives little. When more nodes are ready than slots are free, the node with the most dependents starts first, then the oldest.

Failures

When a node fails, each node that depends on it becomes blocked. The other nodes continue: keep going is the default. With --fail-fast, repoctl starts no new node after the first failure and cancels the running nodes.

A failure has a class: srpm, builddep, build, stage, mock, host, timeout, canceled or internal (shared names). For srpm, builddep, build and stage, the inputs are wrong, and a retry gives the same failure. For host (no disk space, no mock group, a repo metadata error), a retry can help after the human repairs the host. No space on a device (ENOSPC) in any step gives the class host, also in step stage. The skill triage-build selects its playbook by the class.

A failed write of the journal ends the run. repoctl starts no new node, stops the running nodes with the class internal, and tries to write run.finished with the state failed and exit 1. When that write also fails, the readers show the run as abandoned.

Each step has a time limit, and mock must write output. The limits are keys of the user config (user config). They do not change the build result.

KeyDefaultLimitResult

The node then ends failed with the class timeout. error.step names the step, and the message names the limit. The other nodes continue, as after any failure. When build.timeout.run ends, repoctl cancels the run as repoctl cancel does (cancel). Thus a hung mock never holds the set lock for longer than its limit.

Rules for the start and the end of a run

  • Before run.started, build takes the set lock (set.busy, exit 7), compares the selected worktrees with the lock (lock.dirty, lock.missing-package, exit 5) and runs the preflight (exit 9). A stop there writes no run files and gives no run id. Thus the MCP result has no Run in items.
  • After run.started, a plan error, for example state.behind or graph.cycle, ends the run without plan.ready. run.finished then has the state failed, the exit code of the problem and no nodes.
  • canceled wins over failed. A run that a human, a signal or build.timeout.run stops ends canceled with exit 130, also when a node failed before.
  • At a cancel, the running, waiting and queued nodes end canceled. A node that waits for a canceled node also ends canceled, not blocked.
  • With --fail-fast, the first failure stops the run in the same way: the open nodes end canceled, and the dependents of the failed node end blocked. The run ends failed with exit 3.

There is no queued run state. The exit codes of all commands are in the CLI reference (exit codes). Command: repoctl build. Terminal frames: live tree, failure summary.

Set lock and no queue

Three different things have the name "lock". The help and the messages always say which one.

Lock file
repoctl.lock in the set: the pinned commits, committed to git (lock file).
Set lock
$XDG_RUNTIME_DIR/repoctl/SET.lock: one writer per set at a time, for one user on one host. It records the holder: command, pid, host, user, start time and run id. Without XDG_RUNTIME_DIR, for example after su, in cron or in CI, the path is $XDG_STATE_HOME/repoctl/SET.lock.
Host mock lock
/var/lib/mock/.repoctl.lock: shared by each command that runs mock, exclusive for mock update and mock clean, for all users and sets of the host (mock roots).

A command that writes the set or its build state takes the set lock: checkout, pin, rebuild, build (for the whole run), publish, repo pull and the repo commands that make a snapshot, sign add, retire, remove and deployed, release write, clean, mock update and mock clean. repo verify takes it shared. A read command takes no set lock and never waits. repoctl check takes none, so a check can run while a build runs. Each command block gives its lock (commands).

All sets share the bare clone of an external package. Each git step on the clone also takes its clone lock (external package clones).

When another process holds the set lock, a command waits up to --lock-wait (default 0: no wait). While it waits, it prints the holder. When the time ends, it stops with exit 7 and the problem code set.busy.

Rule: no build queue

A second build of the same user on the same host stops at once with exit 7 (set.busy). The message names the running run. This is true in the CLI, in the UI and in MCP.

$ repoctl build slurm
repoctl: error: set slurm-26.05 is busy: repoctl build holds the set lock (run r-20261102-1750-a3f, pid 48213 on hpc-a1)
hint: watch that run. run: repoctl runs latest --follow
hint: wait for it. run: repoctl build slurm --lock-wait 2h

Rule: the set lock after logout

systemd removes $XDG_RUNTIME_DIR at the last logout of the user, unless lingering is on. A build in tmux, under nohup or as a detached child of the UI or MCP can live longer than the login. Thus the holder checks every 30 s that the lock path still names the file that it locked (same device and inode). On a mismatch, it takes the lock again at the same path, and the run continues. When another process has the lock, the run starts no new node, acts as at repoctl cancel, writes the warning set.lock-lost and ends canceled (exit 130). The doctor check build.linger warns when lingering is off.

The set lock ends with its process. Thus a stale set lock cannot stay, and no command removes one. Two admins have two set locks on two hosts. They share no lease. Publish compares latest with its base in step 1 and in step 7 (two admins). The team coordinates in its own channel (humans and hosts).

Soname check after a node build

At the end of step rpm, repoctl compares the sonames that the new RPMs provide with the sonames of the newest published build of the node. The published sonames come from the provides list of the node in the RepoManifest of latest.

  • A soname is gone, and a kept set package requires it: repoctl writes the required advisory soname.removed/DIR@TARGET (advisory codes). The publish gate decides if it blocks (publish gate).
  • No soname is gone: the result is unchanged. repoctl writes it into the node record as checks.soname: unchanged. This is a result, not an advisory.

The plan and the UI show the result in the row of the node: "sonames unchanged: rebuild not necessary". While the node is in the run, its soname advisory is pending (advisory states). The optional ABI check (abi.changed, needs libabigail) also runs after the node build.

In the story, ucx 1.22.1 keeps libucp.so.0, libuct.so.0 and libucs.so.0. The result of ucx@el9 and ucx@el10 is unchanged. Thus the rebuilds of slurm, openmpi and slurm-singularity-exec are not necessary. Dennis wants them, and they do no harm: each has a new NVR.

Why a result and not an advisory

An advisory asks the human for a step. An unchanged soname asks for nothing. The record shows that the check ran. Thus "no advisory" and "not checked" do not look the same.

Rebuild

repoctl rebuild DIR... --reason TEXT prepares a new build of a package with the same version. It does not start a build. For each package, repoctl adds an empty commit Rebuild: TEXT to the package branch, then pins it in repoctl.lock. rpmautospec counts commits, so the release goes up by one, and the changelog shows the reason. The next plan gives the action build with the reason rebuild on all targets of the package.

  • The reason is required, with at least 8 characters. The UI dialog has the same rule.
  • The worktree of each dir must be in-sync: its HEAD is the lock commit, and no tracked file has a change (lock states). Else repoctl stops with exit 5 and lock.dirty.
  • repoctl adds the commit on HEAD. This is the local branch of the package (local branch), or the detached HEAD of a shared branch that another worktree has. After the pin, the worktree is in-sync at the new commit.
  • All or nothing: repoctl checks every dir before the first commit. When a check fails, it makes no commit and does not write the lock. When a commit fails, repoctl resets each branch of this call to its lock commit. Thus the same command again after a failure gives one new release, not two.
  • repoctl fetches the remote branch first and warns when it has new commits.
  • repoctl never pushes. The Next lines give the push of each package branch and the commit of the lock.
  • A rebuild applies to all targets of the package, because the commit is per package.
  • An in-tree package has no package branch. Its commit is the last set commit that changes its path, so an empty commit does not change it. A DIR that names an in-tree package stops the rebuild with exit 1 and rebuild.in-tree, before repoctl makes a commit. A glob that matches an in-tree package leaves it out with the same code as a warning. To build an in-tree package again, change a file below its path, for example its changelog, and commit the change to the builder branch.
  • --dry-run shows the new NVRs and commits nothing.

Why a commit

Each build gets a new NVR, so two builds never share an NVR. Fedora mass rebuilds work the same way: rpmautospec raises the release for each commit, also for an empty one. The reason stays in git and in the changelog.

The word "rebuild" means only this command, on all surfaces. The MCP tool repoctl_rebuild makes the same local commits, pins them and does not push (MCP tools). The web UI has the Rebuild dialog (Rebuild dialog). Synopsis and exit codes: repoctl rebuild.

Forced builds

repoctl build --force builds the selected nodes into staging, also when they are current. The plan reason is forced. This is for tests, for example after a change of the mock config. The commit does not change, so rpmautospec gives the same NVR.

Rule: a forced build of a current node

A forced build of a current node is never staged. The plan asks "commit in latest?" before "ok in a run of yours?", so the next plan keeps the node current. Thus publish never takes the forced build, and repoctl clean deletes it as a staging without staged nodes. A forced build of a node that is not current is a normal build: it is staged, and the newest run wins (staging).

The publish checks nvr.reused and nvr.removed apply to each build that a publish takes. Publish refuses a new commit that gives an NVR that latest holds with other content (nvr.reused, exit 12), for example a spec without %autorelease. It also refuses an NVR that the removed[] list of the RepoManifest holds (nvr.removed), because clients can still have it (checks before the first signature). To publish a new build of the same version, use repoctl rebuild.

Why

Clients and mirrors expect that one NVR always has the same content. A second file with the same NVR and other content gives checksum errors on the clients, or two different packages with one name.

A change in a mock config, a macro file or an extra repository is not in the build identity. It gives the advisory mock.drift or buildroot.drift. Use repoctl rebuild to build against the change. Use --force only to try it.

Cancel and abandoned runs

repoctl cancel [RUN] stops a running build of this user on this host. The default is the running run of the set. repoctl sends SIGINT to the process that holds the set lock. That process stops its mock children (SIGTERM to the process group of each child, SIGKILL after 60 s), marks its open nodes canceled, keeps the staging and the logs, and exits 130. When the holder is on another host or is another user, cancel stops with exit 1 and cancel.not-holder. There is no queue, so there is no queued run to cancel. The cancel button of the web UI has the same scope and names the origin of the run. The Run of a run that has a cancel request has cancelRequested (by, user, reason, force, at). The CLI, the web UI and MCP show interrupting from it until the run ends.

  1. The first Ctrl-C in the terminal of the build does the same as cancel. The tree shows interrupting until the mock children end, at most 60 s.
  2. A second Ctrl-C sends SIGKILL to the mock children and exits at once. repoctl cancel --force does the same for a run without a terminal, for example a run of the UI or of MCP. A second repoctl cancel without --force changes nothing: it prints that the run is interrupting.
  3. After a second Ctrl-C or --force, the journal has no run.finished, and the readers show the run as abandoned. repoctl prints hint: clean the mock roots: run: repoctl mock clean.

A crash also gives an abandoned run. The set lock ends with the process, so the next build can start. The ok nodes of a canceled or abandoned run stay staged. A publish run cannot be canceled after its push step starts (publish order). Command: repoctl cancel. Web UI: finished runs.

Mock roots and verify roots

Each target names a mock config: rocky+epel-9-x86_64 for el9 and rocky+epel-10-x86_64 for el10 (targets). repoctl runs on Fedora. The mock chroots are EL9 and EL10.

repoctl gives each root that it makes a name with --uniqueext. The name starts with repoctl-UID, the numeric id of the user. Thus repoctl knows its own roots, and the roots of two users or two sets never meet.

It also makes or updates the verify root of each target. repoctl mock clean runs mock --clean and --scrub=bootstrap on the roots of this user whose name starts with repoctl-UID. It never touches a root of another user or a root without this prefix. Both commands take the set lock.

Rule: the host mock lock

The mock config, its root cache and its package cache are shared by all users and sets of the host. Thus repoctl has one host mock lock, the file lock /var/lib/mock/.repoctl.lock, which the group mock can write. Each command that runs mock takes it shared: build (for the whole run), plan, graph, list, show, mock shell and the publish step verify-el. repoctl mock update and repoctl mock clean take it exclusive. Thus they never change a cache while a repoctl mock of any user runs. A busy host mock lock waits up to --lock-wait, then stops with exit 7 and mock.busy.

repoctl mock shell TARGET opens a shell in a shell root, for debugging. The doctor check sign.verify-el says when a verify root is missing.

$ repoctl mock shell el10 -- rpm -q --whatprovides rocm-smi-devel
no package provides rocm-smi-devel

A change in the mock config or the macros of a target gives the advisory mock.drift for the nodes that the old config built. It does not start a build (forced builds). Command: repoctl mock.

Help topic build-state

repoctl help build-state prints this text. The other topics are in the CLI reference (help topics).

BUILD STATE

The build identity of a node is the package commit plus the target.
repoctl builds each node of one identity once.

"repoctl plan" gives one action for each node:
  current   the commit is in latest of the target: nothing to do
  staged    built for this lock in a run of yours, not published yet
            (a run --from worktree never stages a node)
  build     no build of this commit for this target. The reason says why:
              commit-changed  the package commit changed
              rebuild         "repoctl rebuild DIR" made an empty commit
              new-package     the package is new in the set
              new-target      the target is new for the package
              forced          --force (for tests; a forced build of a
                              current node is never staged or published)
              staging-missing the staging of a staged node is gone
  skip      not selected, and no selected node needs it

repoctl does not rebuild dependents by itself. A change in a library can
need a rebuild of its dependents. An advisory says so (soname.removed,
closure.broken, provider.changed). You decide.

To build again with the same version:
  repoctl rebuild DIR --reason TEXT
This makes an empty commit "Rebuild: TEXT" in the package branch and
pins it. rpmautospec raises the release. Push the package branch, then
commit and push repoctl.lock.

A change in a mock config, a macro file or an extra repository is not
in the build identity. It gives the advisory mock.drift or
buildroot.drift. Use "repoctl rebuild" to build against the change.

Staging is in $XDG_DATA_HOME/repoctl/SET/staging/. It holds the nodes
that are built for the lock and not published yet. "repoctl clean" keeps
these nodes. The next plan shows them as "staged".
