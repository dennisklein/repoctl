Tool releases

This chapter specifies how repoctl itself reaches the admin hosts and the HTTP server: the RPM repo on GitHub Pages, the tool repository key that signs it, the first install, the upgrade, and what to do when the key or a release is bad.

GitHub Pages

  • Docs site at https://dennisklein.github.io/repoctl/. It has the structure of the GSI-HPC/sind site, with its own theme.
  • RPM repo of repoctl at /rpm/, with one directory per $releasever: rpm/43/x86_64/ and rpm/44/x86_64/ for the Fedora releases that are not end of life, rpm/9/x86_64/ and rpm/10/x86_64/ for EL. A Fedora directory holds the tool RPM repoctl, the release RPM repoctl-release and the mirror job RPM repoctl-mirror. An EL directory holds only repoctl-release and repoctl-mirror, for the HTTP server. Both are noarch. The release RPM installs the public tool repository key as /etc/pki/rpm-gpg/RPM-GPG-KEY-repoctl and /etc/yum.repos.d/repoctl.repo with baseurl=https://dennisklein.github.io/repoctl/rpm/$releasever/$basearch/, gpgcheck=1 and repo_gpgcheck=1. The tool RPM requires all system tools: mock, mock-rpmautospec, rpm-sign, createrepo_c, git and gnupg2. Thus one dnf install gives a ready admin host.

CI flow: a tag v* on main starts the release job. It makes the tool RPM in a fedora container for each Fedora directory, and the two noarch RPMs once. It signs the RPMs, runs createrepo_c in each directory and signs each repomd.xml. It attaches the RPMs and the signed tree rpm-repo.tar to a GitHub Release. The Pages job deploys the docs and the rpm-repo.tar of the newest release together. It needs no key. No gh-pages branch is necessary.

The tree keeps, in each directory, the newest patch release of the newest three minor releases of repoctl, and the newest repoctl-release and repoctl-mirror. Each older RPM stays on its GitHub Release. Thus the site stays far below the size limit of GitHub Pages (1 GB). A copy of the newest repoctl-release is also at rpm/, for the first install.

Rule

The Pages repo has its own key, the tool repository key (below). It is not a key of a package set, and it never signs set RPMs. Only the release job and the yank job can read it.

Admin hosts install repoctl from this repo or from the RPMs of a GitHub Release. repoctl runs on Fedora only (model.html#humans). The slurm sets and the tool share one GitHub repository; whether the sets move to their own repository is an open question (delivery.html#open). The delivery phases are in delivery.html#phases.

Tool repository key

The tool repository key signs the RPMs of repoctl and the repodata of the RPM repo on Pages. The tool RPM runs on the admin hosts, next to the signing keys of the admins. Thus a stolen tool repository key can give the admins a repoctl that signs bad set RPMs. The key never signs a set RPM, but it guards the trust of the clients.

First install of the tool

dnf cannot check the first key. The human checks it by hand, once on each host. The same steps install the mirror job on the HTTP server.

  1. Download https://dennisklein.github.io/repoctl/rpm/repoctl-release-1-1.noarch.rpm.
  2. Compare its sha256 (sha256sum) with the value in the table above. If it is different, stop and tell the team.
  3. Install the file: sudo dnf install ./repoctl-release-1-1.noarch.rpm.
  4. Compare the fingerprint of the installed key with the fingerprint in the table: gpg --show-keys /etc/pki/rpm-gpg/RPM-GPG-KEY-repoctl.
  5. On an admin host, install the tool: sudo dnf install repoctl. On the HTTP server, install the mirror job: sudo dnf install repoctl-mirror.
  6. On an admin host, run repoctl doctor --only host. The check tool.repo-key must pass.

Upgrade repoctl

The text of repoctl help upgrade gives the steps on one admin host. A run that is active during the upgrade ends with the old binary. A UI or MCP server that runs during the upgrade starts no new child (host.stale-server).

UPGRADE

Upgrade repoctl on an admin host:
  1. Read the release notes. They name new keys and fields, a new
     apiVersion and a new minRepoctl.
  2. repoctl runs --state running    in each set: wait until no run is active
  3. repoctl ui --stop               stop the web UI server
  4. sudo dnf upgrade repoctl repoctl-release
  5. repoctl skills install          also --project in each set that has them
  6. repoctl check --install-timer   in each set with a timer: it rewrites
                                     the units when they changed
  7. Restart each agent session that runs "repoctl mcp start".
  8. repoctl doctor                  host.stale-server, skills.version-mismatch
                                     and check.timer-unit must pass
Upgrade the mirror job on the HTTP server: sudo dnf upgrade
repoctl-mirror. The timer runs the new job at its next start.
Two admins can work with two releases for a short time. An older
binary reads newer files, but it never rewrites a file with a field
that it does not know (contract.newer-file, exit 1).
When all admins have the new release:
  - raise minRepoctl in repoctl.yaml if the release notes ask for it;
  - for a new apiVersion, upgrade the HTTP server first, then run
    "repoctl migrate --api".
Commit and push the change of repoctl.yaml.

Rotation of the tool repository key

  1. 180 days before key A expires, make key B as above. Add it to the environment as a second secret.
  2. Release a repoctl-release that ships A and B in one file (F14). The release job still signs with A. The binary of this release lists A and B as current.
  3. Wait 30 days. On each admin host without B, doctor warns with the fix sudo dnf upgrade repoctl-release.
  4. Sign the next release with B. Delete the secret of A. The binary of this release lists A as retired.
  5. Release a repoctl-release with only B.
  6. Erase A on each host: sudo rpmkeys --erase on Fedora, config management on the HTTP server. A release RPM cannot remove a key (F16).

A host that did not get B in step 3 fails with a signature error of dnf. On that host, do the first install again.

Compromise of the tool repository key

Treat the key as compromised when the secret can have leaked, when a job read it without a release, or when the repo holds an RPM that no release job made.

  1. Delete the environment secret. Turn off the release workflow.
  2. Make a new key C as above. Put it into the environment.
  3. Yank each release that the old key signed after the first possible time of the leak (bad release).
  4. Release a fixed version and a repoctl-release with only C, signed with C. Change the fingerprint and the sha256 in this chapter, in the README and in the release notes. The binary of this release lists the old key as revoked.
  5. Tell all admins and the owner of the HTTP server in the team channel. dnf on their hosts cannot verify C.
  6. On each host, erase the old key, then do the first install again. On an admin host, also run sudo dnf reinstall repoctl.
  7. Compare the NVR and the sha256 of each installed repoctl RPM with the GitHub Releases. If a host installed an RPM that no release job made, offboard the signing key of the admin of that host (offboarding).

A bad tool release

  1. Add the version to packaging/yanked.txt on main, in a reviewed commit.
  2. Start the yank job (a manual workflow on main). A maintainer approves it in the environment.
  3. The job makes and signs the repodata without the yanked RPMs. It attaches a new rpm-repo.tar to the newest GitHub Release, and the Pages job deploys it.
  4. Mark the GitHub Release of the bad version as yanked in its title and its notes. Keep its files.
  5. Tag a fix release with a higher version. dnf does not downgrade, so a host with the bad release gets the fix with dnf upgrade.

Records of the tool

A GitHub Actions job builds the repoctl binary and the tool RPMs (decision.html#home). GitHub artifact attestations fit this case. The action actions/attest-build-provenance writes SLSA provenance v1 for each file, signs it with a short-lived Sigstore certificate of the workflow identity and stores it in the attestation store of the repository. This gives SLSA Build L2, and L3 when a reusable workflow does the build. No key to keep. Admins verify a download with gh attestation verify.

permissions:
  contents: write
  id-token: write        # Sigstore certificate for the workflow
  attestations: write    # GitHub attestation store
steps:
  # … build the binary and the RPMs into dist/ …
  - uses: actions/attest-build-provenance@v4
    with:
      subject-path: dist/*
$ gh attestation verify repoctl-0.4.0-1.fc43.x86_64.rpm --repo dennisklein/repoctl
✓ Verification succeeded!

The RPMs of the tool also have the OpenPGP signature of the Pages repo key for dnf. The attestation is an extra record for admins. It does not change the install.
