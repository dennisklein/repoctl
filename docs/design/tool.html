Tool releases

repoctl reaches the admin hosts and the HTTP server as signed RPMs from its own repo on GitHub Pages. This chapter follows the life of a tool release, from the repo and its key to a bad release and the records of the tool.

  • GitHub Pages carries the docs site and the RPM repo of repoctl. A tag v* on main starts the release job that fills the repo.
  • The tool repository key never signs a set RPM. Only the release job and the yank job read it, after a maintainer approves the job.
  • The human checks the first key by hand, once on each host. After that, dnf checks the signatures.
  • A team upgrade changes the set (minRepoctl, migrate --api) only after all admin hosts have the new release.
  • The key rotates 180 days before it expires. Nobody extends the expiry date.
  • The yank job removes a bad release from the repodata. A fix release with a higher version replaces it.
  • Each tool file gets a GitHub artifact attestation as an extra record for admins.

The RPM repo on GitHub Pages

GitHub Pages serves the docs site at https://dennisklein.github.io/repoctl/. The site has the structure of the GSI-HPC/sind site, with its own theme.

Below it, /rpm/ is the RPM repo of repoctl. It has one directory per $releasever. The directories rpm/43/x86_64/ and rpm/44/x86_64/ are for the Fedora releases that are not end of life. The directories rpm/9/x86_64/ and rpm/10/x86_64/ are for EL on the HTTP server.

The release RPM installs the key as /etc/pki/rpm-gpg/RPM-GPG-KEY-repoctl and the repo file /etc/yum.repos.d/repoctl.repo with baseurl=https://dennisklein.github.io/repoctl/rpm/$releasever/$basearch/, gpgcheck=1 and repo_gpgcheck=1.

A tag v* on main starts the release job:

  1. The job makes the tool RPM in a fedora container for each Fedora directory, and the two noarch RPMs once.
  2. It signs the RPMs, runs createrepo_c in each directory and signs each repomd.xml.
  3. It attaches the RPMs and the signed tree rpm-repo.tar to a GitHub Release.
  4. The Pages job deploys the docs and the rpm-repo.tar of the newest release together. It needs no key. No gh-pages branch is necessary.

The tree keeps, in each directory, the newest patch release of the newest three minor releases of repoctl, and the newest repoctl-release and repoctl-mirror. Each older RPM stays on its GitHub Release. Thus the site stays far below the size limit of GitHub Pages (1 GB).

Admin hosts install repoctl from this repo or from the RPMs of a GitHub Release. repoctl runs on Fedora only (model.html#humans). The slurm sets and the tool share one GitHub repository. Whether the sets move to their own repository is an open question (delivery.html#open).

Tool repository key

The tool repository key signs the RPMs of repoctl and the repodata of the RPM repo on Pages. The tool RPM runs on the admin hosts, next to the signing keys of the admins. Thus a stolen tool repository key can give the admins a repoctl that signs bad set RPMs.

Rule

The tool repository key is not a key of a package set, and it never signs a set RPM. But it guards the trust of the clients.

First install

dnf cannot check the first key. The human checks it by hand, once on each admin host and on the HTTP server.

  1. Download https://dennisklein.github.io/repoctl/rpm/repoctl-release-1-1.noarch.rpm.
  2. Compare its sha256 (sha256sum) with the row "First install" of the key table (tool repository key). If it is different, stop and tell the team.
  3. Install the file: sudo dnf install ./repoctl-release-1-1.noarch.rpm.
  4. Compare the fingerprint of the installed key with the row "Fingerprint" of the key table: gpg --show-keys /etc/pki/rpm-gpg/RPM-GPG-KEY-repoctl.
  5. On an admin host, install the tool: sudo dnf install repoctl. On the HTTP server, install the mirror job: sudo dnf install repoctl-mirror.
  6. On an admin host, run repoctl doctor --only host. The check tool.repo-key must pass.

Upgrade repoctl

The text of repoctl help upgrade gives the steps on one admin host. A run that is active during the upgrade ends with the old binary. A UI or MCP server that runs during the upgrade starts no new child (host.stale-server).

UPGRADE

Upgrade repoctl on an admin host:
  1. Read the release notes. They name new keys and fields, a new
     apiVersion and a new minRepoctl.
  2. repoctl runs --state running    in each set: wait until no run is active
  3. repoctl ui --stop               stop the web UI server
  4. sudo dnf upgrade repoctl repoctl-release
  5. repoctl skills install          also --project in each set that has them
  6. repoctl check --install-timer   in each set with a timer: it rewrites
                                     the units when they changed
  7. Restart each agent session that runs "repoctl mcp start".
  8. repoctl doctor                  host.stale-server, skills.version-mismatch
                                     and check.timer-unit must pass
Upgrade the mirror job on the HTTP server: sudo dnf upgrade
repoctl-mirror. The timer runs the new job at its next start.
Two admins can work with two releases for a short time. An older
binary reads newer files, but it never rewrites a file with a field
that it does not know (contract.newer-file, exit 1).
When all admins have the new release:
  - raise minRepoctl in repoctl.yaml if the release notes ask for it;
  - for a new apiVersion, upgrade the HTTP server first, then run
    "repoctl migrate --api".
Commit and push the change of repoctl.yaml.

Rotation of the tool repository key

  1. 180 days before key A expires, make key B as in the key table. Add it to the environment as a second secret.
  2. Release a repoctl-release that ships A and B in one file (F14, client facts). The release job still signs with A. The binary of this release lists A and B as current.
  3. Wait 30 days. On each admin host without B, doctor warns with the fix sudo dnf upgrade repoctl-release.
  4. Sign the next release with B. Delete the secret of A. The binary of this release lists A as retired.
  5. Release a repoctl-release with only B.
  6. Erase A on each host: sudo rpmkeys --erase on Fedora, config management on the HTTP server. A release RPM cannot remove a key (F16).

A host that did not get B in step 3 fails with a signature error of dnf. On that host, do the first install again.

Compromise of the tool repository key

Treat the key as compromised in each of these cases:

  • The secret can have leaked.
  • A job read the secret without a release.
  • The repo holds an RPM that no release job made.
  1. Delete the environment secret. Turn off the release workflow.
  2. Make a new key C as in the key table. Put it into the environment.
  3. Yank each release that the old key signed after the first possible time of the leak (bad release).
  4. Release a fixed version and a repoctl-release with only C, signed with C. Change the fingerprint and the sha256 in this chapter, in the README and in the release notes. The binary of this release lists the old key as revoked.
  5. Tell all admins and the owner of the HTTP server in the team channel. dnf on their hosts cannot verify C.
  6. On each host, erase the old key, then do the first install again. On an admin host, also run sudo dnf reinstall repoctl.
  7. Compare the NVR and the sha256 of each installed repoctl RPM with the GitHub Releases. Find each host that installed an RPM that no release job made. Offboard the signing key of the admin of that host (offboarding).

A bad tool release

  1. Add the version to packaging/yanked.txt on main, in a reviewed commit.
  2. Start the yank job (a manual workflow on main). A maintainer approves it in the environment.
  3. The job makes and signs the repodata without the yanked RPMs. It attaches a new rpm-repo.tar to the newest GitHub Release, and the Pages job deploys it.
  4. Mark the GitHub Release of the bad version as yanked in its title and its notes. Keep its files.
  5. Tag a fix release with a higher version. dnf does not downgrade, so a host with the bad release gets the fix with dnf upgrade.

Records of the tool

The release job builds the repoctl binary and the tool RPMs on GitHub Actions. GitHub artifact attestations fit this case, and they need no key to keep.

For each file, the action actions/attest-build-provenance writes SLSA provenance v1. It signs the provenance with a short-lived Sigstore certificate of the workflow identity. It stores it in the attestation store of the repository. This gives SLSA Build L2, and L3 when a reusable workflow does the build.

permissions:
  contents: write
  id-token: write        # Sigstore certificate for the workflow
  attestations: write    # GitHub attestation store
steps:
  # … build the binary and the RPMs into dist/ …
  - uses: actions/attest-build-provenance@v4
    with:
      subject-path: dist/*

Admins verify a download with gh attestation verify:

$ gh attestation verify repoctl-0.4.0-1.fc43.x86_64.rpm --repo dennisklein/repoctl
✓ Verification succeeded!

The tool RPMs also have the OpenPGP signature of the tool repository key for dnf. The attestation is an extra record for admins. It does not change the install.
