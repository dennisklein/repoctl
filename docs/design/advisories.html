Advisories

An advisory is the result of a deterministic check. It tells the human that a rebuild or another step can be necessary, and it suggests a step. The human decides. This chapter covers the ids, codes and states, the data, the check and its timer, and the publish gate.

  • All surfaces use one id, CODE/SUBJECT, for example closure.broken/pmix@el9.
  • repoctl computes advisories and does not store them. It stores only dismissals (a committed file per team) and acceptances (the journal and the snapshot annotation).
  • The three levels are info, warn and required. Only info and warn advisories can be dismissed.
  • A required advisory blocks a publish only when the publish changes a package in its closure. A publish that fixes the problem passes.
  • --accept-advisory ID --reason TEXT overrides one block for one publish. --yes never accepts an advisory.
  • Each admin host runs its own daily check timer. The check is read-only, so two timers do no harm.
  • A failed or old check never shows as "no advisories".

Four checks read the inputs and compute one list of advisories. The CLI, the web UI, MCP and the publish gate read the same list (kinds Advisory and AdvisoryList, kinds).

These results are not advisories:

  • A soname check that finds no removed soname. The node record keeps checks.soname: unchanged (soname check).
  • dep.not-for-target, a plan warning (graph per target). It is about the next build, not the published state, and it has no closure.
  • Drift of an adopted manifest entry from the import. The entry has no buildroot file, so buildroot.drift, mock.drift and provider.changed skip it until the next build of the node writes one (adopted entries).

Facts and factsDigest

Each code has one fixed facts shape, so the same inputs give the same facts on each host:

  • The facts hold only values of the inputs: NVRs, capabilities, versions, hashes and repo ids. They never hold a time, a host name, a user or a path.
  • Each list has no duplicates and is sorted in byte order of the key in the column Sort.

  • factsDigest is sha256: plus the hex SHA-256 of the JSON Canonicalization Scheme form (JCS, RFC 8785) of facts. No other field goes into the digest, also not hostFacts.
  • The facts shape of a code changes only with a new apiVersion (versioning). Thus two repoctl versions with the same apiVersion give the same digest for the same inputs.
  • The schema has one $defs/Facts… entry per code (output.schema.json).

States

StateConditionRules
pendingThe check needs a build that did not end, for example soname.removed for a node that is still in the run.Only the UI and repoctl advisories show it, during a run. The end state of the node ends it: only ok can give an advisory (soname check).
openThe check finds the problem now, and no dismissal matches.-
dismissedA dismissal in .repoctl/advisories.yaml has the same id and the same factsDigest.A dismissal never matches a required advisory.
goneThe check does not find the problem any more.Not stored, so not in the contract enum. The journal of the check records advisory.gone.

A dismissed advisory is open again when a human undismisses it or the dismissal becomes stale (dismissal file). Two examples: a newer upstream version changes the facts of upstream.release, and thus the digest. A package builds a retired package again, and its closure.broken becomes required.

A run advisory (soname.removed, abi.changed) comes from a node build and lives in the record and the journal of its run. It is gone in these cases:

  • At run.finished, repoctl checks each soname.removed of the run again, on latest plus the staging of the run. It is gone when no newest NVR there requires a removed soname, for example because a dependent built later in the same run. The run journal records advisory.gone.
  • Its node is published (gate).
  • A newer run stages a new build of the node.

Two admins compute the same advisories from the same inputs: latest in the registry, the closure repos and the release feeds. Thus the check result can stay per user, and only the dismissals must be shared.

One code depends on the host: mock.drift compares the mock config and the macros of this host with the manifest.

  • The hash of this host is outside the digest. Thus a dismissal of mock.drift matches on each host with a different config.
  • On a host whose config equals the manifest, the advisory does not exist, and the dismissal is not stale there.
  • The default closure repos also come from the mock config of the host (check).
  • The doctor check mock.config-differs (warning) finds a target whose mock config on this host differs from the config of the newest build in latest.

Dismissal file

# .repoctl/advisories.yaml
# Written by repoctl advisories dismiss. Commit and push it.
apiVersion: repoctl/v1alpha1
dismissed:
  - id: upstream.release/slurm-singularity-exec
    facts: sha256:802ef6…                 # factsDigest at dismiss time
    note: 3.2.1 only changes the docs
    by: d.klein@gsi.de                    # git config user.email
    at: 2026-10-21T09:14:52Z
  • repoctl writes the file atomically and keeps the entries sorted by id. Thus two dismissals of different ids seldom give a git conflict.
  • repoctl does not commit the file. dismiss prints the commit and push command. repoctl status shows "advisories.yaml: not committed" when the file has changes.
  • Publish does not require a commit of the file, because the file does not change the output of a build. Publish never reads it: the gate uses only required advisories.
  • An invalid file gives the warning advisories.invalid: a YAML error, git conflict markers, an unknown apiVersion or a bad entry. repoctl then ignores the whole file, so no advisory is dismissed.
  • After a git conflict, keep the entries of both sides and remove the markers. Two entries with the same id are valid: repoctl uses the one with the newest at. The next dismiss or undismiss writes one entry per id.
  • An entry is stale when its id is gone, its digest does not match, or its advisory is required now. A mock.drift entry whose id this host does not find is not stale, because another host can still find it.
  • A new set does not copy this file from the old set (new set).

Dismiss and undismiss

repoctl advisories dismiss ID... --note TEXT adds a dismissal for each open id. The note is required, with at least 8 characters, and is public in the set repository (public information). repoctl advisories ls --dismissed adds the dismissed entries and marks the stale ones. repoctl advisories undismiss --stale removes all stale entries.

CaseExitProblemHint
dismiss: the advisory is required.1advisory.not-dismissablerepoctl publish --accept-advisory
dismiss: the id is not open.1advisory.unknown-
dismiss or undismiss: the file is invalid. They do not change it.1advisories.invalid-
undismiss --stale: in the last check, a code did not run ok on each target. Thus a failed input never removes a valid dismissal.1check.incompleterepoctl check

dismiss and undismiss write only this file. They take no set lock, because a build can hold it for an hour. They take a short file lock, $XDG_RUNTIME_DIR/repoctl/SET.advisories.lock, for the read, the change and the rename of the file.

$ repoctl advisories dismiss upstream.release/slurm-singularity-exec --note "3.2.1 only changes the docs"
dismissed upstream.release/slurm-singularity-exec (facts sha256:802ef6…)
Next: git add .repoctl/advisories.yaml && git commit -m "chore: dismiss upstream.release/slurm-singularity-exec" && git push

After the commit and the push, the whole team sees the dismissal.

repoctl check

repoctl check computes all advisories that need no build, for each target. Its inputs are:

  • the RepoManifest and the repodata of latest (check pulls only the repodata, not the RPMs),
  • the closure repos of the target,
  • the upstream release feeds,
  • the mock config of this host.

The closure repos of a target are the RPM repos that its clients have: targets[].closure_repos in repoctl.yaml. Without this key, they are the enabled repos of the mock config of the target, plus targets[].repos. In the story, the closure repos of el9 are Rocky 9 BaseOS, AppStream and CRB, and EPEL 9.

The check finds the closure of a closure.broken as the gate does (step 3), on latest. For example, an old ucx NVR that still provides libucp.so.0 puts ucx into the closure of closure.broken/openmpi@el9.

Check lock

  • The check is read-only. It takes no set lock and can run while a build runs.
  • It takes the check lock $XDG_RUNTIME_DIR/repoctl/SET.check.lock: one check per set for one user on one host. A second check (the timer, Check now, MCP or a terminal) starts no second run. It waits for the running check and gives its result, with the note "check running since TIME".
  • The holder of the check lock writes the journal (kind: check) and check.json in the state directory. It writes check.json to a temporary file and renames it, so a reader never sees a part of it.
  • A check run without run.finished whose check lock nobody holds is abandoned.

Failed and narrowed checks

A failed or a narrowed check never loses an advisory. When one input fails, for example an upstream repo that is not reachable, the other checks still run. check.json records the failure (upstream.unreachable), and the exit code is 1.

  • check.json holds one result per code and target: the time, ok or failed, the digest of latest that it used, and the advisories. upstream.release has one result for all targets.
  • A code that fails on a target keeps the advisories of the last good result. Each one has carriedFrom, the time of that result. The CLI and the UI show "check failed: CODE; from the check of TIME". Thus closure.broken/pmix@el9 stays in status, in Needs you and in the gate rows.
  • A check writes no advisory.gone for a code and target that failed or did not run.
  • --code and --target run some codes and targets only. Their results replace only those entries in check.json.
  • The publish step cache runs all codes except upstream.release on the new local copy of each published target. It reads the same repodata as the gate, takes the check lock and replaces their results in check.json. Thus after a publish, a fixed advisory is gone and an accepted break shows at once. When this fails, the publish gives a warning, and the old result stays.

Check timer

Each admin host runs its own timer for each set that the admin works on. The result is ready when the work day starts.

repoctl check --install-timer writes the template pair and starts one instance for the set. The instance name is the escaped set directory (systemd-escape --path). --remove-timer stops and removes the instance, for example for a set that you no longer work on.

  • The units call /usr/bin/repoctl, so the timer runs the new binary after an upgrade.
  • When a template file differs from the template of this repoctl version, --install-timer writes it again, runs systemctl --user daemon-reload and prints "updated".
  • A moved set directory leaves an instance with the old path (check.timer-orphan, health signals). Its fix is systemctl --user disable --now repoctl-check@INSTANCE.timer, then --install-timer in the new directory.
  • A user service does not have the environment of a login shell. The service reads the optional file ~/.config/repoctl/check.env (mode 0600), for example with GH_TOKEN=…. The human writes it; repoctl never does.
  • Without a token, repoctl tries gh auth token, then asks GitHub without a token (upstream.rate-limited).
# ~/.config/systemd/user/repoctl-check@.service
[Unit]
Description=repoctl check for the set in %I
After=network-online.target

[Service]
Type=oneshot
EnvironmentFile=-%h/.config/repoctl/check.env
ExecStart=/usr/bin/repoctl -C %I check --quiet
Nice=10
# ~/.config/systemd/user/repoctl-check@.timer
[Unit]
Description=Daily repoctl check for the set in %I

[Timer]
OnCalendar=*-*-* 06:00:00

[Install]

The timer prints nothing, and it does not fail on an open advisory. For an alert on a new required advisory or a failed check, add the optional drop-in:

# ~/.config/systemd/user/repoctl-check@.service.d/alert.conf (optional)
[Unit]
OnFailure=repoctl-check-alert@%i.service

[Service]
ExecStart=
ExecStart=/usr/bin/repoctl -C %I check --quiet --check --min-level required

With --check --min-level required, an open required advisory (exit 11) or a failed check (exit 1) fails the unit. systemd then starts the unit of OnFailure=. repoctl does not ship that unit: it is a local script, for example with notify-send or mail.

  • repoctl runs on Fedora hosts only. On a workstation, lingering is optional, so the linger note is info, not a warning.
  • The onboarding of an admin has the step repoctl check --install-timer (onboarding, help team).
  • At offboarding, the timers of the other admins still run, and their hosts do nothing. The admin who leaves runs --remove-timer on each of their hosts, or the host goes away (offboarding).
  • A retired set needs no timer, and the health signals do not apply to it. Each admin runs --remove-timer at the end of the set (end of a set).

Publish gate

The gate runs in the check step of publish (checks before the first signature), for each target of the publish:

  1. Make the result tree of the target. It holds the published repo of latest and the nodes that the publish takes (what a publish takes). A new NVR is the newest NVR of its name, because publish refuses an older one (nvr.older).
  2. Run dnf repoclosure --newest on the result tree plus the closure repos of the target. The result is a list of broken requirements: an RPM and a requirement.
  3. Name the advisory of each broken requirement, and find its closure. One advisory holds all broken requirements of its subject (facts).
    • A package of this publish provided the soname in its newest published build. Its new build does not provide it: soname.removed/PROVIDER@TARGET. The closure is the provider plus each package that requires the soname.
    • Every other broken requirement: closure.broken/REQUIRER@TARGET, with REQUIRER the package that built the RPM. The closure is REQUIRER, plus each set package with an older NVR in the tree that provides the requirement.
  4. A required advisory blocks the target when its closure contains a package of the publish on that target. An acceptance of the human removes the block.
  • A required advisory whose closure has no package of the publish does not block. The summary shows it as "open, not changed by this publish".
  • A broken requirement of an old NVR (not the newest of its name) never blocks. The gate finds it with a second dnf repoclosure run without --newest: only the second run gives it. The summary shows it as info, with a prune suggestion. repoctl check does not run the second repoclosure.
  • The gate checks each soname.removed of a taken node again on the result tree. When no newest NVR there requires the soname, the advisory is gone, for example because this publish also takes a rebuilt dependent.
  • A retired package is never in a closure. Its broken requirements are closure.broken at level warn.
  • Info and warn advisories never block.

Why the result tree

The gate uses the result tree, not the last check result. Thus the advisory is gone after a fixing publish. An unrelated, urgent fix on the same target does not wait for the fix of the advisory.

Example

A blocked publish fails with exit 12 and the problem code advisory.open. Its humanAction is accept-advisory with the exact command. The output of the variant:

hint: rebuild the dependents into this publish. run: repoctl rebuild openmpi --reason "ucx: libucp.so.0 removed"

When the gate cannot run

The gate fails closed:

  • When repoctl cannot read the repodata of the result tree or of a closure repo, the publish stops in step check with advisory.gate-unavailable (exit 13). The message names the repo.
  • No acceptance overrides this stop, and the last check result never stands in for the gate.
  • This applies to each kind that runs the gate, also prune and import.
  • Run the publish again when the repo answers.

Acceptance

  • --accept-advisory takes an id, not a code. One flag accepts one advisory. It does not accept a later advisory with the same code.
  • --reason is required with --accept-advisory, with at least 8 characters. One reason covers all ids of the call.
  • Only the gate in step check knows if an id blocks. An id that does not block this publish stops the publish in step check with advisory.not-blocking (exit 12), before the first signature. The output has the envelope and the problem. Thus a human cannot accept an advisory in advance.
  • An acceptance does not change what the clients can install. After an accepted soname.removed, a client that has a requirer installed cannot update the provider, and a new host cannot install both. This stays so until the requirer has a new build in latest.
  • The acceptance is valid for this publish only. repoctl writes the event advisory.accepted (id, factsDigest, reason, user, host) to the journal and the same list to the snapshot annotation io.repoctl.advisories.accepted.
  • An unattended publish with a blocking advisory fails with exit 12.
  • An acceptance needs a human. Without a terminal, publish refuses --accept-advisory with publish.unattended-refused (exit 6), also when REPOCTL_ALLOW_UNATTENDED_PUBLISH is 1. In the web UI, the confirm dialog is the step of the human (confirm).
  • MCP has no accept tool. An acceptance is a step of a human (humanAction).
$ repoctl publish --target el9 --accept-advisory soname.removed/ucx@el9 \
    --reason "openmpi loads libucp only in mca_pml_ucx; our clusters use ob1"

The summary of the publish has one gate row per required advisory: id, blocks and accepted. For soname.removed, the row also lists the affected requirer NVRs (affected in the variant output). Web UI: publish review, accept for this publish. Flags: repoctl publish.

Recovery path

repoctl help advisories prints the full path for a required advisory:

REQUIRED ADVISORIES

A required advisory blocks a publish only when the publish changes a
package in its closure.

  1. repoctl advisories show ID          read the facts and the closure
  2. Fix the package, one of:
       repoctl rebuild PKG --reason "..."   a rebuild is enough (it pins)
       change the spec in packages/PKG, commit, then repoctl pin PKG
  3. git -C packages/PKG push origin BRANCH
     git add repoctl.lock && git commit && git push
  4. repoctl build PKG
  5. repoctl publish --target T          the gate checks the result tree
  6. Optional: repoctl repo prune --nvr OLD-NVR   remove the old broken NVR

An unrelated publish on the same target does not wait for this path.

To publish with a required advisory open, give the reason:
  repoctl publish --target T --accept-advisory ID --reason "..."
Only info and warn advisories can be dismissed:
  repoctl advisories dismiss ID --note "..."

A REQUIRED ADVISORY THAT IS WRONG OR HAS NO FIX

A required advisory is never dismissed. Remove its cause:
  - The clients get the provider from a repo that the check does not
    read: add the repo to targets[].closure_repos in repoctl.yaml,
    commit, push, then repoctl check. The advisory is gone.
  - The requirement in the spec is wrong: fix the spec (step 2).
  - The package is not needed any more: retire it (repoctl help
    packages). Its closure.broken is then a warn advisory, and a
    dismissal can hide it.

A required advisory stays open until its cause changes. Until then, repoctl check --check gives exit 11, and each publish that changes its closure needs an acceptance. A wrong advisory comes most often from closure repos that do not agree with the repos of the clients.
