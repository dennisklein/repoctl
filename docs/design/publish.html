Publish and snapshots

This chapter gives the path of a publish from the admin host to the clients. It covers the publish order, the records, the snapshot format, the mirror job and the rules to keep, prune, restore and delete snapshots. Signing and trust gives the signing rules.

  • GHCR is the authority. The tag latest of each set and target says what is published. All other records are copies.
  • Publish has one fixed order: check, sign, repodata, verify, verify-el, push, tag, cache. Only step 7 (tag) changes what other humans see.
  • A failed push or tag leaves the signed and verified tree, and repoctl repo push completes the publish. repoctl never pushes a tree that did not pass verify and verify-el.
  • There is no lease between admins. Publish compares latest with its base in step 1 and again in step 7.
  • A mirror job on the HTTP server pulls latest, verifies it with the keys of the clients and swaps the served tree. It uses only curl, jq, gpgv and rpmkeys.
  • Publish takes all staged nodes of the plan, per target, and never deletes a file. Prune and restore make a new snapshot, and latest moves forward. Fix forward is the normal way back.
  • A snapshot is one OCI artifact with one blob per file. gc deletes old snapshots only with --apply. It keeps each file that a client can have for keep_removed (default one year) after its prune or restore.

Topology

Clients read the repository from an HTTP server. GHCR holds the snapshots. The set repository and its OCI packages are public. Each admin builds as an own user, on an own host or on a shared host (humans and hosts). repoctl runs on the admin hosts only.

Mirror job

The mirror job is a shell script with systemd units. It ships in the repoctl repository as contrib/mirror/. The RPM repo of repoctl (GitHub Pages) has it as the noarch RPM repoctl-mirror, for EL 9, EL 10 and Fedora.

The job runs on the HTTP server as an own system user. A systemd timer starts it every 5 minutes. The HTTP server needs systemd, curl, jq, gnupg2 and rpm. repoctl does not run there.

# /etc/repoctl-mirror.conf: one mirror line per set and target
# set        target  package                                      served path                             keyring
slurm-26.05  el9     ghcr.io/gsi-hpc/slurm-repo/slurm-26.05-el9   /srv/repos/slurm-repo/slurm-26.05/el9   /etc/repoctl-mirror/keys/slurm-26.05-el9.asc
slurm-26.05  el10    ghcr.io/gsi-hpc/slurm-repo/slurm-26.05-el10  /srv/repos/slurm-repo/slurm-26.05/el10  /etc/repoctl-mirror/keys/slurm-26.05-el10.asc
KEEP_TREES=2

The job reads the RepoManifest apiVersions of its release. A snapshot with another apiVersion fails step 5 (verify), so the job keeps the old tree. Thus the HTTP server gets the new release of the job before the first publish in a new apiVersion (stored files).

One run of the job

Each run takes the lock /run/lock/repoctl-mirror.lock with flock. A second run waits for the first, so a manual run and a timer run never write one tree at the same time. Then the job does these steps for each line:

  1. Get an anonymous pull token and the manifest of latest with curl (OCI distribution API). If the digest equals the served digest, stop.
  2. Check the manifest, else refuse it. The annotations io.repoctl.set and io.repoctl.target equal the set and the target of the line. Each annotation org.opencontainers.image.title is a relative path: each segment has only the characters A-Z a-z 0-9 . _ + -, and no segment is . or ... No two layers have the same title.
  3. Download the missing blobs into .objects/sha256/. Check the sha256 of each blob.
  4. Make a new tree .trees/<set>-<target>/<digest>/ from hard links. Each file gets its path from its title annotation.
  5. Verify the tree with the keyring of the line:
    • Run gpgv on each repomd.xml.asc (exactly one signature).
    • Check the checksums in repomd.xml.
    • Run rpmkeys --checksig on each RPM, with a temporary rpmdb.
    • Check that the root key file has the sha256 of the key file in the root release RPM (rpm -qp --dump).
    • With jq, check that the RepoManifest has an apiVersion that this release of the job reads.
    • With jq and sha256sum, check that each supply chain record has its sha256 in the RepoManifest.
    • Check that each record subject has the sha256 of its file (supply-chain.html#verify).
  6. Check that the snapshot does not go back. The <revision> of each repomd.xml in the new tree must not be lower than in the served tree. createrepo_c writes the time of the repodata step as the revision, and repomd.xml is signed. Thus an old signed snapshot that a token holder tags as latest again stays unserved. A restore or a prune writes new repodata, so it passes.
  7. Write repoctl-snapshot.json into the tree: set, target, digest, publish id and the time of the pull.
  8. Swap: replace the symlink of the served path in one rename. Keep KEEP_TREES old trees. Delete the objects that no tree uses.

Rule

If a step fails, the job keeps the old tree, writes the error to the journal and exits with 1. The next run tries again. The job never serves a tree that its keyring does not verify.

Keyring of a mirror line

Rule

Each mirror line has its own keyring: the key file of the release package that the clients of that set and target have. Config management puts this file at the keyring path in the same rollout as these clients, for example from the release RPM with rpm2cpio. The HTTP server does not install the release packages of the sets.

Thus each mirror line has the same trust as its clients:

  • A snapshot that a key signs before the clients of that set and target have the key stays unserved. This is a second guard behind gate 2.
  • A key change in one set or target does not change what the other lines trust.
  • The deployment record of a target covers its clients and the keyring of its mirror line (signing.html#deployment-record).
  • After a key compromise, config management first replaces the keyring of each mirror line. Then the job serves no new snapshot with a file of the revoked key (signing.html#compromise).

Mirror lines and the served file

The job keeps the served path of each line in .trees/<set>-<target>/served-path. A change of the config takes effect at the next run (add or retire a target):

Change of the configNext run of the job
A new set or target: one new mirror line and its keyringMakes the tree from GHCR.
A line is no longer in the configDeletes the symlink of its served path, the trees of the line and the objects that no tree uses. It writes each deletion to the journal. The URL then gives 404: the target is no longer served.
The line comes backMakes the tree again from GHCR.

The file repoctl-snapshot.json tells repoctl what the HTTP server serves:

{"set": "slurm-26.05", "target": "el9", "digest": "sha256:9d07…",
 "publish": "p-20261103-1412-5e1", "pulled": "2026-11-03T14:15:02Z"}

repoctl status reads <repo.url>/<target.path>/repoctl-snapshot.json and shows served: same, served: behind or served: unknown.

Job health and alerts

Each run writes repoctl-mirror.json, the heartbeat of the line, into the served tree of each mirror line. It writes it also when the digest is the same or a step fails, to a temporary file and then with a rename:

{"set": "slurm-26.05", "target": "el9", "checked": "2026-11-03T14:15:02Z",
 "result": "swapped", "served": "sha256:9d07…", "latest": "sha256:9d07…",
 "behindSince": null, "error": null}
  • result is same, swapped or failed. error is the message of the failed step.
  • behindSince is the time of the first run that saw a latest other than the served digest. It is null when the two are the same.

The job ships these systemd units:

# /etc/systemd/system/repoctl-mirror.service
[Unit]
Description=repoctl mirror job
After=network-online.target
OnFailure=repoctl-mirror-failed.service

[Service]
Type=oneshot
User=repoctl-mirror
ExecStart=/usr/libexec/repoctl-mirror/mirror /etc/repoctl-mirror.conf

# /etc/systemd/system/repoctl-mirror.timer
[Timer]
OnCalendar=*:0/5
Persistent=true

[Install]
WantedBy=timers.target

The config key NOTIFY names an optional command, for example a script that sends a mail or calls a webhook of the team channel. The job ships no mail or chat code.

  • After each swap, the job runs NOTIFY served SET TARGET. Standard input gets the annotations of the new latest: kind, publish id, signer, user and host. Thus the team gets one message for each publish, restore, prune, resign and import, from any admin host.
  • repoctl-mirror-failed.service runs NOTIFY failed. Standard input gets the last 50 journal lines of the job.
  • A failed NOTIFY goes to the journal. It does not change the result of the run.

Without NOTIFY, the journal and repoctl status still show each failure (stale served tree). Who owns the mirror job is an open question.

Records: where the truth lives

Each record other than latest is a copy that names the snapshot that it comes from. model.html#records lists all records of a set, with who writes and reads each one.

Status, the Overview card "Last publish", the sign step and the default key set of repo verify read the annotations of latest. Thus repoctl repo pull gives all of this back after the loss of a host. The shared audit record is the publish history in the RepoManifest of latest (snapshot format).

Pull

repoctl repo pull [REF] makes the local copy equal to a snapshot: latest (the default), a publish id or a digest.

Pull downloads the missing blobs and checks their sha256. It verifies each RPM and each repomd.xml.asc with the keys of sign.keys (all states), then writes the local copy in one rename. Last, it writes snapshot.json, the cache of the annotations (digest, publish id, signer).

snapshot.json is one Snapshot object of the output schema without local, served and gc (contract.html#kinds).

Stale served tree

status also reads repoctl-mirror.json of the served tree (job health). It gives the warning served.stale in two cases:

  • the served tree is behind latest, and behindSince is more than 15 minutes ago (three runs of the job);
  • checked is more than 15 minutes ago: the job does not run.

The warning names the time and the last error of the job. Its hint is read the journal of the mirror job on the HTTP server: journalctl -u repoctl-mirror.service. repoctl doctor (group registry) and the Needs you list of the web UI show the same warning (ui-build.html#needs-you).

Publish order

Publish has one fixed order with eight steps. The journal records each step as a publish.step event with the step name (contract.html#events).

Rule

Steps 1 to 5 change only files of the human who publishes. Step 7 is the only step that changes what other humans see. A publish is a success when step 7 is done.

Several targets

One publish id covers all selected targets. repoctl runs the steps in the order of targets[] in repoctl.yaml:

StepsRunA failure of one target
1 to 5for each target, before repoctl pushes a blobstops the publish of all targets. repoctl pushes nothing.
6 to 8for one target after the otherdoes not stop the other targets.

A publish that tags some targets and not all is a partial publish. It exits with 13, and the run state is failed. Run.publish[TARGET].state gives the result of each target: ok, failed, canceled or skipped. The tree of each failed target stays pushable, and repoctl repo push p-… --target ID completes one target.

Why

The human confirms one summary for all targets, so all targets pass the same checks before the first push. Steps 6 to 8 change only the OCI package of one target. Thus a failed push of el10 does not make the tag of el9 wrong.

Stop and complete

After each step, publish writes publishes/p-…/state.json next to the tree. It holds the publish run as a Run object (contract.html#kinds). Per target, it records the base, the digest of the new manifest and the result of each step.

Rule: pushable tree

A tree is pushable for a target when its state file records verify and verify-el ok, and step 8 of the target is not done. Only a pushable tree whose base is still latest counts for state.unpushed.

repoctl repo push p-… completes the publish, for each target of the publish or for the target of --target ID. Without a publish id, it takes the newest pushable publish.

  1. The state file must record verify and verify-el ok for the target. Otherwise push refuses with publish.not-verified (exit 10).
  2. The files of the tree must give the new manifest digest of the state file. Otherwise push refuses with verify.failed (exit 10).
  3. push reads latest. If latest equals the new digest, step 7 is done. Then push runs only step 8 and records the success in the journal. If latest equals the base, push runs steps 6 to 8 with the compare of step 7. Otherwise push refuses with snapshot.diverged (exit 13).

repoctl clean --publish p-… deletes the tree and its state file. repoctl status names each kept tree that is not pushable, or whose base is not latest, with the hint repoctl clean --publish p-….

First publish and import

A first publish of a target has no base. The registry has no snapshot of the target (no tag latest), the local copy has none, and keys/deployed.yaml has no record for it. The freshness check passes. Gate 2 does not apply, because no client uses the target yet. In the story, the first snapshot of el10 is p-20260912-1403-c21.

An import of an existing repository is different, because clients of the old repository exist. repoctl repo push --from DIR --manifest FILE --target ID makes the first snapshot of a target from a signed tree. It works only when the registry has no snapshot of that target. Else it stops with import.not-empty (exit 13).

The import verifies each RPM with sign.keys and keeps the RPM signatures. It adds the RepoManifest from FILE with modifyrepo_c, adds the root files (snapshot format) and signs the new repomd.xml with one signature. Then it runs verify and verify-el, and pushes p-import-YYYYMMDD. The advisory gate runs as a report and does not block (gate per publish kind).

Rule

Gate 2 applies to an import. Before the import, the human records the deployment of the old key, for example repoctl sign deployed hpc-repo --release slurm-release-26.05-1 --target el9 --path DIR. Only a target that no client uses yet skips gate 2.

What a publish takes

Publish works on the plan, not on one run. For each selected target, publish takes each node with the plan action staged. A staged node has a build for the current lock in an unpublished run of this user (staging and node reuse).

  • Of a staged node, publish takes only the files of its artifact.added events, never a whole staging directory. It checks the sha256 of each file.
  • When two runs have a build of one node, publish takes the build of the newest run (fromRun). The summary names the source run of each node.
  • --run RUN limits the publish to the nodes of one run.
  • Publish never builds. It never signs a node whose plan action is not current or staged.
  • The advisory gate looks at the whole publish, so a dependent that another staged run rebuilt counts (advisories.html#gate).

A target is publishable when each node of the target is current (in the base) or staged. Without --target, publish takes the publishable targets, and the summary names the others.

publish.not-ready (exit 12) stops the publish when a target that --target names is not publishable, or when no target is publishable. --hold NODE makes a target publishable for one urgent publish (urgent fix).

Rule: publish the ready target first

Publish a publishable target before you pin a fix of a package that it shares with a failed target. The commit is per package, so the pin ends the staged node on each target. The publishable target then needs a new build, or a new NVR with the same content when it is already published (the story run).

In the story, the review of el9 at 2026-11-03 14:05 takes the four staged el9 nodes of r-20261102-1750-a3f: ucx, slurm, openmpi and slurm-singularity-exec. These give 38 new RPMs. The 170 RPMs of the base stay, so the new snapshot has 208 RPMs. el10 is not publishable: slurm@el10 failed, and slurm-singularity-exec@el10 is blocked (the blocked page of the web UI).

Urgent fix

A failed, blocked or unbuilt node of another package makes its target not publishable. For an urgent fix, the human holds that node back for one publish. A held node keeps its build in the base, or stays out of the snapshot when the base has no build of it. The publish takes the other staged nodes as usual.

  • --hold NODE needs --reason TEXT with 8 characters or more. A held node that is current or staged is a usage error (exit 2), so nobody holds in advance.
  • The advisory gate runs on the result tree with the base build of each held node. When a taken node needs the new build of a held node, the gate finds the broken requirement and blocks the publish.
  • The summary shows each held node with the NVR that it keeps and the reason. The annotation io.repoctl.held and the publish history record the held nodes with the reason.
  • The lock does not change. The next plan shows each held node with the action build again.

Two admins

Changes are rare, and the team coordinates in its own channel. Thus repoctl has no lease in the registry. The set lock is a local lock: it protects the processes of one user on one host (build.html#lock).

Rule

Publish compares latest with its base two times: in step 1, and in step 7 just before it moves the tag. If latest moved, publish stops with snapshot.diverged (exit 13). The new snapshot stays as a tag that nobody serves, and repoctl repo snapshots --all lists it.

Why

GHCR has no compare-and-swap for tags. The race window is the time between the read and the write of the tag in step 7, less than one second. For a small team that coordinates in a channel, this window is acceptable. A lease would need a second shared record and a way to break it.

In the race window, two publishes can both pass step 7. The second tag write wins, and the first snapshot leaves the chain of latest. Its NVRs reach the served tree only if the mirror job reads latest in that window.

repoctl finds this case when the local copy holds a publish of this user and latest is newer. It walks the parent chain of latest back to the first snapshot that is older than the local copy. If the local publish is not on that chain, pull, status, plan, build and publish warn with snapshot.orphaned (freshness check).

After snapshot.diverged or snapshot.orphaned, run repoctl repo pull, then plan and publish again.

Rule

A run counts as published only when its publish is on the chain of latest. Thus the staged nodes of an orphaned publish are staged again, the next plan shows them as staged, and repoctl clean keeps their staging. The next publish signs them again: the NVRs and the payloads stay the same, only the signatures change.

Why OCI artifacts with one blob per file

The registry stores each blob once. Image layers would bind files to publishes and make a prune hard. A git repository keeps each binary in its history: the clones grow, and one old file cannot be deleted. oras-go does the work inside the Go binary, and GHCR gives a shared state to the team.

Public packages are free. Private packages count against the storage quota of GitHub Packages. The debuginfo repositories are the largest part.

Keep all versions and prune

Rule: keep all versions

Publish adds to the repository. It never deletes. All old versions stay, as with createrepo_c --update in the bash scripts, so clients can still install each old version.

Step 4 (verify) enforces this rule. The new tree must hold each layer of the base manifest with the same title and sha256. Only the files that a prune or a restore removes, the files that a re-sign changes and the repodata files can differ. A missing file gives verify.failed, also when the local copy lost the file.

repoctl repo prune removes NVRs only on request. The dry run is the default, and --apply acts. With --apply, prune is a publish run of kind prune: steps 1 to 8 make a new snapshot without the selected NVRs (checks per kind). The NVRs go into removed[].

Old snapshots still hold the files until gc deletes these snapshots. Thus the registry frees the blobs of a pruned NVR at the earliest retention.snapshots.keep_removed after the prune (default 1y), when gc runs. A prune of debuginfo frees storage only then.

Restore and fix forward

To take back a bad build, fix forward: make a new commit or a rebuild (build.html#rebuild), so that the release goes up, and publish. Clients then update to the fix. This is the normal way back.

A revert of a version bump gives a lower NVR, for example ucx 1.22.0 after 1.22.1. dnf never installs a lower NVR on a client that has the higher one, so publish refuses it with nvr.older (exit 12).

To take back a version, raise Epoch in the spec, or give the old code a version that is higher than the bad one. Then the clients that installed the bad NVR update to the fix, and new clients get the fix.

repoctl repo restore REF is for a broken repository, for example bad repodata. It makes a new snapshot with the files of the older snapshot REF and moves latest to it. latest moves forward to a new digest, never back to the old digest. A REF that names no snapshot of the target gives snapshot.not-found (exit 1).

Restore is a publish run of kind restore: the eight steps with the checks of its kind (checks per kind). The advisory gate also runs (gate per publish kind). The rules of restore:

  • The summary lists each NVR that leaves the repository. It says that clients keep these NVRs, because dnf does not downgrade.
  • These NVRs go into removed[]. Then publish refuses a build that gives one of them again with other content (nvr.removed, exit 12). The hint is repoctl rebuild PKG --reason "…".
  • RPMs in REF that a key in state removed or revoked signed get a new signature from the human who restores (re-sign rules).
  • The new snapshot keeps each release NVR that a deployment record names for the target, also when REF does not hold it. Thus gate 2 and verify-el still find the key file of each signer. The summary lists these NVRs as "kept: deployment record". For example, a restore of el9 to p-import-20260828 keeps slurm-release-26.05-2, the release of the record of d.klein; REF holds only slurm-release-26.05-1.
  • REF can have a RepoManifest of an older apiVersion. Restore reads it and writes the new RepoManifest in the apiVersion of repoctl.yaml (stored files).

After a restore

The lock still pins the commits of the builds that left. plan shows these nodes with the action build, and each build gives a removed NVR again: publish refuses it with nvr.removed. Before the next publish, do one of these steps for each package that the summary names:

  • Run repoctl rebuild PKG --reason TEXT. The release goes up, so the new NVR is newer than the removed one.
  • Or move the worktree to the commit of the build in REF and run repoctl pin PKG --older, because that commit is behind the branch. plan then shows the node as current.

gc and retention

GHCR has no garbage collection that a user starts. repoctl repo gc deletes old snapshots (package versions) in GHCR with the GitHub REST API, and GitHub then frees the blobs that no version uses. The dry run is the default, and --apply acts. Nothing to delete gives exit 4.

Rule

gc never deletes these snapshots. The defaults come from retention.snapshots in repoctl.yaml (config.html#set-config). A flag changes a default for one call.

  • latest;
  • the newest N snapshots of the chain (keep: 10, --keep N);
  • the snapshots younger than D (keep_days: 90d, --keep-days D);
  • for each entry of removed[], the newest snapshot that still holds it, until keep_removed after the publish that removed it (keep_removed: 1y, --keep-removed D).

Thus each RPM that a client can have stays in at least one snapshot for keep_removed. After that time, gc can delete the last snapshot that holds it. removed[] still holds the NVR and the sha256 of each RPM, so nvr.removed still works.

gc deletes the annotations of a snapshot with it, but the publish history in latest keeps each acceptance (snapshot format). gc needs the token scope delete:packages and admin access to the package (registry access). gc never runs unattended, because it deletes history (cli.html#safety).

gc --apply is a run of kind gc with its own journal. It deletes the package versions of one target after the other, oldest first, so the chain from latest has no gap. It writes one gc.deleted event per deleted version: target, publish id and digest (contract.html#events).

Rule: a failed delete

When the GitHub API refuses or fails one delete, gc stops at once. The versions that it deleted before stay deleted, and the journal lists them. gc exits with 13: registry.denied for a missing scope or role, else gc.failed. A second repoctl repo gc --apply continues, because gc computes the list again from the registry.

gc frees the storage of a pruned NVR only after keep_removed: until then, the newest snapshot that holds it stays. A prune removes an NVR from latest, so that no new install gets it. It does not make the registry smaller at once.

Registry outage and loss

GHCR holds the only chain of snapshots. The local copies of the admins and the served tree hold latest, and the mirror job also keeps KEEP_TREES old trees. repoctl has no second store.

Rule: no break-glass

While GHCR does not answer, publish stops with registry.unreachable (exit 13). The mirror job keeps the served tree, and the clients keep working with it. Build and stage the fix in the meantime, and publish it when GHCR answers. Do not copy files to the HTTP server by hand.

Why the team accepts the loss of the chain

Publish never deletes (keep all versions), so latest holds each RPM that is not pruned, with its signature and its supply chain records. Its RepoManifest lists each removed NVR in removed[]. A second store would add a job and a credential only for the older snapshots, the diverged tags and the pruned files. The team accepts their loss.

When an OCI package is deleted, or the organization is lost, re-seed each target from the newest copy of its last latest. Compare the publish id in snapshot.json of each local copy and in repoctl-snapshot.json of the served tree: the served tree can be behind.

When the namespace is gone, change store.oci in a set commit and the package lines of the mirror config (mirror job).

repoctl repo push --reseed --target ID re-seeds one target from the local copy, or with --from DIR from a copy of the served tree. It needs a target without a snapshot in the registry (else snapshot.exists). A re-seed keeps each file as it is, so the clients see no change, and the protections of removed[] and nvr.reused stay.

  • It keeps the RPM signatures, repomd.xml and its signature, the RepoManifest and the supply chain records.
  • It signs nothing, so it needs no signer probe and no gates.
  • It verifies the tree as repo pull does, and runs verify-el with the client trust set.
  • It pushes the snapshot p-reseed-YYYYMMDD of kind reseed without a parent, and moves latest to it.

Then an organization owner sets the new OCI package to public and turns on the inherited access (registry.public). The steps for a human are in the runbook Recover from a registry outage or loss.
