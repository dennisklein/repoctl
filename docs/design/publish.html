Publish and snapshots

This chapter specifies the path of a publish from the admin host to the clients. It gives the publish order, the records of what is published, the snapshot format and the mirror job on the HTTP server. It also gives the rules to keep, prune, restore and delete snapshots. The signing rules are in Signing and trust.

  • GHCR is the authority. The tag latest of each set and target says what is published. All other records are copies.
  • Publish has one fixed order: check, sign, repodata, verify, verify-el, push, tag, cache. Only step 7 (tag) changes what other humans see.
  • A failed push or tag leaves the signed and verified tree. repoctl repo push completes the publish. repoctl never pushes a tree that did not pass verify and verify-el.
  • A mirror job on the HTTP server pulls latest, verifies it with the keys of the clients and swaps the served tree. It uses only curl, jq, gpgv and rpmkeys.
  • There is no lease between admins. Publish compares latest with its base in step 1 and again in step 7.
  • Publish takes all staged nodes of the plan, per target. It adds files and never deletes them.
  • Prune and restore make a new snapshot, and latest moves forward. Fix forward is the normal way back.
  • A snapshot is one OCI artifact with one blob per file. gc deletes old snapshots only with --apply. It keeps each file that a client can have for keep_removed (default one year) after its prune or restore.

Topology

Clients read the repository from an HTTP server. GHCR holds the snapshots and is the authority. The set repository and its OCI packages are public. Each admin builds as an own user, on an own host or on a shared host (humans and hosts). The admin hosts share only the git remote and GHCR. repoctl runs on the admin hosts only.

Mirror job

The mirror job is a shell script with systemd units. It ships in the repoctl repository as contrib/mirror/ and in the release RPMs of repoctl. It runs on the HTTP server as an own system user. A systemd timer starts it every 5 minutes. The HTTP server needs systemd, curl, jq, gnupg2 and rpm. repoctl does not run there.

# /etc/repoctl-mirror.conf: one line per set and target
# set          target  package                                         served path
slurm-26.05    el9     ghcr.io/gsi-hpc/slurm-repo/slurm-26.05-el9      /srv/repos/slurm-repo/slurm-26.05/el9
slurm-26.05    el10    ghcr.io/gsi-hpc/slurm-repo/slurm-26.05-el10     /srv/repos/slurm-repo/slurm-26.05/el10
KEYRING=/etc/pki/rpm-gpg/RPM-GPG-KEY-slurm   # from the release package on this host
KEEP_TREES=2

Each run of the job does these steps for each line:

  1. Get an anonymous pull token and the manifest of latest with curl (OCI distribution API). If the digest equals the served digest, stop.
  2. Download the missing blobs into .objects/sha256/. Check the sha256 of each blob.
  3. Make a new tree .trees/<set>-<target>/<digest>/ from hard links. Each file gets its path from the annotation org.opencontainers.image.title.
  4. Verify the tree with KEYRING. Run gpgv on each repomd.xml.asc (exactly one signature), and check the checksums in repomd.xml. Run rpmkeys --checksig on each RPM with a temporary rpmdb. Check with jq and sha256sum that each supply chain record has the sha256 in the RepoManifest, and that each record subject has the sha256 of its file (supply-chain.html#verify).
  5. Write repoctl-snapshot.json into the tree: set, target, digest, publish id and the time of the pull.
  6. Swap: replace the symlink of the served path in one rename. Keep KEEP_TREES old trees. Delete the objects that no tree uses.

Rule

If a step fails, the job keeps the old tree, writes the error to the journal and exits with a failure. The next run tries again. The job never serves a tree that its keyring does not verify.

The keyring of the job is the key file of the release package that config management installed on the HTTP server. Thus the job has the same trust as a client. A snapshot that a key signs before the clients have that key stays unserved. This is a second guard behind gate 2. After a key compromise, config management replaces this keyring first. Then the job serves no new snapshot with a file of the revoked key (signing.html#compromise).

The file repoctl-snapshot.json tells repoctl what the HTTP server serves:

{"set": "slurm-26.05", "target": "el9", "digest": "sha256:9d07…",
 "publish": "p-20261103-1412-5e1", "pulled": "2026-11-03T14:15:02Z"}

repoctl status reads <repo.url>/<target.path>/repoctl-snapshot.json and shows served: same, served: behind or served: unknown. A new set or target needs one new line in the config of the job (add a target).

Pull

repoctl repo pull [REF] makes the local copy equal to a snapshot: latest (the default), a publish id or a digest. A REF that names no snapshot of the target gives snapshot.not-found (exit 1). It downloads the missing blobs and checks their sha256. It verifies each RPM and each repomd.xml.asc with the keys of sign.keys (all states) before it writes the local copy in one rename. A file of a revoked key gives the warning sign.removed-signer (signing.html#compromise). Then it writes snapshot.json: one Snapshot object of the output schema (contract.html#kinds), from the annotations of the snapshot, without local, served and gc. A file that does not verify stops the pull, and repoctl writes nothing (exit 10). When the signer of a file is not in sign.keys, and the set commit of the snapshot (.set-commit) is not in the history of the set checkout, the checkout is older than the publish. Then the hint of sign.unknown-signer is git pull of the builder branch, then repoctl repo pull again. When the local copy holds a publish of this user that is not on the chain of latest, pull warns with snapshot.orphaned before it replaces the local copy (two admins). Command: repo pull.

Publish order

Publish has one fixed order with eight steps. The journal records each step as a publish.step event with the step name (contract.html#events). The explainer plays the story publish of el9.

Rule

Steps 1 to 5 change only files of the human who publishes. Step 7 is the only step that changes what other humans see. A publish is a success when step 7 is done.

Several targets

One publish id covers all selected targets. repoctl runs steps 1 to 5 for each target, in the order of targets[] in repoctl.yaml, before it pushes a blob. A failure in steps 1 to 5 of one target stops the publish of all targets, and repoctl pushes nothing. Then repoctl runs steps 6 to 8 for one target after the other, in the same order. A failure in step 6 or 7 of one target does not stop the other targets.

A publish that tags some targets and not all is a partial publish. It exits with 13, and the run state is failed. Run.publish[TARGET].state gives the result of each target: ok, failed, canceled or skipped. The tree of each failed target stays pushable. repoctl repo push p-… --target ID completes one target.

Why

The human confirms one summary for all targets, so all targets pass the same checks before the first push. Steps 6 to 8 change only the OCI package of one target. Thus a failed push of el10 does not make the tag of el9 wrong.

Stop and complete

publish writes publishes/p-…/state.json next to the tree after each step. The file holds the publish run as a Run object (contract.html#kinds): per target, the base, the digest of the new manifest and the result of each step. A tree is pushable for a target when its state file records verify and verify-el ok for that target, and step 8 of that target is not done. Only a pushable tree whose base is still latest counts for state.unpushed.

repoctl repo push p-… completes the publish, for each target of the publish or for the target of --target ID:

  1. The state file must record verify and verify-el ok for the target. Otherwise push refuses with publish.not-verified (exit 10).
  2. The files of the tree must give the new manifest digest of the state file. Otherwise push refuses with verify.failed (exit 10).
  3. push reads latest. If latest equals the new digest, step 7 is done: push runs only step 8 and records the success in the journal. If latest equals the base, push runs steps 6 to 8 with the compare of step 7. Otherwise push refuses with snapshot.diverged (exit 13).

Without a publish id, push takes the newest pushable publish. repoctl clean --publish p-… deletes the tree and its state file. repoctl status names each kept tree that is not pushable, or whose base is not latest, with the hint repoctl clean --publish p-…. Commands: repo push, clean.

First publish and import

A first publish of a target has no base: the registry has no snapshot of the target. The freshness check passes. Gate 2 does not apply, because no client uses the target yet. In the story, the first snapshot of el10 is p-20260912-1403-c21.

An import of an existing repository is different, because clients of the old repository exist. repoctl repo push --from DIR --manifest FILE --target ID makes the first snapshot of a target from a signed tree.

The import works only when the registry has no snapshot of that target. Otherwise it stops with import.not-empty (exit 13). It verifies each RPM with sign.keys and keeps the RPM signatures. It adds the RepoManifest from FILE with modifyrepo_c and signs the new repomd.xml with one signature. Then it runs verify and verify-el, and pushes. The publish id is p-import-YYYYMMDD.

Rule

Gate 2 applies to an import. Before the import, the human records the deployment of the old key, for example repoctl sign deployed hpc-repo --release slurm-release-26.05-1 --target el9 --path DIR. Only a target that no client uses yet skips gate 2.

What a publish takes

Publish works on the plan, not on one run. For each selected target, publish takes each node with the plan action staged. Of a staged node, it takes only the files of its artifact.added events, never a whole staging directory, and it checks the sha256 of each file. A staged node has a build for the current lock in an unpublished run of this user (staging and node reuse). The summary names the source run of each node. When two runs have a build of one node, publish takes the build of the newest run (fromRun). --run RUN limits the publish to the nodes of one run.

A target is publishable when each node of the target is current (in the base) or staged. Without --target, publish takes the publishable targets, and the summary names the others. A target that --target names and that is not publishable stops the publish with publish.not-ready (exit 12). When no target is publishable, publish stops with the same code. --hold NODE makes a target publishable for one urgent publish (urgent fix).

Rule: publish the ready target first

Publish a publishable target before you pin a fix of a package that it shares with a failed target. The commit is per package, so the pin ends the staged node of the package on each target. If the publishable target is not yet published, it then needs a new build too. If it is published, the fix gives it a new NVR with the same content. Example: the story run.

Publish never builds. It never signs a node whose plan action is not current or staged. The advisory gate looks at the whole publish, so a dependent that another staged run rebuilt counts (advisories.html#gate).

In the story, the review of el9 at 2026-11-03 14:05 takes the four staged el9 nodes of r-20261102-1750-a3f: ucx, slurm, openmpi and slurm-singularity-exec. These give 38 new RPMs. The 170 RPMs of the base stay, so the new snapshot has 208 RPMs. el10 is not publishable: slurm@el10 failed, and slurm-singularity-exec@el10 is blocked. The web UI shows this on the blocked page.

Urgent fix

A failed, blocked or unbuilt node of an other package makes its target not publishable. For an urgent fix, the human holds that node back for one publish. A held node keeps its build in the base. When the base has no build of the node, the node stays out of the snapshot. The publish takes the other staged nodes as usual.

  • --hold NODE needs --reason TEXT with 8 characters or more. A held node that is current or staged is a usage error (exit 2), so nobody holds in advance.
  • The advisory gate runs on the result tree with the base build of each held node. When a taken node needs the new build of a held node, the gate finds the broken requirement and blocks the publish.
  • The summary shows each held node with the NVR that it keeps and the reason. The annotation io.repoctl.held and the publish history record the held nodes with the reason.
  • The lock does not change. The next plan shows each held node with the action build again.

Two admins

Changes are rare, and the team coordinates in its own channel. Thus repoctl has no lease in the registry. The set lock is a local lock. It protects the processes of one user on one host (build.html#lock).

Rule

Publish compares latest with its base two times: in step 1, and in step 7 just before it moves the tag. If latest moved, publish stops with snapshot.diverged (exit 13). The new snapshot stays as a tag that nobody serves.

Why

GHCR has no compare-and-swap for tags. The race window is the time between the read and the write of the tag in step 7, less than one second. For a small team that coordinates in a channel, this window is acceptable. A lease would need a second shared record and a way to break it.

After snapshot.diverged, run repoctl repo pull, then plan and publish again. repoctl repo snapshots --all lists the diverged tag.

In the race window, two publishes can both pass step 7. The second tag write wins, and the first snapshot leaves the chain of latest. Its NVRs reach the served tree only if the mirror job reads latest in that window. repoctl finds this case: when the local copy holds a publish of this user, and latest is newer, repoctl walks the parent chain of latest back to the first snapshot that is older than the local copy. If the publish of the local copy is not on that chain, repo pull and status give the warning snapshot.orphaned, and plan, build and publish give it with state.behind. The hint is repoctl repo pull, then plan and publish again.

Rule

A run counts as published only when its publish is on the chain of latest. Thus the staged nodes of an orphaned publish are staged again, the next plan shows them as staged, and repoctl clean keeps their staging. The next publish signs them again: the NVRs and the payloads stay the same, only the signatures change.

Summary and confirmation

Publish shows a summary before it asks. The summary always shows these items:

  • the publish id, the target and the source run (the header line), the base (latest, its digest and the state of the local copy) and the store,
  • the signer with its deployment record,
  • one row per changed source package: published NVR, new NVR and RPM count, then the totals and the count of unchanged packages,
  • the sign counts per key: new, keep and re-sign,
  • the checks: the inputs (the set commit and the package commits are pushed), the trust state, gates 1 to 3, the signer probe and the advisory gate,
  • when the publish holds a node, the held nodes with the NVR that each keeps and the reason (urgent fix).

Snapshot format and names

A snapshot is one OCI artifact: one manifest per set and target, with one blob per file. It holds all three repositories of a target: slurm, slurm-source and slurm-debuginfo.

ItemValue
Package<store.oci>/<set>-<target>
Tagslatest, and one tag per publish id, for example p-20261103-1412-5e1. The package name holds the set and the target, so the tags do not repeat them.
artifactTypeapplication/vnd.repoctl.repo.v1
LayersOne blob per file. The annotation org.opencontainers.image.title gives the path in the tree, for example slurm/Packages/u/ucx-1.22.1-1.el9.x86_64.rpm.
Annotationsorg.opencontainers.image.source (the GitHub repository of the set), io.repoctl.set, .target, .publish, .kind (publish, restore, prune, resign, import), .parent (digest of the base), .set-commit, .signer (full fingerprint), .user, .host, .created, .repoctl-version, .advisories.accepted (the acceptances of this publish, with the reason), .held (the held nodes of this publish, with the reason). An unattended publish also records unattended: true with the trace parent.

The annotation .parent links each snapshot to its base. This makes a chain. repoctl repo snapshots lists the chain of latest, newest first. --all also lists the tags outside the chain, for example a diverged publish (repo snapshots). The chain of el9 in the story:

The annotations go away when gc deletes a snapshot. Thus the RepoManifest of each snapshot also holds the publish history history[]: one entry per publish of the chain, with the publish id, the kind, the human, the host, the signer, the set commit, each acceptance with its reason, each held node with its reason and each trust change. Each snapshot copies the list from its base and adds its own entry. The list is in the signed repodata, and latest always holds it. Thus latest is the full audit record of the target, also for the snapshots that gc deleted (model.html#manifest). repoctl repo snapshots --history lists it.

RepoManifest and removed[]

The RepoManifest (model.html#manifest) is in the repodata of the binary repository (slurm/) only. Its entries list the source RPM and the debuginfo RPMs, so slurm-source and slurm-debuginfo need no manifest of their own.

The RepoManifest has the list removed[]. Each entry has the NVR, the sha256 of each RPM, the publish id and the reason (prune or restore). Each new snapshot copies the list from its base. Thus plan and publish know each NVR that clients can still have, also when the repository no longer holds it. Publish refuses a build that gives such an NVR again with other content (nvr.removed, exit 12).

Why OCI artifacts with one blob per file

Each file has a content hash, and the registry stores each blob once. A prune is a new manifest without the file. The registry frees the blob when no manifest uses it, that is after gc deletes the old snapshots (gc and retention). A restore pulls one manifest. Image layers would bind files to publishes and make a prune hard. oras-go does the work inside the Go binary, and GHCR gives a shared state to the team.

GHCR has no garbage collection that a user starts. repoctl repo gc deletes package versions through the GitHub REST API (gc and retention). Public packages are free. Private packages count against the storage quota of GitHub Packages. The debuginfo repositories are the largest part.

Keep all versions and prune

Publish adds to the repository. It never deletes. All old versions stay, as with createrepo_c --update in the bash scripts. Clients can still install each old version. Step 4 enforces this rule: a file of the base that is not in the new tree gives verify.failed, also when the local copy lost the file (publish order).

repoctl repo prune removes NVRs only on request. The dry run is the default, and --apply acts. With --apply, prune is a publish run of kind prune: steps 1 to 8 make a new snapshot without the selected NVRs (checks per kind). The NVRs go into removed[]. Old snapshots still hold the files until gc deletes these snapshots. Thus the registry frees the blobs of a pruned NVR at the earliest retention.snapshots.keep_removed after the prune (default 1y), when gc runs. A prune of debuginfo frees storage only then. The selectors combine:

SelectorEffect
--target IDOnly these targets. The default is all targets of the set.
--repo binary|source|debuginfoOnly this repository, for example --repo debuginfo --keep-last 1.
--keep-last NKeep the newest N NVRs of each package name.
--older-than DOnly NVRs older than D, for example 2y.
--package NAMEOnly this source package.
--package NAME --allAll NVRs of a source package that is retired on the target (retire a package).
--nvr NVROne build with all its subpackages, for example slurm-26.05.2-1.el9.

Rule

Prune never deletes the newest NVR of a kept package. Prune never deletes a release NVR that a deployment record in keys/deployed.yaml names for the target, because gate 2 and verify-el need its key file (signing.html#gates). A prune adds no broken requirement: repoctl runs the repoclosure of the publish gate on the base and on the result tree, and each broken requirement of the result tree must also be in the base. Thus an open upstream break, for example closure.broken/pmix@el9, does not block a prune. A selector that matches many NVRs (--keep-last, --older-than, --package) keeps a protected NVR, and the dry run names the rule. --nvr or --package NAME --all that selects a protected NVR stops the prune with prune.unsafe. --package NAME --all needs a package that is retired on the target; otherwise exit 1 with prune.not-retired. A safety rule that refuses gives exit 12. Nothing to prune gives exit 4.

Command: repo prune.

Restore and fix forward

To take back a bad build, fix forward: make a new commit or a rebuild (build.html#rebuild), so that the release goes up, and publish. Clients then update to the fix. This is the normal way back.

A revert of a version bump gives a lower NVR, for example ucx 1.22.0 after 1.22.1. dnf never installs a lower NVR on a client that has the higher one, so publish refuses it with nvr.older (exit 12). To take back a version, raise Epoch in the spec, or give the old code a version that is higher than the bad one. Clients that installed the bad NVR then update to the fix. New clients get the fix.

repoctl repo restore REF is for a broken repository, for example bad repodata. It makes a new snapshot with the files of the older snapshot REF and moves latest to it. latest moves forward to a new digest. It never moves back to the old digest. Restore is a publish run of kind restore: steps 1 to 8 with the checks of its kind (checks per kind), gates 1 to 3, verify and verify-el.

  • The summary lists each NVR that leaves the repository. It says that clients keep these NVRs, because dnf does not downgrade.
  • These NVRs go into removed[]. After a restore, publish refuses a build that gives one of them again with other content (nvr.removed, exit 12). The hint is repoctl rebuild DIR --reason "…".
  • RPMs in REF that a key in state removed or revoked signed get a new signature from the human who restores (re-sign rules).
  • The new snapshot keeps each release NVR that a deployment record names for the target, also when REF does not hold it. Thus gate 2 and verify-el still find the key file of each signer. The summary lists these NVRs as "kept: deployment record". For example, a restore of el9 to p-import-20260828 keeps slurm-release-26.05-2, the release of the record of d.klein; REF holds only slurm-release-26.05-1.

After a restore, the lock still pins the commits of the builds that left. plan shows these nodes with the action build, and each build gives a removed NVR again: publish refuses it with nvr.removed. Before the next publish, do one of these steps for each package that the summary names:

  • Run repoctl rebuild DIR --reason TEXT. The release goes up, so the new NVR is newer than the removed one.
  • Or move the worktree to the commit of the build in REF and run repoctl pin DIR --older, because that commit is behind the branch. plan then shows the node as current.

The summary counts these packages, and Run.publish[TARGET].rebuild lists them. A variant of the story, not the story: the repodata of p-20261103-1412-5e1 is bad, and d.klein restores el9 to the snapshot before it:

gc and retention

repoctl repo gc deletes old snapshots (package versions) in GHCR with the GitHub REST API. GitHub then frees the blobs that no version uses. The dry run is the default, and --apply acts.

Rule

gc never deletes these snapshots:

  • latest,
  • the newest N snapshots of the chain (default 10),
  • the snapshots younger than D (default 90 days),
  • for each entry of removed[], the newest snapshot that still holds it, until keep_removed (default 1y) after the publish that removed it.

gc deletes the annotations of a snapshot with it. The publish history in latest keeps who published, who signed and which advisories were accepted, with the reason (snapshot format).

Thus each RPM that a client can have stays in at least one snapshot for keep_removed. After that time, gc can delete the last snapshot that holds it. removed[] still holds the NVR and the sha256 of each RPM, so nvr.removed still works.

The defaults come from retention.snapshots in repoctl.yaml (keep: 10, keep_days: 90d, keep_removed: 1y, see config.html#set-config). The flags --keep N, --keep-days D and --keep-removed D change them for one call. gc needs the token scope delete:packages and admin access to the package. gc never runs unattended, because it deletes history (cli.html#safety). Nothing to delete gives exit 4. Command: repo gc.

gc --apply is a run of kind gc with its own journal. It deletes the package versions of one target after the other, oldest first, so the chain from latest has no gap. It writes one gc.deleted event per deleted version: target, publish id and digest (contract.html#events).

Rule: a failed delete

When the GitHub API refuses or fails one delete, gc stops at once. The versions that it deleted before stay deleted, and the journal lists them. gc exits with 13: registry.denied for a missing scope or role, else gc.failed. A second repoctl repo gc --apply continues, because gc computes the list again from the registry.
