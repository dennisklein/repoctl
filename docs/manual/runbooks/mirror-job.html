Failed mirror job

Use this runbook when the mirror job does not serve latest. The clients keep working, but they do not get the new snapshot. The rules of the job are in Publish: mirror job and job health and alerts.

  • When a step fails, the job keeps the old tree.
  • The job never serves a tree that the keyring of its mirror line does not verify.
  • The journal of the job on the HTTP server names the failed step.
  • Each failure has a cause on the HTTP server, in the registry or in the snapshot.

Rules

  • A human with access to the HTTP server does the steps there. repoctl does not run on the HTTP server.
  • Do not change the keyring of a mirror line by hand to make a snapshot pass. Config management puts it in place from the release package of the set and target.
  • Do not write into the served tree. Only the job writes it.

The examples use the story: the el9 publish p-20261103-1412-5e1 at 14:13, and the served path /srv/repos/slurm-repo/slurm-26.05/el9.

Trigger

  • repoctl status shows served: behind more than 15 minutes (three runs of the timer) after a publish.
  • repoctl status shows served: unknown: the file repoctl-snapshot.json is not at the URL.
  • The service unit of the job is in state failed on the HTTP server.

Find the failed step

  1. On the HTTP server, run systemctl status repoctl-mirror.service and journalctl -u repoctl-mirror.service --since -1h. The last error names the set, the target and the step.
  2. From an admin host, run repoctl repo verify --snapshot latest --el --target el9. Exit 0 means that the snapshot is good, and the cause is on the HTTP server.
  3. Find the cause in Causes. Fix it.
  4. Run the job once: systemctl start repoctl-mirror.service. Read the journal again.

Why the fix is a deployment of the key

A signer that is not in the key file of the HTTP server is the second guard behind gate 2 (gates). When the clients also miss the key, a signature of that key would break them. Thus the fix is a deployment of the key, never a change of the keyring.
