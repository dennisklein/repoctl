Tutorial: start a new set

In this tutorial you start the set slurm-26.11 from the set slurm-26.05. You fork the package branches, bump slurm, build for EL9 and EL10, publish the first snapshots and roll them out to the clients.

  • You need an installed repoctl, a signing key, a registry login and a set slurm-26.05 that you can read. Read Install repoctl first.
  • The steps are those of repoctl help new-set. Each step names the repository that gets the commit.
  • repoctl never pushes for you. It prints the push command.
  • If you stop, run repoctl status. It lists the steps that are still open.

The plan

Stage 1: prepare the set in git

Step 1: make a worktree for the new set branch

Work in the git directory of your set. Make a new worktree on a new branch, from the old set branch. Repository: the set repository.

$ git fetch origin
$ git worktree add -b set/slurm-26.11 ../slurm-repo-26.11 origin/set/slurm-26.05
$ cd ../slurm-repo-26.11

Step 2: fork the set files

repoctl init --from copies the config of the old set and renames each branch from slurm-26.05 to slurm-26.11. It writes an empty lock.

$ repoctl init --from set/slurm-26.05 --name slurm-26.11
wrote repoctl.yaml   set slurm-26.11, 10 branches renamed (slurm-26.05 → slurm-26.11), 0 shared branches
wrote repoctl.lock   empty
Next: steps 3 to 15 of "repoctl help new-set": …

The new set takes the repo name and the targets of the old set. To change them, edit repoctl.yaml later. Do not use --repo or --add-target with --from.

Step 3: set the URL and the release package

  1. In repoctl.yaml, set repo.url to the public URL of the new set, for example https://repo.example.org/slurm-26.11.
  2. In the spec file of the in-tree package packages/slurm-release, set Version: 26.11.
  3. Run repoctl release write. It writes the key file and the .repo files of the release package.
  4. Commit all of it. Repository: the set branch.
$ repoctl release write
$ git commit -am "feat: start set slurm-26.11"

Step 4: fork the package branches

checkout --create --from-set makes one new branch for each package, at the lock commit of the old set. The history, the rpmautospec release counter and the changelog continue.

$ repoctl checkout --create --from-set set/slurm-26.05
munge   munge/slurm-26.11   forked from munge/slurm-26.05 at 1723823
ucx     ucx/slurm-26.11     forked from ucx/slurm-26.05 at 1d1a9eb
…
slurm   slurm/slurm-26.11   forked from slurm/slurm-26.05 at 60e1f6d
…
10 branches created, 0 exist on the remote
Next: git push origin munge/slurm-26.11 ucx/slurm-26.11 …
      git -C packages/rocm-smi push origin slurm-26.11
      repoctl pin

The in-tree package slurm-release has no branch. Thus 10 of the 11 packages get a branch. An external package, for example rocm-smi, gets its branch in its own repository. The project must exist on that git server.

Step 5: bump slurm, push and pin

  1. Find the newest release: repoctl upstream slurm --releases.
  2. Edit the spec in the worktree packages/slurm. Set Version to the new release, for example 26.11.0. Change the sources if needed.
  3. Commit in that worktree: git -C packages/slurm commit -am "Bump to 26.11.0". Repository: the package branch.
  4. Push all package branches. Copy the command from the output of step 4.
  5. Run repoctl pin. It writes one line for each package into repoctl.lock.
  6. Commit and push the lock. Repository: the set branch.
$ repoctl pin
munge   new → 1723823  munge/slurm-26.11   "Import munge 0.5.18"
…
$ git commit repoctl.lock -m "feat: pin the packages of slurm-26.11"
$ git push origin set/slurm-26.11

Push the package branches

If you pin before you push, pin warns for each package: "is not on origin/…". Push the package branches before you publish. Clients and other admins need these commits.

Stage 2: build

Step 6: check the host and the set

$ repoctl doctor

Fix each failed check. Until step 10 is done, repoctl doctor shows the open step registry.public for the new set. This is normal now.

Step 7: read the plan

$ repoctl plan

Expect the action build with the reason new-package for every node. The new set has no snapshot yet, so nothing is current. Run repoctl graph to see the build order of each target.

Step 8: build

$ repoctl build

repoctl builds each node in a mock chroot, as soon as its dependencies are done. The result goes to the staging of a new run. Nothing is public.

  • Watch the run in the web UI: repoctl ui, or in the terminal with repoctl runs --follow.
  • Read the log of a node: repoctl logs RUN NODE.
  • A failed node stops the nodes that need it. Fix the package, commit, push, repoctl pin PKG, and run repoctl build again. It builds only what is not built.
  • Stop a build with repoctl cancel.

Stage 3: publish

Step 9: publish the first snapshots

Run a dry run first. It shows the summary and runs all checks. It signs nothing.

$ repoctl publish --dry-run
$ repoctl publish
Type the set name to publish el9 el10 of slurm-26.11:

Type slurm-26.11 to confirm. repoctl signs the RPMs with your key, pushes one snapshot for each target, and moves the tag latest. The first publish of a target needs no deployment record, because no client uses the target yet. A required advisory can block the publish. Read repoctl advisories ls.

Rule: the first publish needs a free URL

The first publish stops with exit 12 when repo.url already serves a repo. Use a new URL for each set.

Stage 4: roll out to the clients

Step 10: make the new OCI packages public

An organization owner opens each new OCI package in GHCR, sets it to public, and turns on "Inherit access from source repository". repoctl doctor then passes registry.public.

Step 11: serve the repository

On the HTTP server, add one mirror line for each target to the mirror job. Put the key file of the release at its keyring. Read the mirror job runbook.

Step 12: install the release package on the clients

Install the release package slurm-release on the EL9 and EL10 clients with your configuration management. Then record it for each active key and target. repoctl asks you to type the key id.

$ repoctl sign deployed d.klein --release slurm-release-26.11-1 --target el9
$ repoctl sign deployed d.klein --release slurm-release-26.11-1 --target el10

Commit and push the changed files of keys/. Repository: the set branch. The release NVR is in repoctl repo ls --name 'slurm-release*'.

Step 13: start the check timer

$ repoctl check --install-timer

This writes and starts a user systemd timer. It computes the advisories each day, and it opens an advisory when the world changes. Remove it with repoctl check --remove-timer.

Done

Run repoctl status. It should list no open setup step. A client can now run dnf install slurm-release and then dnf install slurm. To keep the set healthy, read Operate a set.

If something goes wrong

You seeDo this
branch.exists-remote in step 4The branch exists on the remote. Run repoctl checkout PKG in place of --create.
Exit 5 from a commandA worktree does not match the lock, or a change is not committed or not pushed. Run repoctl status.
Exit 9 from buildThe host is not ready. Run repoctl doctor.
Exit 12 from publishA rule refuses the publish. Read the error code and the hint.
Exit 13 from publishThe registry or the remote stopped the command. Check the login and the network, then run repoctl repo push to complete the publish.

The reference of the exit codes is in CLI reference. The design of this task is in Sets and packages.
