Verdict. The core model is good. The safety rules for publish are strong, and the daily build loop on one host is clear. But the design record is not ready for implementation. Two things block it: the 03 build model did not reach the CLI reference, the contract and MCP, and the publish and snapshot flow has no defined order or source of truth.

  • 66 findings after the merge of 98 reviewer findings: 5 blocker, 32 major, 28 minor, 1 nit. The reviewers dropped 61 more candidates after their own check against all documents.
  • Weakest journeys: team work (A5) and failure and recovery (A4). Of 134 journey steps, only 19 are fully covered, 89 are partial and 26 are missing.
  • Most fixes are document work (effort S or M). Four fixes need a decision from Dennis first: where clients read the repo, which record is the truth, how a key deployment is proven, and which GHCR namespace the team uses (section Open questions).
  • Recommended next step: one propagation pass from 03 into 04 (mechanical), then one new spec "05 publish, snapshots and team" after the four decisions. See Proposed order of work.

How we reviewed

Scope: the design record on branch main (README, design index, documents 01 to 04, mockups, contract schemas and examples). Six reviewers worked in parallel. Each reviewer took one user journey, walked it step by step as a persona, and checked each finding against all documents before it reported the finding. Each finding has short, exact quotes as evidence. The lead then merged duplicates, checked the blocker claims in the source files, and changed the severity of six findings (each card says why).

Severity scale. Blocker: the journey cannot finish with the documented design, two documents contradict so that an implementer must guess, or the design can publish a repo that clients reject without notice. Major: the journey works but needs an error-prone manual step or tribal knowledge, or has a safety gap. Minor: friction, a missing hint, an inconsistent word. Nit: wording.

What the lead checked in the source files: the three contract schemas have no match for "advisor"; Figure 3 of 04 says gate 2 is "FPR in published slurm-release" and "First publish of a set (no release package yet) skips gate 2"; the two 03 figures show the snapshot push after the repo update and the mirror "written from the snapshot by publish"; the bump-package skill allows Bash(git -C packages/:*) and denies only Bash(git push:*); the set lock is $XDG_RUNTIME_DIR/repoctl/<set>.lock; 04j says "The UI does not offer a partial publish".

Six cross-cutting themes

Most findings fall into six themes. Each theme names its findings and shows the problem in a diagram.

Theme 1. The 03 build model did not reach the reference

03 changed the build model: a rebuild is an empty commit, the plan says build, current, staged or skip, and advisories replace automatic rebuilds. 04 section 2 says that 03 wins. But only the two UI v2 sections were written again. The CLI reference, the terminal mockups, the contract, the MCP tool list, the skills and the help topics still describe the old model. An implementer reads the CLI reference first. Findings: UX-02, UX-40, UX-52, UX-51.

Theme 2. Where does the truth live?

03 makes the published repo the build state and adds an OCI snapshot store for the team. Now three records say what is published: the manifest in the mirror on disk, the -latest tag in GHCR, and published.yaml in one user's XDG state. Each command reads a different one. No document gives the order in which publish writes them, or what happens when one write fails. Findings: UX-01, UX-07, UX-08, UX-11, UX-13, UX-19, UX-20.

Theme 3. Team safety: keys and concurrent publishes

Personal keys with one signature per file are a good decision. The gates in publish turn the onboarding rule into a tool check. But gate 2 checks the wrong fact, and the set lock does not reach a second user or a second host. Findings: UX-04, UX-06, UX-09, UX-21, UX-22, UX-23, UX-24, UX-25, UX-26, UX-35.

Theme 4. Advisories need a surface outside the UI

Advisories replace automatic rebuilds, so they carry the safety of the new model. Today they exist only as UI cards. The CLI, the contract and MCP have nothing, and the publish override is a flag name only. Findings: UX-03, UX-12, UX-34, UX-38, UX-18.

Theme 5. Package and set lifecycle has gaps at both ends

The middle of the lifecycle is well designed: pin, plan, build and publish. The start and the end are not. A new set cannot fork the branches of the previous set, migration cannot adopt today's repo, and a package can never leave the repo. Findings: UX-05, UX-27, UX-28, UX-29, UX-30, UX-31, UX-32, UX-33, UX-42, UX-43, UX-44.

Theme 6. UI, agents, CLI and MCP do not match

Each UI dialog shows its CLI command, and one journal feeds all surfaces. Those are strong choices. But many actions exist on one surface only, and the agent safety rests on a mode that is not specified. Findings: UX-15, UX-16, UX-17, UX-18, UX-36, UX-37, UX-49, UX-50.

Blocker UX-01 · Publish has no defined push step, order or source of truth

Major UX-06 · Set lock is per user and per host, so it cannot exclude two admins

Angle: A5 Team: second admin, keys, shared state · Kind: safety · Fix effort: M · Raised as: A5-02

03 section 6 says that the set lock convention covers the race between two publishes. But the set lock is a file in $XDG_RUNTIME_DIR, which is a per-user tmpfs. Two admins on one host have two lock files, and two hosts share no lock. The design also does not say when publish compares …-latest. If the compare happens only in the check step, the race window is the full sign time, which takes minutes with a YubiKey. When two publishes overlap, the second snapshot does not hold the packages of the first one. Both publishes then report success.

Evidence (5)
  • 03 section 6: Registries have no atomic tag compare-and-swap, so a small race window stays; the set lock convention covers it for a small team.
  • 03 section 6: Publish checks that …-latest still points to the snapshot that the build started from.
  • 04c section 8: The set lock $XDG_RUNTIME_DIR/repoctl/<set>.lock: one writer per set at a time (fsutil.Lock). It records the holder: command, pid, host, user, start time and run id.
  • 04b section 2: This directory is a per-user tmpfs under systemd-logind
  • 04j section 4 step 3: Signing is serial, because one smartcard signs one file at a time.
Recommendation. Do not use the set lock as protection between admins. Compare …-latest two times: in the check step, and again just before the tag update and the swap. Add a lease in the registry. Before it signs, publish writes a tag such as <set>-<target>-lease with user, host, publish id and expiry. Publish refuses when another person holds a fresh lease (problem publish.busy, exit 7, hint with holder and age). After the tag update, read …-latest again, and fail with a clear error if it does not point to this snapshot. Remove the sentence about the set lock convention, or define the convention.

Strengths to keep

All six reviewers named strengths. These are the ones that two or more angles named, or that carry a decision.

  • Set discovery works like git, and repoctl.yaml is strict: an unknown key is an error, and repoctl schema serves editors and agents.
  • The build order comes from the spec BuildRequires. Nobody edits a build order by hand any more.
  • Per-package targets work well. The selector error names the reason (rocm-smi is not built for el10), and plan warns before the build.
  • Exit codes are a stable contract. A failed command still writes a JSON envelope. Errors have one line and at most three hints with a command to copy.
  • Keep going is the default, and good nodes of a failed run come back as staged. An el10 failure does not cost the el9 work.
  • Publish safety is strong: summary first, default no, refusal without a terminal, all checks before the first signature, verify with a temporary keyring of the set keys, nothing swapped on failure.
  • Personal keys with one signature per file fit EL9 and EL10. Gate 1 and gate 2 make the onboarding rule a tool check. sign offboard prints the exact client commands.
  • One journal and one fold function feed the CLI, the UI and MCP. Runs record their origin, and runs --follow attaches a terminal to any run.
  • Every UI dialog shows its CLI command. The rebuild dialog shows the commit, the NVR change, the changelog entry and "push is your step".
  • The Advisories card lists the checks with no finding and the checks that are not set up, so "no row" never means "not checked".
  • Agent buttons only propose. Each proposed action is a normal button, and the buttons are not rendered without an agent. The needs-human pattern gives agents a clean handover.
  • Credentials never go into a config file or a log.
